## 二、欧工真实工作流还原（七环节）

### 环节 1：资料准备（建"池子"）
- 客户发来协议 PDF（几十上百个指令）或需求材料。
- AI 按工作流 SOP **先建标准化项目文件夹**（欧工原话："你可以把它当做一个池子，然后收集这个项目的资料"）。
- 收集范围：数据手册、单片机引脚定义、原理图、功能说明、协议文档等；**按工作流规则自动归档**到对应文件夹。
- 不同项目资料不一样，按项目来收集归档，使用灵活。

### 环节 2：硬件接口整理
- 写任何完整驱动之前，工作流**约束 AI 先去找原理图和数据手册**，结合资料把**芯片接口先整理清楚**，留存到项目资料里。
- 欧工原话："AI 先得知道你这个板子是怎么接的"。
- 后面写代码、查问题都需要用这份接口资料核对。

### 环节 3：功能说明固化
- 客户功能需求提前整理好，**留存到项目资料**里，后面开发、测试都要用。
- 维护铁律：客户改要求后，**代码和功能说明必须同步更新**——"不能说程序已经改了，但是功能说明还是上一版的"。

### 环节 4：代码开发
- AI 按协议 + 接口资料 + 功能需求写代码。
- 写代码规则由欧工**前期花大精力调优**，因此每个项目产出的代码架构、质量都标准化。
- 碰到芯片配置问题，AI **自动回到手册和例程里查**（规则已写进工作流，不用人工每次解释）。

### 环节 5：编译下载（自动化）
- 编译、烧录动作由工具链自动执行（AI 产出代码后直接进入编译下载），不再人工搬运。

### 环节 6：测试验证（闭环调试核心）
- **反面模式**（欧工明确批判）：只让 AI 写代码 → AI 写完人去编译下载、测试、看程序变量值、日志，人绞尽脑汁把问题现象描述给 AI，AI 改一遍、人再测一遍——"人一直在中间给 AI 打杂"。
- **正面模式**（工作流核心设计）：把**调试工具接进工作流**——
  1. AI 写完代码 → 2. 自动编译下载到板子 → 3. **拿板子实际运行数据**（变量值/日志/现象）→ 4. 根据数据分析问题 → 5. 排查 → 6. 修复 → 7. 再自动编译下载 → 8. 复测 → 循环**直到跑通**。
- 欧工原话："这样才算是把 AI 提效真正落地"。

### 环节 7：交付与验收
- AI 交到手时协议功能已经跑通，**人只做检查和验收**。
- 交付文档归档（交付目录）；后续维护走环节 3 的同步更新铁律。

### 前置三件事（欧工强调的就绪条件）
1. **协议文档你要给它读到**（文档可读）；
2. **硬件你要给它接好**（硬件就绪）；
3. **调试工具要能正常采集数据**（数据可采）。
- "AI 拿不到正确的运行结果，就没有办法去判断这次修改有没有起到作用。"

### SOP 与知识沉淀
- 以上做法全部整理进**工作流的 skill**里；按 SOP 走就能生成标准化的项目背景资料。
- 换一个项目按同一套 SOP **无限复用**；项目背景不因换对话/换上下文而丢失（资料留存 + 规则内嵌）。
- 学员实证："直接调用 skill 等待结果就行。"

### 效果数据
- 欧工本人：原来写两三个月的代码，现在基本一两周完成（硬件没问题、功能清晰的前提下）。
- 学员：以前 3-5 个月的项目，现在代码及调试部分最多 2 周；需求明确时几天。

## 三、欧工标准项目目录（课件实证原样）

```
项目根/
├── .claude/            ← AI 工作流配置目录（skill/SOP 载体）
├── 00_项目管理         ← 项目计划、进度、会议/需求记录
├── 01_硬件设计         ← 原理图、数据手册、引脚定义、PCB
├── 02_软件源码         ← 代码工程（按芯片工具链组织）
├── 03_结构设计         ← 结构件/外壳相关
├── 04_测试验证         ← 测试用例、测试记录、运行数据/日志
├── 05_生产资料         ← 生产/贴片/烧录相关
├── 06_开发工具         ← 工具链、脚本、调试工具配置
├── 07_参考资料         ← 例程、第三方资料、协议原文
├── 08_交付文档         ← 交付物：功能说明、使用说明
├── 09_归档             ← 历史版本、旧资料
├── AGENTS              ← AI 代理规则文件
├── CLAUDE              ← AI 代理规则文件（Claude 口径）
└── README              ← 项目说明
```

- 资料归档流向：协议 PDF/需求 → 00 或 07；原理图/数据手册/引脚定义 → 01；代码 → 02；运行数据/日志/测试记录 → 04；工具链与脚本 → 06；例程 → 07；功能说明/交付物 → 08；旧版本 → 09。

## 四、仿真改造映射（真实环境 → 本机仿真，契合 v2.0）

改造原则：**结构不动、环节不动、SOP 不动；只把"真实硬件"换成"本机仿真执行器"**。全部本机回环运行，禁真实外连公网（四不红线保留）。

| 欧工真实环境 | 仿真改造（Windows 本机直跑） | 说明 |
|--------------|------------------------------|------|
| 真实开发板（STM32/ESP32 等） | **Renode**（开源，Antmicro，支持 STM32/ESP32/RISC-V 多系列，Windows 原生运行）为主；QEMU 为辅 | 板子→仿真器实例；一个仿真器实例=一块"板子" |
| 调试器/串口线 | Renode 内置 UART/分析器，日志重定向到文件；或虚拟串口对（com0com，开源）+ 本机串口工具 | 运行数据可采集=前置三件事之第 3 件 |
| 编译下载（烧录器） | 保留原芯片工具链（arm-none-eabi-gcc / ESP-IDF / 开源 51 工具链），"下载"动作=把固件加载进仿真器 | 编译环节不变，烧录语义换成加载 |
| 协议对端设备（客户设备/上位机） | Python 脚本模拟协议对端，与本机仿真器走**回环 Socket（127.0.0.1）** | 协议联调闭环在本机完成，不碰真实外网 |
| 示波器/电源等仪器 | 不需要（数字仿真环境无物理信号）；故障注入用仿真器脚本实现 | 对应烧机大法的"限幅注入"思想：注入须设限 |
| 运行数据（变量/日志/现象） | Renode 执行日志 + 外设状态快照 + 串口输出落盘到 04_测试验证 | 与真实板子的数据同构，AI 分析逻辑不变 |

**改造后闭环（与欧工七环节一一对应）**：
1. 资料准备：不变（本机文件，AI 可读，自动归档到目录池）。
2. 接口整理：不变（原理图 PDF/手册 PDF 由 AI 读取整理；小智场景用仿真板卡的引脚映射文档替代实物原理图）。
3. 功能说明：不变。
4. 代码开发：不变（AI 按规则写代码，配置问题回手册/例程查）。
5. 编译下载：工具链编译 → 固件加载进 Renode。
6. 闭环调试：Renode 运行 → 日志/外设状态/串口输出落盘 → AI 读数据 → 分析修复 → 再编译加载 → 复测直到跑通。**人只验收**（模型只规划不直控、执行只认回执的底座纪律完全兼容：每次编译/加载/采集都是一步任务，AI 凭回执推进）。
7. 交付：功能说明与代码同步更新后交付归档。

**与底座/小智的衔接**：
- 欧工工作流作为嵌入式类目的**项目开发 SOP**挂载；其"标准化目录池"与底座"类目注册+适配契约"天然对齐（每个项目=一个实例，目录池=实例的工作区契约）。
- 小智 = 该 SOP 下第一个跑通实例（小智固件在 Renode/仿真环境编译加载运行，串口日志闭环调试跑通，即"注册+下发完整任务并收到结果事件"的类目内验收）。
- 就绪自检沿用 spec v2.0 口径：工具链可编译、仿真器可加载、日志可落盘，三项过了才允许开工（对应欧工"前置三件事"）。

## 五、使用规则（本项目内执行本工作流时）

1. 新项目开工第一步：AI 按 SOP 建目录池（第三节结构），缺目录不得开写代码。
2. 任何驱动开发前，01_硬件设计 里必须有已整理的接口资料，否则该任务不许下发。
3. 每轮调试的运行数据必须落盘 04_测试验证（带时间戳），AI 的分析结论必须引用落盘数据，禁止凭空描述现象。
4. 代码变更必须同步更新 08_交付文档 的功能说明，不一致视为任务未完成。
5. 仿真资源（Renode 实例/回环端口/日志文件）用完释放，崩溃即重建（本机直跑、弄坏重装自负口径）。
6. 全程不连真实设备、不外连公网；协议对端一律本机回环模拟。
