# 知识库维护机制

> 本文档是知识库维护的唯一规程入口。后续会话仅凭本文档 + notes/知识库索引.md 即可执行维护，不依赖会话记忆。
> 建立日期：2026-11-06。依据：docs/官方最佳实践-如何写好一个Skill-bp0010.md（已验证）、docs/项目协作公约-最终稿.md（定稿）、notes/知识库初始化.md（已验证约定）。最后核验：2026-11-06。

## 1. 三库归属判定决策表

| 内容来源 | 归属目录 | 类型标注 | 判定依据 |
|---------|---------|---------|---------|
| 官方文档（外部官方来源） | docs/ | 官方参考文档 | 命名规则"类型-主题-编号.md"，须可识别官方来源 |
| 用户定稿规范（公约类） | docs/ | 定稿规范 | 须可识别用户定稿身份 |
| 工作过程笔记、索引、浓缩版、档案 | notes/ | 工作笔记/索引/档案区 | 派生内容，非官方原文 |
| 规范流水线产物（spec/design/tasks/审查/测试报告） | .codeartsdoer/specs/ | 流水线产物 | specs/ 既有约定 |
| 技能知识包（SKILL.md） | .codeartsdoer/skills/ | 技能 | 码道运行时约定位置 |

执行规则：
- 官方文档禁止写入 notes/，临时过程记录禁止写入 docs/；意图出现即拒绝并给出归属建议。
- 归属两可 → 停止归档，呈报两可原因请用户裁决（禁猜禁编）。
- 同主题双处存在 → 盘点差异后交用户裁决保留方。
- 单一权威源：同主题笔记与 Wiki 并存时，docs/ 原文为权威，notes/ 侧只存摘要与原文链接。

## 2. 增删改查四操作规程

- **增**：先查 notes/知识库索引.md 确认同主题是否已存在 → 已存在则增量更新原条目并刷新核验日期；不存在则新建并在索引登记。禁止另起新文件重复承载同主题。
- **删**：逐条目获用户明确批准 → 删除正文 → 同步清理索引条目与对应浓缩版 → 复查无残留引用。无批准不发生任何删除。
- **改**：docs/ 官方原文只增不改（仅可追加核验批注，不篡改正文）；notes/ 笔记类可改，改后同步更新最后核验日期。
- **查**：从索引定位 → 只加载索引与被命中条目。禁止为查询目的全量扫描或全量加载。
- 任何维护动作的上下文加载范围恒为"索引 + 本次涉及的目标条目"。

## 3. 三级渐进加载机制

与官方最佳实践 bp0010 的渐进式加载三层架构同构（依据：bp0010 原文，已验证）：

| 层级 | 承载物 | 何时进入上下文 | 体量 |
|------|-------|--------------|------|
| 第一层：常驻元数据 | notes/知识库索引.md 条目（名称/主题/路径） | 会话需要调用知识库时即加载 | 极轻量 |
| 第二层：按需摘要 | notes/浓缩版/ 对应文件 | 索引定位后加载 | 中等，不设行数上限【用户裁决 2026-11-06：内容完整优先】 |
| 第三层：深读原文 | docs/ 原文 | 仅当浓缩版不足以支撑当前任务，且有明确理由时 | 全量 |

浓缩版约束：必含原文路径、核心要点、关键结论、最后核验日期四要素；与原文同名存放（同名即对应）；原文变更后同步更新，冲突以原文为准；原文不存在时该条目标记异常并暂停依赖它的任务。

## 4. 异常处置清单

| 异常 | 处置 |
|------|------|
| 归属两可 | 停止归档，呈报原因请用户裁决 |
| 索引未覆盖实存文档 / 指向不存在条目 | 以磁盘实查为准重建或修正索引，修正结果上报 |
| 同主题新增内容与既有条目结论冲突 | 暂停写入，列差异交用户裁决 |
| 浓缩版结论与原文不一致 | 以原文为准修正浓缩版并记录修正 |
| 原文缺失但浓缩版/索引指向存在 | 条目标记异常，暂停依赖该条目的任务并上报 |
| 工单编号缺失 | 向用户申请编号，禁止自行编造 |
| 参考项目拉取失败 | 报原文错误，同目标至多重试 3 次，之后转降级（以本地 docs/ 资料为依据） |

## 7. Obsidian 评估结论（落档）

**结论：弱依赖、维持现状、不撤销、不冗余。**（评估日期 2026-11-06）

1. vault 现状：已由用户手动集成生效（notes/知识库初始化.md 记录）；.obsidian/ 4 个配置文件全为软件出厂默认（app.json/appearance.json 为空对象，core-plugins 全默认无社区插件，workspace.json 仅一次验证性打开记录），用户零定制。
2. 私有功能依赖：零依赖。全部机制基于普通 Markdown + 目录约定 + 相对路径，不使用 wikilink/双链/callout 等私有语法。
3. 撤销影响：仅失去可视化浏览入口，机制不受任何影响。撤销收益趋零（软件可重建的默认配置），保留成本趋零（建议排除出提交）。

备查方案（如用户主动要求撤销）：仅删 .obsidian/ 下 4 个文件，notes/ 逐文件原样保留；恢复方式=用户在 Obsidian 软件中重新指向 vault。任务全程 vault 配置零触碰。
