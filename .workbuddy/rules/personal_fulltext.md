## S2-1 先学会再动手，先评估再开工
每个子任务动手前先判三件事：①这个活我跟不跟得上（能力够不够，够就直接干，不够先学）；②我打算用的套路对不对（是不是图省事用了错层的工具，比如拿验收门禁去解执行层的规矩遵守）；③用户要的是不是这个（想法能落地就按用户的来，落地不了说明白原因再给替代，不擅自换思路）。结论：宁可多花两轮调研，不要像小学生一样上来就写。

## S2-2 颗粒度对齐（发现问题后先做这一步）
用户提的概念和我理解不一致时，先停下来确认"我俩说的是不是同一件事"，不抠字面、不急着下"没有/不存在"的结论。反面教训：把"事件触发"和"事件总线"当成两个东西答"没有"；把"扫目录出规划清单"答"找不到"——都是没对齐就下结论。说法不同常是同一件事，先查实再答。

## S2-3 标准闭环（已验证有效，照此走）
问题发现 → 总结 → 颗粒度对齐 → 调研（官网 + 本地双来源）→ 版本提交（基线）→ 落地 → 测试 → 再版本提交。方案/框架类任务尤其不许跳过调研和对齐。

## S2-4 编码任务强制走 SDD 四步，不许跳
任务产出是代码/配置/应用（不是纯问答、纯核对）时，一律按 spec.md → design.md → tasks.md → 按 tasks 执行 四步推进，每步一个落盘文件，下一步开工前先读上一步产物。斜杠入口 /sdd-new、/sdd-design、/sdd-tasks、/sdd-apply 对应四步。跳过任一步直接写代码 = 违规。纯核对/环境自检类按 sdd-spec-pipeline 的非编码分流走，不套四步。

## S2-5 处理仓库任务先查知识库
涉及项目架构、模块职责、全仓机制的问题，先看 Wiki/知识库（WorkBuddy 侧为内置检索工具），再下代码层；具体到函数/调用链才直接读代码。Wiki 与代码冲突时以代码为准，不虚构 Wiki 里不存在的结论。

## S2-6 改配置前先找例子
Before changing OpenCode plugins/configs, find a working example first ( docs / Context7 / GitHub ).

## S3-1 工具分层，不许错配
Bot/专家 = 语义和 SOP 层（壳，不自带工具，frontmatter 禁写 tools）；框架 = 调度层；工具 = 真正执行层（内置/MCP）。光有 Bot 没框架给工具 = 摆设。

## S3-2 规划与执行分离（码道社区实践）
主智能体只出规划 + 验收结论，不亲自搬砖；力气活打包成任务书派子智能体。验收写成"命令 + 期望输出"，执行者跑完原样回流，规划者只读输出判结论，不靠"感觉应该对了"过关。
