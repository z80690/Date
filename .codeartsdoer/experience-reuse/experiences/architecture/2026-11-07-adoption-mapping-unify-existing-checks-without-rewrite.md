# 统一化需求先盘点存量：收编映射保证判定逻辑零变更，匹配度三档判定防高估

## Scenario

SDD design 阶段，需求要求"统一一个标准/接口：什么叫完、什么叫成"（DoD 统一验收接口），但项目里已分散实存多套检查机制（编码必审四查、门禁自信度阈值、状态迁移三要素、实证等级标注等），且各有原文载体与运行实证。这是权衡决策而非默认选择：统一到新接口存在三条路径——推翻重建、维持分散、收编映射——选错任何一条要么浪费已验证资产，要么不满足统一需求。

## Key Signals

- 需求原文出现"收编/不推翻/统一"字样——用户要的是汇聚既有资产而非发明新机制。
- 既有机制各有文件载体与运行实证——重写定义会丢失溯源链。
- 存量盘点发现大量需求项可直接复用（本例约 40%）——统一化设计的大头是"映射"而非"新建"。

## Essence

统一化设计的核心张力是**接口统一性 vs 既有机制保全**。正确解法是收编而非重写：新接口只做结构容器（公共必查项层 + 分类型专属项层），既有机制逐条映射进清单，判定逻辑零变更，映射表标注原文位置保证可追溯。配套的需求-存量对比用三档匹配度（100% 复用 / 部分扩展 / 全新），判 100% 须双重证据——运行实证与文件实存齐备；仅有文档定义、无运行痕迹的降档处理，防止"文档写了"被当成"已实存"。

## Approach

1. **动笔前先做存量盘点**：逐项列"需求功能 ↔ 存量机制 ↔ 载体位置（文件:行）↔ 匹配度"对比表，先于任何新接口设计。
2. **匹配度三档判定**：100%（复用）/部分（扩展）/全新三档；判 100% 须运行实证或文件实存双重支撑，仅文档声明降为"部分"。
3. **统一接口设计为两层清单**：公共必查项层（所有任务类型都要过）+ 分类型专属项层（每类任务的既有检查项收编于此），接口另配判定流程与三态结果（通过/返工带上限/降级报告）。
4. **收编映射表逐条登记**：既有机制名 → 收编去向 → 判定逻辑是否变更（必须为"零变更"）→ 原文位置；映射表即审阅抓手。
5. **触发复用既有事件检查位**，不新增触发器，保持机制活性口径一致。
6. **被弃方案留痕**：推翻重建（丢运行实证、破坏溯源）、维持分散（不满足统一需求）——写明弃用理由供评审复核。

## Faster Next Time

- "统一/标准化"类需求的第一反应不是设计新机制，而是盘点存量——多数统一需求是映射问题不是新建问题。
- 警惕信号：新接口里出现"重新定义既有检查步骤"的内容——立即改为引用原文位置，做到语义零变更。
- 映射表是说服力证据：评审者逐条核对"判定逻辑零变更"即可放心，无需重读全部存量文档；对比表统计出的复用/扩展/全新占比（如 40/25/35）直接支撑"不推倒重来"的结论。
- ROI：一次存量盘点+映射表，避免重写全部检查机制、避免统一后与存量定义冲突造成的隐性返工。

## Applicability Boundaries

- 适用：面对已有多套并行机制/规范的统一化需求；design 阶段需求-存量对比分析；验收标准整合；能力收编类派工。
- 不适用：存量机制本身被判定有缺陷需重写的场景（先修缺陷再收编）；全新领域无存量可映射（对比表直接判"全新"即可）。
- 重评条件：存量机制发生演进（检查项增删）→ 映射表须同步更新；用户明确要求推翻既有机制 → 本模式不适用。
- 边界：收编只保证语义不变，不保证接口结构本身最优——接口设计仍需独立评审；匹配度判定只回答"有没有对应物"，不评价存量机制好坏。
