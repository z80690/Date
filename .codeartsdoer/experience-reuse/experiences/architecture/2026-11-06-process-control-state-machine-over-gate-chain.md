# 流程管控机构选型：既有事件基础设施在位时优先状态机+迁移守卫而非串行门禁链

## Scenario
为长周期、多阶段、带人类审批的任务设计流程管控机构。项目已有事件驱动基础设施（事件钩子表 + 单一状态事实源），初版设计用串行门禁链（每阶段末设一个审批门）组织流程，被用户质疑"这是什么意思？有没有更优雅的方案？再去调研一下"——这是一个需要权衡的决策，不是默认选择。

## Key Signals
- 门禁链是全项目唯一非事件驱动的流程机构：既有的动态触发全部走事件钩子，唯独流程推进用了串行审批门——机构异构本身就是重复建设的信号。
- 每个门禁产生一个"等待用户确认"的点，阶段多时确认点泛滥，用户成为流水线瓶颈。
- 门禁状态没有唯一存放处，与既有状态事实源形成第二处真相。

## Essence
门禁语义可以拆解为三件事：**当前处于哪个阶段（状态）、怎样算过关（迁移条件）、哪里必须人裁决（确认点）**。串行门禁链把三者绑死在"每阶段一个门"的形态上；当项目已有事件钩子（可作迁移触发载体）和单一事实源（可作状态存放处）时，状态机能以零新增机构承载同一语义——这正是"更优雅"的本质：不是换个词，而是复用既有基础设施消除机构重复。

## Approach
1. 新增流程机构前先盘点既有基础设施：列出已有的事件钩子/状态存放处/通知机制，逐项问"新机构能否以其为载体"。
2. 做机构同构性检查：候选方案与既有事件驱动机制是否同构？异构 = 重复建设信号，优先改造候选使其同构。
3. 三方案对比模板（本次实证）：
   - **串行门禁链**：每阶段末设审批门。强制性强，但确认点=阶段数、状态无唯一存放处、与事件钩子重复。弃。
   - **检查点事件化**：把门禁挂成事件钩子。解决了"非事件驱动"问题，但本质上仍是串行审批链，阶段推进语义弱，且"该到哪个阶段了"无处可查。弃。
   - **状态机+迁移守卫**：枚举全部合法状态（含阻塞态），迁移条件即验收标准，迁移动作复用既有事件钩子触发，状态唯一写事实源，人类确认点收敛为枚举类（只列哪几类决策必须人裁决）。选。
4. 确认点收敛：把散落的"每阶段问一次"收敛为固定几类确认点枚举，其余靠迁移守卫（条件不满足即拒绝迁移）自动拦截。

## Faster Next Time
- 一句话判据：**已有事件基础设施 → 状态机；什么都没有 → 门禁链反而是低成本选择**。先看存量再选机构。
- 看到"流程里唯一一个不走事件的机构"就应停下来重审——异构机构几乎总是可以并入既有机制。
- 门禁链设计可以直接翻译成状态机：每个门 = 一个迁移条件，每次人工审批 = 一个确认点枚举成员。

## Applicability Boundaries
- 适用于：项目已有事件钩子/单一状态事实源，且阶段间有明确先后依赖的场景。
- 不适用于：阶段间无顺序依赖的并行任务（此时依赖图更合适）；基础设施完全空白的新项目（门禁链实现成本更低）。
- 重新评估条件：若事件钩子表后续被裁撤，或阶段数量少到状态机枚举比门禁列表更冗长，应重选。

## Evidence or Examples
- 实证会话：2026-11-06 重新规划 kb_arch_foundation spec。初版 M1–M7 门禁链被用户裁决"规划不合格"，要求调研 2–3 种替代方案。
- 调研后选定"阶段状态机 + 迁移守卫"：7 态（盘点→环境→考核→设计→规则→SDD 实施 + SX 阻塞态），迁移载体复用既有 H1/H3/H6/H7 事件钩子，状态唯一存项目事实表，确认点收敛为 3 类枚举。
- 结论随新版 spec 落盘（同路径覆盖，标注 v2 重构说明），用户审阅中。
