# 治理栈复杂度收敛三态判定：合并/降为惯例/保留硬约束，检查位不减为能力底线

## Scenario

治理机制长期累积（事件钩子 N 个 + 状态机 + 注册表 + 评估表 + 准入流程 + 问答协议 + 门禁清单 + 多通道加载），用户判定"框架比较复杂"，要求给出简化重构建议且明确底线"治理能力不降级"。简化与能力保持存在真实张力，需要结构化判定法而非直觉删减——这是需要权衡的架构决策，不是默认选择。

## Key Signals

- 用户同时锁定简化方向与不降级底线（"更简单但治理能力不降级"）——说明要的是**组织收敛**而非功能裁剪，直觉式的"删掉一些规则"从根上不符。
- 治理栈组件可枚举且各自有实证运行记录——具备逐组件判定的条件。

## Essence

核心张力：机制数量增长与治理能力保持的矛盾；判据锚点：**检查位一个不减**。三态判定法——逐组件判定属于：

- **合并**：多个组件做同一件事（同类检查点、同质登记表），合并后检查位一个不减，只减表数量与心智条目数（如三个动作级纪律钩子合并为单一动作检查点规程；复用评估表并入注册表——同质登记查一处即知全部）。
- **降为惯例**：非红线的协作约定降级为默认习惯，不再占治理编制——但其内含的红线条款逐条迁入保留清单，一条不丢。
- **保留硬约束**：门禁类、状态机、准入流程、授权边界是能力底座，原样保留。

备选方案对比（为何选三态收敛）：
- 备选一：全栈推倒重设计——拒绝：既有机制均有实证运行记录，重设计引入回归风险，且用户要的是"简化"不是"换一套"。
- 备选二：仅删文档不改机制——拒绝：删文档不删检查 = 治理能力实际降级，违背底线。
- 采纳：逐组件三态收敛——保留已验证资产，只重组组织形态，收益可量化。

## Approach

1. **全量盘点**：列出治理栈全部组件（钩子/状态机/表/协议/门禁/通道/加载机制），不漏项。
2. **逐组件三态判定**：每判定附理由（同质性证据或红线属性证据）。
3. **合并自检**：合并前后逐项核对检查位清单，确认一个不减——合并改变的是检查的组织方式，不是检查的存在。
4. **降惯例自检**：把被降组件中的红线条款逐条迁入保留清单。
5. **收益量化**：改前/改后的表数量、心智条目数、通道数对比（如 3 表→1 表、7 钩子心智→3 类通道）。
6. **提案门禁**：全部判定标为提案，用户裁决前治理栈零改动——简化建议本身也要走裁决。

## Faster Next Time

- 判定口诀：**同质则合并、非红线则降惯例、门禁与状态机原样保留**；检查位清单是能力不降级的唯一硬证据。
- 警告信号：简化建议说不出"删的是表还是检查位"时停下——只能删表/合并表，不能删检查位。
- 重新评估触发：治理组件再次累积超过用户容忍度（如新的"太复杂"反馈）、或新增机制导致表数量回升时，重跑三态判定。

## Applicability Boundaries

- 适用：有长期累积治理机制的 Agent 项目/团队流程的收敛重构；任何"机制多但不敢删"的治理栈简化决策。
- 不适用：机制尚未稳定运行的新体系（先跑通再收敛）；红线条款本身（只能精简措辞，不能降级为惯例）。
- 前提：判定对象有实证运行记录可盘点；用户已给出"能力不降级"底线，判定才有稳定锚点。

## Evidence or Examples

- 实录（2026-11-07，ses_e4cdf992cffeY5nxZpoxvM1wZ2）：治理栈 14 组件三态判定落为 spec v3 框架简化章——合并 3（H2/H3/H7 三个动作级钩子→单一动作检查点规程；复用评估表→并入注册表；三问自检→并入六要素）、降惯例 2（三问三答协议、静默清单，红线逐条保留）、保留硬约束 5（状态机/五步准入/四查门禁/双通道/加载上限）、保留原样 4（三类平台原生钩子 + 权威源三副本）。
- 收益量化实例：3 表→1 表、7 钩子心智→3 类通道（平台原生/动作内嵌/内容 diff），检查位声明一个不减。
- 提案门禁实录：全部判定标为提案，裁决前治理栈零改动——与"规矩层冻结"原则一致。
