# 外部依赖敏感的验收断言须按依赖就绪状态分支期望——"未就绪被正确拒绝"与"就绪后成功"都是通过

## Scenario

全流程验收脚本中包含两类断言于同一场景：①外部依赖就绪时业务应成功闭环；②外部依赖未就绪时红线/门禁应拒绝启动。实例：某场景依赖从官方渠道获取的工具（Tor 洋葱浏览器），本机网络对该官方源不可达 → 该场景被系统按红线正确拒绝（如实登记未就绪→拒跑）。初版验收对这两类情况写的是**恒定期望**，导致同一脚本在依赖在场/缺席两种状态下必然有一种状态被误判为失败。

## Key Signals

- 验收汇总 all_pass=false，但逐项细读发现被"拒"的场景记录里 `rejection_valid=true`、拒绝码与拒绝原因完全正确——拒绝本身就是被验收的红线行为，却计入失败。
- 同一脚本换时间/换网络重跑结果翻转——断言期望绑定的是"外部世界的实时状态"，不是"被测系统的行为"。
- 验收场景同时存在"依赖可达→成功"与"依赖不可达→拒绝"两个合法出口，而断言只认其中一个。

## Essence

对外部依赖（外部渠道可达性、外部资源部署状态、第三方服务）敏感的断言，其期望值是**前置状态的函数**，不是常量：依赖就绪 → 期望成功闭环（终态字段齐）；依赖未就绪 → 期望"REJECTED + 拒绝要素可核对"（拒绝码正确、拒绝原因引用正确条款、拒绝留痕）。"系统在依赖缺失时正确拒绝"与"系统在依赖在场时正确成功"是两个并列的被验收行为，验收脚本必须两个都认，否则必然产生时绿时红的假红/假绿。

## Approach

1. **盘点**：逐条检查验收断言，标记每一项的期望是否依赖外部实时状态（判别问句：这一项在任何网络/时间下被测系统的正确行为都相同吗？不同 → 敏感项）。
2. **取状态口径**：敏感项的前置状态从**系统自身的就绪自检结果**读取（如准备项就绪登记），不要在验收脚本里重新探测外部源——两套探测口径不一致会让分支判据本身抖动。
3. **双分支断言**：
   ```python
   if dep_ready:                       # 状态口径来自系统就绪自检
       assert status == SUCCESS and result.completed
   else:
       assert status == "REJECTED" and rejection_valid   # 拒绝码+原因可核对
   ```
4. **汇总合并**：分支判定结果按"任一分支通过即该项通过"合并进总判定；分支路径与依据写进验收明细，供人复核。
5. **补路机制**：依赖恢复后（渠道可达/资源部署完成）重跑同一脚本即自动走成功分支补齐闭环证据，无需改代码——把"重跑补路"写进交付说明而非遗留缺陷。

## Faster Next Time

- 设计验收时先问"这项断言依赖外部网络/资源吗"→ 是则直接写成双分支，不要等第一次翻车再改。
- 看到 all_pass=false 先读分支明细：`REJECTED + 拒绝要素正确` 与 `验收失败` 是两类结论，前者可能恰是红线正确行为的证据。
- 警示信号：验收脚本里出现对外部 URL 的直接探测（检查官方渠道是否可达）作为期望判据 → 违反第 2 步口径纪律，改为读系统就绪登记。
- 回归成本锚点：本改造为零成本重构（只动断言表达式），且附带获得"依赖恢复后重跑即补成功路径"的免费回归能力。

## Applicability Boundaries

- 适用：含红线/门禁/降级路径的系统验收（依赖未就绪应拒跑）、外部资源获取类流程的端到端验证、任何"合法出口有两个（成功/正确拒绝）"的场景验收。
- 不适用：纯内部逻辑的单元测试（无外部依赖时用恒定期望即可，双分支是画蛇添足）；被测行为本身是"无论依赖状态都必须成功"的场景（此时拒绝恒为失败，不适用分支）。
- 边界：分支判据必须单调可信（系统就绪自检的结果本身要已被验证过），否则分支会在错误的前提下双假；"正确拒绝"的核对要素（拒绝码、原因条款、留痕）要在验收设计期就定义好，不能事后解释。

- 来源会话：ses_e39c0284affeQIVsP1a0NNgpgC（2026-11-10 组 7 全链路验收）。
- 实测：Tor 官方渠道（dist.torproject.org）本机不可达 → 准备项登记未就绪 → 通讯隐匿/Tor 两场景 `REJECTED + PREPARE_NOT_READY + rejection_valid=true`（拒绝原因正确引用红线条款"5.2.1 规则 10"）；初版恒定期望误判为失败，改双分支后该项通过；同脚本中依赖本机的资金安全场景走成功分支闭环。
