# 治理机制必须事件驱动才有活性：绑定触发时点 + 自动加载通道 + 单一事实源

## Scenario

多阶段协作任务中产出了一批治理类机制（冲突检测、优先级仲裁、记忆清理、状态同步），最初按常规做法落为 design 章节与机制文档。用户验收时发出关键质询："这些机制现在是什么触发时机？是否依赖定时或死脚本？"并裁决：所有规矩与机制必须是"事件驱动、自动加载"，严禁死脚本、严禁定时任务硬跑；随后补充放宽——非定时的其他实现（如后台任务）也可接受。工作流规模：单人 + Agent 长期协作工作区，机制需跨会话存活。

## Key Signals

- 机制文档只写"应该做什么"而没有"何时做"——没有触发时点的机制就是死文档。
- 用户质疑触发时机、点名"死脚本/死规矩/定时任务硬跑"——说明机制设计缺少活性论证环节。
- 同一状态事实（环境状态、基线状态、决策结论）在规则、记忆、知识库多处出现且版本不一。

## Essence

**文档存在 ≠ 机制存活。** 治理机制要有活性，三件必须齐备：①绑定真实执行时点（事件钩子：任务启动、文件写入前、引用记忆前、规则变更后、门禁执行时），不依赖定时器与人工提醒；②有自动进入上下文的加载通道（规则强加载声明、hook 注入、检索上下文注入等），不靠"下次会话记得去看"；③状态收敛到单一事实源，其他文档活引用而非复制值，改事实只改一处。三缺一，机制必然退化为"写过就死"的文字。

## Approach

1. 为每条机制定义三元组：**触发事件**（绑到流程中必然发生的时点）→ **执行条件** → **回退策略**（检测失败时不卡死主流程，降级记录待办）。
2. 建立"事件 → 检测 → 仲裁 → 修正"闭环，并用**模拟事件触发**自检每条钩子可达（而非定时跑通）。
3. 单一事实源：建一张事实表只存核心状态；其他文档引用表而非抄值；状态变更只改事实表一处。
4. 新机制落盘前跑"活性三问"自检：何时触发？怎么自动加载？状态存哪、谁引用它？任一答不上来就先补齐再落盘。
5. 与用户对齐"禁令的可接受集合"："禁定时任务"通常指禁无人值守周期硬跑；事件触发、任务内联检查、后台随附任务等非定时方式应先列出来供确认，不要把禁令自行扩大化导致机制无处安放。

## Faster Next Time

- 设计治理机制的固定第一问不是"怎么做"而是"**什么时候做**"——没有触发时点的设计直接打回重做。
- 警告信号：机制描述里出现"定期""记得""下次会话应注意"而无绑定事件 → 立即补事件钩子，或降级为人工可选步骤并明示。
- 收敛信号：同一事实在 ≥2 处以"值"的形式存在 → 立即建/引事实表，改为活引用。
- ROI：本例若按最初静态章节交付，机制上线即失效，需后续会话反复人工补救；返工为"钩子总表 + 事实表 + 自动加载"后一次通过用户验收，并在同会话内完成模拟事件自检与版本提交，避免了跨会话的隐性返工。

## Applicability Boundaries

- 适用：Agent 长期协作工作区中需要跨会话存活的治理机制（规则执行、仲裁、清理、状态同步）；交付物是"机制"而非一次性产物的任务。
- 不适用：一次性任务内的临时步骤（此类项目通常明示"临时步骤只活在当前派工单，干完即弃"，静态记录即可）；确需周期执行且找不到可绑定事件的场景（如纯定时备份）——此时应如实说明必须定时并请用户豁免，而不是硬凑事件伪装成事件驱动。
- 证据等级：机制设计已落盘、模拟事件自检通过、随版本提交验证，用户确认方向正确；**长期运行有效性尚未经多会话验证**，后续实施偏差应回写本条。
