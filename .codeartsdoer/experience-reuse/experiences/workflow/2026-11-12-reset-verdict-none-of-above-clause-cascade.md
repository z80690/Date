# 多选一裁决单的"全不选/重置"分支：用户否定选项集所基于的演化前提时，按被否决前提反查连带废弃条款

## Scenario

多阶段流程中出现基线级分歧（如同名框架身份混淆、spec 条款与本地资产不符），执行者按惯例呈报 A/B/C 多选一裁决单（各选项附推荐项与理由）。用户回复不在选项集内：给出"方案 D（重置，不接 A/B/C）"，要求回归初始需求最简落地，并点名废弃上游 spec 中的某条款（如"黑板机制"）、明确"不补学、不额外调度、勿再拟多选一"。

## Key Signals

- 用户裁决文本以"不接/全不选/重置"开头——这不是对某选项的追问，而是对**选项集所基于的演化前提**的整体否定。
- 伴随表述"回归初始需求/最简落地/勿再拟多选一"——表达了对"选项框定本身"的不信任：上游多轮演化加出来的复杂度（并行方案、双框架并用、补学材料）被整体否定。
- 裁决附带了明确的执行边界（"仅本地版/MCP 接入/127.0.0.1 不越界"），说明重置不是放弃而是收敛到初始需求。

## Essence

多选一裁决单的选项集天然不封闭：用户保留"none of the above"权利。重置裁决的语义 = 否定演化前提 + 回归初始需求。此时处置分三层：①承接（裁决落盘用全局注记，不逐处改写）；②**连带废弃识别**——反查哪些上游条款建立在被否决前提上（如"黑板机制"条款基于 oritera/Cairn 身份，前提被否则条款直接废弃而非修订），并识别连带的学习材料范围、部署落点、接入方式；③执行纪律（按初始需求最简落地，不再拟多选一）。呈报侧的教训：裁决单应预置"以上皆非/重置"出口。

## Approach

1. 判定重置语义：用户给出选项集外答案且表述"重置/不接"时，显式声明"本次裁决 = 全不选 + 回归初始需求"，不做选项内猜测。
2. 落盘承接（减法）：三份基线文档（spec/design/tasks）加全局注记行登记裁决原文与生效口径，既有条款值不改写（沿用全局注记代逐处改写的既有模式）。
3. 连带废弃反查：以"该条款的存在前提"为索引 grep 上游文档——凡前提是"oritera/黑板机制/补学"类被否决前提的条款（部署落点、学习材料清单、考核范围），登记为"直接废弃"而非修订，废弃清单随注记落盘。
4. 执行指令承接：用户"勿再拟多选一"= 后续同类分歧按初始需求红线直接判定，分歧仅在实际矛盾时以事实证据呈报（不回归选项化）。
5. 收口：各文档注记 + gates/ 留痕同步后即推进，不再就已裁决事项二次呈报。

## Faster Next Time

- 呈报多选一裁决单时**预置"以上皆非（重置）"出口**并说明其含义（回归初始需求/维持现状），给用户表达重置意图的合法通道，避免被三个选项框死。
- 收到重置裁决后第一动作是**前提反查**：列出被否决前提 → grep 其在 spec/design/tasks 的派生条款 → 生成废弃清单，防"只改被点名条目"造成新旧口径并存。
- 重置 ≠ 推翻全部历史：既成事实的留痕不回溯（历史登记不回改），只对活口径做废弃/收敛——与"推翻后留痕处理"的既有经验互补使用。
- ROI 实测：本会话重置裁决后连带废弃识别覆盖 3 类条款（spec 机制条款/学习材料/G2 部署落点），避免了执行阶段按废弃条款部署错框架的返工。

## Applicability Boundaries

- 适用：多阶段门禁流程中的裁决呈报场景；用户有"初始需求优先于演化方案"倾向；选项集基于某个已被质疑的身份/机制前提。
- 不适用：用户在选项集内正常选择（此时按选项执行即可）；选项间是纯技术等价方案（无前提依赖，重置无意义）；用户仅表达倾向而非裁决（应走倾向委托裁决模式而非重置）。

## Evidence or Examples

- 实测事件序列（2026-11-12 本会话）：AI 呈报 Cairn 身份三选一（换 oritera/维持 xcosmosbox/两者并用）→ 用户回"选方案 D（重置，不接 A/B/C），回归初始需求最简落地，Cairn 仅用本地 xcosmosbox 版（MCP 天然吻合），原 spec '黑板'条款直接废弃，不补学 oritera，勿再拟多选一"→ 执行：spec v1.3 全局注记 + design/tasks 注记 + 废弃条款识别（"黑板机制"条款直接废弃、oritera 相关学习材料不补学、G2 部署落点锁本地 xcosmosbox 版）→ 考核出题范围同步收窄（方案 D 红线：无 oritera/黑板机制题）。
