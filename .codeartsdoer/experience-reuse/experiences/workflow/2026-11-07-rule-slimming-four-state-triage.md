# 规则堆积的批量精简判定：红线留规矩、操作分装技能，逐条四态裁决

## Scenario

项目级规则经多轮派工追加后膨胀（本会话实证 10 条），规则按轮全量常驻注入上下文；用户判定"规矩太多了、越简单越好"，要求评估合理性、产出精简方案并保留最终批准权。此场景在规则条数增长、用户出现"显示字数太多就不能用"类感知成本信号时触发。

## Key Signals

- 用户感知成本信号：抱怨规矩数量、关注常驻上下文字数、要求"越简单越好"。
- 条款类型混杂信号：红线/原则类条款（禁定时、单一事实源、仲裁顺序）与操作型流程条款（考核流程、准入步骤、必审动作）混编在同一规则文件中。

## Essence

1. **归属判据（批量版）**：红线与原则 → 规矩（每轮常驻，保证强制力）；流程与操作 → 技能（按需加载，零常驻成本）。判断依据不是"内容重要程度"，而是"是否需要每轮强制在场"。
2. **逐条四态判定**：保留为规矩 / 分装为技能 / 合并精简 / 删除候选。禁止整包重写，逐条留判定理由。
3. **验收锚**：精简生效的判定标准 = 新会话注入的规则内容与批准草稿**逐字一致**（经 session-rules diff 感知），加上分装技能的注册状态实证。
4. 权力边界：Agent 只产草稿与技能，规则文件的替换粘贴由用户在界面完成——零手改规则文件是前置硬约束。

## Approach

1. 全量逐条标注类型：红线/原则 vs 操作/流程，一条一行给出四态判定与理由。
2. 操作型条款映射到技能：已有技能直接引用；缺载体的新建技能并走五步准入（登记、注册验证）。
3. 产出两件套一并呈批：精简草稿（每条一行、总量压缩）+ 技能封装清单（含注册证据）。
4. 用户界面粘贴替换后做生效验证：比对注入内容与草稿逐字一致 + 技能注册状态核对（状态文件/运行时清单双源）。
5. 能力不丢失证明：每条被分装/删除的条款，指出其能力现在的承载位置（技能名或"确无必要"理由），缺证明的条目退回保留。

## Faster Next Time

- 新增规则前先问"这是红线还是操作流程"：操作流程直接写成技能，避免日后返工精简。
- 精简方案必须携带"能力不丢失"证据链（技能注册实证），否则用户无法放心批准。
- 生效验证用逐字比对而非条数比对，防粘贴时丢条或改字。

## Applicability Boundaries

- 适用于规则按轮常驻注入上下文的平台；一次性任务指令既不该入规矩也不必成技能。
- 判定对象分层：治理组件（钩子/登记表/协议/门禁）的简化判定用治理栈三态判定法（见 governance-stack-three-state-simplification：合并/降惯例/保留硬约束），规则文件条目的去留用本条四态判定——两层方法论同构但对象不同，不可混用。
- 用户未批准前禁执行任何规则文件改动；草稿呈批是必经门禁。
- 若平台规则不常驻注入（仅显式引用），"上下文预算"论据弱化，归属判据退化为纯组织管理问题。

## Evidence or Examples

- 本会话实证 10→6：4 条被分装——学习考核两条由 learn-gate 承接、五步准入由 register-feature 承接、编码必审已由 review-code 承接（规矩仅留半句引用）；红线类（禁定时、单一事实源、仲裁顺序、规矩层冻结、隔离防护、SDD）全部保留。
- 生效验证：批准草稿与新会话注入内容逐字一致；`ProjectSkillStatus.txt` 实证 learn-gate=true、register-feature=true，注册表与索引同步登记。
