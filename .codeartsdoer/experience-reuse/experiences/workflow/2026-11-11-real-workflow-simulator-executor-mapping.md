# 真实硬件工作流移植为仿真环境：保结构换执行器 + 外部交互回环化 + 就绪自检逐项映射

## Scenario

用户派工：把某真实从业者的标准工作流（实例：嵌入式 UP 主七环节流程——资料准备→硬件接口→功能说明→代码开发→编译下载→测试验证→交付）配成"主力干活"的工作流，但明确约束：**无硬件，只能本机仿真**（Windows 直跑、禁真实外连、环境简化重装自负）。参考流程里每个环节都挂着真实物理执行器（真实开发板、万用表/示波器、烧录器、协议对端设备），直接照搬无法执行，全部重写又破坏参考价值。

## Key Signals

- 参考流程中含"实物操作"环节（接板子、烧录、连设备联调）——这是需要改造映射的执行器，不是流程本身的缺陷。
- 项目约束出现"禁真实外连/仅本机/仿真"字样——执行器选型被硬过滤：任何需要联网对端或云服务的方案直接出局。
- 用户强调"按参考流程的层级配目录、不许乱放"——流程骨架（环节顺序、目录规范、验收点）是冻结项，改动自由度只在执行层。

## Essence

仿真改造的正确切面是**一个二维分离**：流程骨架（环节、SOP、目录规范、验收纪律）原样冻结不动；真实执行器逐个替换为"开源 + 本机可跑 + 离线可用"的仿真等价物。所有跨进程/跨机器的外部交互一律收紧到本机回环（127.0.0.1）。就绪自检不是另起炉灶，而是把原流程的"前置三件事"逐项翻译成仿真等价检查——这样仿真版天然继承原流程的质量门禁，而不是一套没有约束依据的新流程。

## Approach

1. **先还原后改造**：把真实流程骨架（环节序列、每环节输入/动作/产出、验收点）先冻结成文，作为不可变更的改造基线。
2. **逐环节列执行器清单并映射**：对每个真实执行器找仿真等价物。实测映射表（可直接复用）：

| 真实执行器 | 仿真等价物 | 映射要点 |
|-----------|-----------|---------|
| 真实开发板/MCU | 开源 MCU 仿真器（实例：Renode，Windows 本机直跑，支持 STM32/ESP32） | 选型资格线=离线本机可跑+目标芯片覆盖 |
| 串口调试工具/日志 | 仿真器日志落盘 + 虚拟串口 | 观测点不减少，只换载体 |
| 烧录器 | 固件文件加载 | 验收从"烧录成功日志"变为"加载成功回执" |
| 协议对端设备 | 本机回环 Socket 模拟进程 | 协议行为仿真，禁外连公网 |

3. **回环化收口**：全部网络交互绑定 127.0.0.1，作为硬过滤条件写进执行器选型判据（不是事后补救）。
4. **就绪自检逐项映射**：原流程每个"开始前确认"翻译成仿真等价检查（实例：真实"工具装好/板子接好/联调环境通"三件事 → 仿真三自检"工具链可编译/仿真器可加载/日志可落盘"）。
5. **回执语义对齐**：仿真宿主的可观测输出（日志/回执/状态事件）对应原流程的实物反馈，保证"执行只认回执、成功失败由回执拉动"等底层纪律在仿真版中原样成立。

## Faster Next Time

- 一句话路线：骨架冻结 → 执行器清单逐项映射 → 回环收口 → 自检翻译 → 回执对齐。
- 映射表先查本条 Evidence；执行器选型第一过滤条件永远是"离线 + 本机 + 开源"，再比覆盖度与成熟度。
- 警示信号：改造中想"顺便优化原流程环节" → 停，那是需求变更不是仿真改造；找不到仿真等价物的环节 → 如实登记"本环节不可仿真"，禁用虚构模拟充数。
- ROI：改造与还原共用同一份骨架文档，还原越扎实改造越快（实例：七环节骨架还原后，映射表+自检翻译一小时内闭环）。

## Applicability Boundaries

- 适用：参考流程基于真实硬件/真实环境、但项目约束为纯本机仿真的移植任务；同类"真实 X → 仿真 X"映射（测试靶场、协议对端、生产部署流程）可迁移。
- 不适用：有真实硬件可用的场景（直接用真机，过度仿真化反而引入失真）；参考流程本身含联网云服务的核心环节（若不可回环化则该流程整体不适配纯仿真约束，需向用户呈报）。
- 边界：仿真等价物与真实执行器永远存在行为差异（时序、外设精度），验收口径要写明"仿真通过 ≠ 真机通过"；映射表随候选工具演进需定期复核。
