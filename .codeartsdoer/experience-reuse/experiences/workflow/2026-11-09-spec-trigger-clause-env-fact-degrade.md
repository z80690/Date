# 需求触发时机条款的环境事实降级：缺失事件锚点时改写为语义等价真实事件

## Scenario

SDD spec 阶段承接工具链/门禁类需求（换 linter、换审查引擎、加检查点），用户写的触发时机是 IDE 语境措辞（如"保存时审查"），而执行环境是 CLI/headless 会话——无 IDE、无编辑器回调、无文件保存事件。照抄字面写条款，实施阶段无法实现"保存时"事件；自作主张砍掉该触发点，需求覆盖出现缺口且用户不知情。单人协作、规格先行，触发时机的条款措辞必须在 spec 阶段一次定准，否则事故延后到实施与验收才爆。

## Key Signals

- 需求原文触发时机含"保存时/实时/编辑器内/监听"等 IDE 语境措辞，而执行环境是 CLI 会话、headless 或纯文件系统操作环境。
- 环境事件通道盘点显示不存在与该措辞对应的事件钩子（无保存事件、无编辑器回调）。
- 需求中的其他触发时机在环境中均有真实对应物（如"提交前"对应 git 提交动作、"执行步门禁"对应流程节点）——只有个别措辞悬空。

## Essence

触发时机条款的有效性锚定在**环境真实存在的事件**上，而非需求原文措辞。需求措辞中的事件在环境中不存在时，既不硬造（虚构钩子 = 实施期卡死），也不静默砍除（需求覆盖缺口），而是定位**语义等价的最近真实事件**降级改写：先还原该措辞想捕获的动作意图（"保存时审查"真实意图是"内容变更后尽快审查"），再在环境中找最近的因果等价锚点（文件落盘完成 → "落盘即审"）。降级必须三要素齐备随条款落盘：**原措辞 + 降级措辞 + 降级依据（环境事实）**——三要素防两类下游事故：实施者拿字面"保存时"无法落地；验收者拿字面措辞判伪验收或指责偷换需求。

## Approach

1. **枚举触发措辞**：通读需求原文，列出全部触发时机字样，逐条编号。
2. **核对环境承载**：逐一核对当前环境是否有真实事件承载（IDE 钩子/文件系统事件/git 动作/流程节点），输出"有承载/无承载"二值结论，禁止凭印象断定。
3. **定位语义等价锚点**：无承载项先还原动作意图，再找环境中最近的因果等价事件（保存 → 落盘；实时 → 每次操作后；编辑器内校验 → 内容层比对）；确实无等价物则标记为"环境不可实现"项，不得硬造。
4. **降级条款三要素落盘**：原措辞 → 降级措辞 + 降级依据（环境事实原文，如"本环境为 CLI 会话，无 IDE 保存钩子"），并在呈报摘要中显式告知用户，保留回改入口。
5. **验收条款同步降级**：验收判定按降级后措辞写可判定标准，禁止验收项仍按原措辞出题。

## Faster Next Time

- 一句自查："需求里的每个触发时机，环境里都有真实事件吗？"——没有 → 降级改写，不硬造、不砍除、不沉默。
- 警告信号：spec 中出现"保存时""实时监听""编辑器回调"字样而执行环境是 CLI/headless，逐处核对承载。
- 反模式：虚构不存在的事件钩子（实施期卡死）；静默删除该触发点（需求缺口且用户不知情）；降级不写依据（下游疑偷换需求）；验收仍按原措辞出验收项（伪验收）。
- ROI：一次措辞-承载核对（分钟级）避免实施阶段返工与验收争议；比"写到一半发现事件不存在"再回改 spec 便宜一个量级。

## Applicability Boundaries

- 适用：CLI/headless/无 GUI 会话中规格化含 IDE 语境措辞的需求；环境事件通道有限（如禁轮询、仅事件驱动）的项目；spec 先行、条款一次定准的流程。
- 不适用：环境真实具备 IDE/编辑器钩子的场景（原措辞可直接落条款）；需求方明确坚持字面语义且拒绝降级的场景——此时如实呈报"环境不可实现"作为事实性阻塞，而非擅自降级。
- 证据强度边界：本条为 spec 设计层规则，降级条款尚未经实施/验收实测，执行层证据待后续阶段补充。
