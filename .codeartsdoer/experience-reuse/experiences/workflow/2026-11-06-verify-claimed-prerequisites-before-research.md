# 派工单声称"已核实"的结构性前提，动手前仍用特征检索秒级复核

## Scenario
任务书/派工单以"借鉴某外部仓库的 XX 组织方式"为设计依据，且声称该调研前提"已核实"（如"仓库含 skill 组织方式与知识库分级方式"）。任务链的多个后续阶段（提炼、沉淀、复用）都建立在该结构性前提上。实际调研时才发现目标结构根本不存在——前期阶段全部建立在错误前提上。

## Key Signals
- 前提表述为"参考/借鉴某仓库的 XX 结构/方式/机制"，属于结构性存在性断言。
- 声称"已核实"但未附文件级证据（无具体文件路径、无检索记录）。
- 对目标仓库的接触仅限 README、宣传页或二手描述——这些材料不构成结构存在性证据。

## Essence
"已核实"标签不等于可验证证据。结构性前提（某文件/目录/机制存在）可以用一次特征检索在秒级证伪或证实：glob 特征文件名（如 `SKILL.md`、`AGENTS.md`、`.cursorrules`）或 ls 关键目录。该成本远低于按错误前提推进多个阶段后的返工成本。前提提供者的"已核实"可能只是"听说过"，与"检索过文件系统"是两回事。

## Approach
1. 启动任务前，提取任务链依赖的每个结构性前提，写成清单（"仓库 X 存在 Y 结构""机制 Z 可用"）。
2. 对每个前提执行一次特征检索：glob 特征文件名、或列目录关键路径；能命中即证实；空结果不可单独定论——先 read 目标目录复核，确认无才判证伪（可靠性边界见关联经验 2026-11-06-glob-empty-result-read-verify）。
3. 结果回填：全部证实 → 按原计划推进；任一证伪 → 立即上报并暂停依赖该前提的任务链，等待裁决，不擅自找替代方案推进。
4. 复核结果记录进交付说明（"前提 X 已于 <date> 经 glob 复核证实/证伪"），供后续会话免重复核实。

## Faster Next Time
- 把"前提特征复核"固定为调研类任务的第 0 步，成本秒级，排在克隆/读 README 之前。
- 前提来源越间接（用户转述、第三方文章、AI 生成的任务书），复核优先级越高。
- 特征文件名选目标结构的最小判别特征（如验证"skill 组织方式"直接搜 `**/SKILL.md`），一次检索即可定性。

## Applicability Boundaries
- 适用于"结构/文件/机制存在性"类前提；不适用于业务逻辑正确性类前提（需深入调研或运行验证）。
- 前提无法低成本复核时（需运行环境、需权限），标注风险等级并告知依赖方，而非阻塞任务。
- 复核仅针对存在性；命中后是否值得借鉴仍需正常调研判断，两者不互相替代。
- 与《知识库生成规范文档先核实仓库实际状态再动笔（零编造法）》的分工：本条管调研/借鉴类任务链第 0 步的前提证伪与暂停上报；知识文档生成过程中的现状核实与行号溯源见该条。

## Evidence or Examples
- 实测：会话派工单声称"调研前提（已核实）：它是 AI for Science 科研框架……借鉴其 skill 组织方式与经验沉淀结构"。
- 实测：执行中对 hyra-results 全仓 glob 检索 `SKILL.md`/`AGENTS.md`/`AGENTS*` 特征文件均无命中；README 证实其为科研成果集（AI4Science 20 项、AI4AI 3 项、AI4Fun 4 项，共 27 个成果目录），"经验分级+沉淀成 skill"结构不存在——依赖该前提的提炼与沉淀任务设计失效。
- 后果对照：若第 0 步做一次 glob（秒级），可在克隆前即证伪，省去后续多阶段的错误前提推进。
