# SDD 规格阶段实查期的规则冲突显式化：编号裁决项+预设方案随规格呈报

## Scenario

SDD 流水线 spec-requirement-agent 角色承接改造类派工单（含剥离既有机制、改智能体职责、考核门禁等要求），前置核实三件套照做后仍有一个盲区：派工单要求与项目规则层（公约、注册表、机制文档）之间的**意图冲突**，以及派工单使用口头惯例值/模糊指称留下的规格模糊。这些若在实查期不识别，规格定稿甚至 design/tasks 展开后才暴露，返工成本最高。

## Key Signals

- 派工单含"剥离/去掉 X"类指令，而规则层有"新流程一律走 X 登记/准入"类条款——剥离对象正是承载合规机制的载体；
- 派工单使用"老规矩""合格线"等口头惯例指称，但规则层与知识库均无成文数值；
- 派工单指称某实体（如"图框架"）但项目中无精确对应物，实体边界不明；
- 数值要求（题量、合格线、测试范围）只有叙述无结构定义。

## Essence

前置核实的对象分两层：**支持性事实**（落点、现状、环境——三件套已覆盖）与**约束性规则层**（公约、注册表、机制文档——易漏）。规格阶段的职责不是替冲突任一方拍板，而是把冲突与模糊显式化为**编号裁决项**（冲突双方出处 + 为什么冲突 + 预设方案），随规格一并呈报交用户裁决。它与三层仲裁顺序（规则>知识库>记忆>推断）的分工：仲裁解决事实/状态冲突，裁决项上呈需求意图与规则约束的意图层冲突——后者本质是需求方决策，代理无权代行。

## Approach

1. 实查期同步扫规则层：读公约/注册表/机制文档，不只读"支持派工单的事实"，重点找"约束派工单的条款"；
2. 交叉比对：派工单逐条要求 × 规则层条款，产出冲突清单与模糊清单，零遗漏；
3. 裁决项四栏化：每项编号（B1…Bn）+ 冲突双方出处 + 冲突原因 + 预设方案（默认推荐，可被覆盖）；
4. 随规格呈报：裁决项入规格附录，呈报中醒目独立标注"需您裁决的 N 项"，不藏在正文；
5. 并行输入设计：明确"若能一并给出裁决倾向，下一阶段（design）即可直接承接"——裁决项不阻塞规格定稿，只影响下阶段启动，与门禁停驻呈报兼容。

## Faster Next Time

- 实查清单固定为四件：落点 + 单一事实源 + 知识库索引 + **规则层**（前三件是三件套，第四件为本经验新增）；
- 警告信号：发现自己在想"按派工单办"或"按规则办"任一句，立即停——转裁决项，两个都不选；
- ROI 实测：一次实查识别 5 项裁决项（注册表剥离范围/实体指认/合格线数值/题量结构/对比范围），全部随规格一次呈报，零事后返工；
- 反模式：把裁决项写成开放式提问（无预设方案）——用户裁决成本翻倍；把冲突私下"调和"成折中方案——违反仲裁顺序且不可审计。

## Applicability Boundaries

- 适用：改造类/强约束派工单 + 项目存在成文规则层（公约/注册表/机制文档）+ SDD 规格阶段；
- 不适用：无规则层的一次性小任务（无冲突可识别）；派工单已逐字裁决过全部冲突；用户已全权授权且冲突有既定仲裁顺序可自行裁决的场景（按仲裁顺序裁并报告即可）；
- 与《派工单协作中的冲突裁决单与人工门禁前置模式》分工：那条管**执行前**新派工单 vs 已确认规格的冲突（独立裁决单 + 门禁前置 + 无冲突部分并行先行），本条管**规格撰写实查期**派工单 vs 规则层的意图冲突（裁决项嵌入规格附录随规格呈报）；两者可能先后发生在同一任务的不同阶段。

## Evidence or Examples

- 本 session 实测（派工单"规范驱动接入与两智能体改造"）：识别 5 项裁决项——B1 注册表剥离 vs 公约第 4 条（注册表承载五步准入登记，剥离范围需裁决）；B2 "图框架"实体指认；B3 合格线数值（惯例 80% 来自事实表但未成文为规则）；B4 50 题结构；B5 对比测试范围——全部附预设方案随规格附录 B 呈报；
- 实证出处：notes/项目事实表.md（门禁惯例值 80%）、notes/知识库索引.md（注册表承载五步准入）、.codeartsdoer/rule/项目协作公约.mdc（6 条现行）。
