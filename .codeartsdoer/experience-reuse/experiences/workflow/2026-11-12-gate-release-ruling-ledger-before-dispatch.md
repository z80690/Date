# 门禁放行型口头裁决的留痕先于派发——核验报告作为跨上下文裁决传递的单一事实源

## Scenario

带门禁链的多阶段流程（如 SDD：spec→design→tasks→执行，叠加前置门禁 G-PC1~G-PC3 与核验报告文档）推进到"核验报告待用户审阅"的停驻位。用户在一条消息里同时给出多项裁决与推进指令（如"选 A""模型解耦走方案 a""两项一并确认，放行 G-PC3，进入 design 阶段"）。此时核验报告文档中的门禁状态表仍写着"实测完成待审阅/未放行"，审阅记录写着"待定"——文档实态与口头裁决不一致，而下一阶段子代理即将被派发。

## Key Signals

- 用户裁决语句与阶段推进指令合并在同一条消息（"XX 一并确认，放行 G-PC3，进入 design 阶段"）——裁决与放行互为前提，放行是裁决生效的标志；
- 核验报告中存在结构化门禁状态表（门禁/状态/说明三列）与审阅记录节（用户审阅结论字段）——存在现成留痕点但当前值与裁决不符；
- 下一阶段子代理上下文隔离，看不到主会话对话历史——裁决若只存在于对话中，下游只能靠主代理 prompt 转述获得。

## Essence

口头裁决只存在于主会话对话历史中，而 Task 型子代理持有隔离上下文——**直接派发会把裁决传递退化为 prompt 转述**，既有转述失真风险，又留下"文档说未放行、实际已放行"的基线脱节（后续任何只读文档的代理或用户抽查都会误判状态）。留痕先于派发的本质是：把裁决写进核验报告的既有结构化字段（门禁状态表行 + 审阅记录行），使文档成为裁决的单一事实源；派发 prompt 只需"先完整读取留痕文档"，裁决传递零失真，且放行动作本身留下可审计证据链（谁裁决、何时、裁决原文）。

## Approach

1. **判定推进指令类型**：沿用阶段推进指令时序消歧的三分判定（回溯对齐/终判授权/常规进入）；本模式适用于"常规进入下一阶段"分支——基线未变，仅门禁放行。
2. **提取裁决清单并映射留痕点**：把一条消息中的多项裁决逐项列出（选项裁决、方案裁决、放行裁决），逐项映射到留痕字段——选项/方案裁决写入审阅记录（含裁决原文摘要与日期），放行裁决写入门禁状态表对应行。
3. **定位后落盘**：grep 定位门禁状态行与审阅记录行号 → **先 read 再 edit**（grep 结果不构成 read 前置，直接 edit 会报错）；每次 edit 保持既有表格结构不动、只改状态值与说明列。
4. **留痕后才派发**：确认留痕落盘（门禁三行状态齐变）后，才调用下一阶段子代理；prompt 中要求"先完整读取 spec 与核验报告"，裁决依据从文档取，不靠转述复述。

## Faster Next Time

- 口诀：**裁决先落盘，派发后于留痕；门禁状态表是放行的唯一权威字段**——收到"放行 + 进入下一阶段"类消息，第一动作是定位留痕点，不是调子代理。
- 多项裁决逐项映射、逐项落盘，防"放行写了、选项裁决漏写"的不完整留痕。
- 反模式：直接派发下一阶段子代理并在 prompt 里口头转述"用户已选 A 和方案 a"——下游文档没有任何放行痕迹，审计链断裂；核验报告状态表与实态脱节。
- ROI：本模式两次 edit 一次落盘（约 1 分钟），换来 design 阶段子代理一次成功零澄清往返；不留痕的潜在代价是下游按"未放行"拒绝执行或越权按转述执行。

## Applicability Boundaries

- 适用：任何"文档承载门禁/审批状态"的多阶段流程（SDD 门禁链、发布审批链、变更单流程），用户以对话消息放行门禁的场景；多项裁决与推进指令合并下达的场景尤甚。
- 不适用：裁决本身需要新增/修订文档条款的场景（走补充裁决增量修订路径，留痕量远超状态表更新）；纯对话型流程无文档载体；用户裁决表述含糊需先澄清再落盘（不可替用户裁决）。
- 局限：依赖文档中已有结构化门禁状态表/审阅记录节；无此结构时须先补建结构再留痕，成本略增；裁决原文较长时审阅记录只登记摘要，全文靠对话历史追溯。
