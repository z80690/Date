# 章节编号顺延修订：从后往前替换保 oldString 唯一 + 残留 grep 双向核验

## Scenario

对数百行结构化 markdown 文档做版本修订，且需要在中间插入新章节，导致其后所有章节编号整体位移（如 5.4–5.9 顺延为 5.5–5.10，内部小节 5.x.y 同步顺延）。此类文档通常有密集的编号交叉引用：正文互引（"见 5.3"）、附录映射表（需求条目↔章节编号）、门禁表联动项、交付物清单编号。触发场景：SDD 规格阶段承接用户意见出修订版、设计文档结构重排、门禁表插行。

规模参照：本次实战为 604 行规格文档 v2→v3，插入一整章 + 新增规则条款 + 门禁表更新，共 30+ 次 Edit 分 9 批完成。

## Key Signals

- 痛点信号：编号顺延若按自然顺序（从前到后）替换，会产生临时重号——先把 5.4 改成 5.5 时，原文 5.5 尚未顺延，全文出现两个 5.5；继续替换"5.5→5.6"时 oldString 命中多处，Edit 报"非唯一匹配"失败，或更危险地改错位置。
- 痛点信号：同名/相似小节标题（如多个"## 5.x 子标题"结构雷同）单靠标题行无法唯一定位。
- 痛点信号：顺延改完后，无法用肉眼确认几十处交叉引用没有漏改一处——漏改即产生指向错误章节的引用，且这类残留不在本次改动区，事后很难被发现。

## Essence

替换顺序本身就是唯一性约束的实现手段：**从后往前（从大到小）顺延**，使任一时刻全文每个编号只存在一个实例，oldString 永远唯一。同理，同名标题用"标题 + 下一行首句"组成更长上下文锚点消歧。完成度证据不靠人工目检，靠 grep 双向校验：旧编号残留为零（清零证明）+ 新编号引用计数符合预期（结构完整证明）。

## Approach

1. 动笔前全文梳理交叉引用清单：正文互引、附录映射行、门禁联动项、交付物编号，列出所有受顺延影响的引用点，作为后续批次的任务底单。
2. 章节编号顺延严格按从大到小执行（5.9→5.10 先于 5.4→5.5），内部小节标题（5.7.x→5.8.x）同样从后往前，与父级顺延保持同一纪律。
3. 同名/相似标题用"标题行 + 紧随其后的首个内容句"组成 oldString 上下文消歧。
4. 分批执行（每批 5–6 个 Edit），批内全部成功再进下一批；【2026-11-12 实证修正】同轮多 Edit 为并行执行、完成顺序不保证——顺序依赖链（顺延相邻两步）必须一步一轮，"分批"仅指同轮内互不相邻的编辑打包；插入式 Edit 因 newString 引入同名标题行会污染 oldString 唯一性，须放整批改号后的最后一轮。见 2026-11-12-sequential-edit-chain-one-per-turn-insert-last。
5. 完成后 grep 双向核验：a) grep 旧编号/旧标题 → 期望零残留；b) grep 新编号 → 期望命中数与交叉引用清单吻合（本次实测 39 处新引用匹配，零旧残留）。
6. 输出修订摘要时把"零残留校验结果"作为完成度证据写入。

## Faster Next Time

- 背下顺序纪律一句话：**顺延 = 从后往前；新旧编号同时存在于文中即是危险信号，立即停手检查顺序**。
- 交叉引用清单在动笔前一次性梳理（一次完整读 + grep 检索），比边改边找再返工补漏快得多。
- grep 双向校验是分钟级成本，换取"几十处引用零漏改"的完成度证据，可直接写进修订摘要供审阅者复核。

## Applicability Boundaries

- 适用：结构化 markdown 大文档的章节插入/删除导致编号整体位移，且全文存在编号交叉引用；批量 Edit 工具要求 oldString 唯一的场景。
- 不适用：无交叉引用的小文档（直接整文件重写更快）；编号体系本身要废弃重编的场景（应先定新编号体系再一次性重排，而非顺延）；内容大部分重写的打回重构（应走继承/作废清单法而非增量顺延）；文件被平台托管不可编辑的场景。

## Evidence or Examples

- 本次实战（spec v2→v3，承接用户新增"能力迁移"意见）：插入新章 5.4，原 5.4–5.9 顺延为 5.5–5.10；9 个批次 30+ 次 Edit 全部一次成功，无 mtime 冲突、无重号报错。
- 核验实测：grep 旧编号引用零残留；grep 新编号 39 处匹配；最终确认"章节结构 5.1–5.10、6.1–6.6 完整顺延"。
- 反模式说明：本方法防的是"顺延改错/漏改"；trace 中为预防性执行（未实际踩坑），但重号冲突的失败模式可由 Edit"多匹配报错"机制确认，信号明确可辨。
