# 实现状态核实用定义侧×实证侧双侧比对：仅文档无运行痕迹一律降档"部分实现"

## Scenario

SDD 流程要求核实"某机制/流程在当前环境的真实实现状态"——如派工单要求对 SDD 六环节（各阶段/门禁/完成定义）逐项标注已实现/部分实现/未实现并附证据；平台能力盘点也属同类。仅读定义文档（技能契约/规则/机制文档）会系统性高估：文档声明 ≠ 实际运行过。需要一种可判定、可审计的核实方法。

## Key Signals

- 定义文档齐全（SKILL.md/规则/状态机文档都在）但缺"它真的发生过"的证据——文档存在 ≠ 机制运行过。
- 本轮会话中该机制实际发生的动作（迁移、验证、落盘）本身就是可用的实证侧素材。
- 需求要求逐项三态标注+证据——纯定性描述不满足审计口径，必须双侧证据对照。

## Essence

实现状态核实用**双侧证据比对**：定义侧 = 设计/契约/规则文档声明"应该存在"；实证侧 = 运行痕迹（会话中实际发生的动作）或磁盘实查证明"确实发生"。双侧一致 → 已实现；仅定义侧、无任何运行痕迹 → 部分实现（最易误判的一档）；双侧皆无 → 未实现。每项核实结论必须附双侧证据位置（文件:行或动作记录），把"感觉实现了"变成"可证明实现了"。

## Approach

1. **列核实清单**：把待核实对象逐环节拆项，每项独立判定，禁止笼统整体结论。
2. **收集定义侧证据**：在文档/契约/规则中定位该机制的声明位置（文件:行）。
3. **收集实证侧证据**：找本轮会话中该机制实际发生的痕迹（迁移/验证/落盘动作记录），或对磁盘/配置做实查。
4. **三态判定**：双侧齐备 → 已实现；仅定义侧 → 部分实现（注明缺哪类实证、差在哪）；双侧皆无 → 未实现。
5. **结论表格化呈报**：每行含环节名、判定、定义侧指针、实证侧指针（或"无"），附核对方法说明。

## Faster Next Time

- 核实的固定第一问："这个机制有没有**发生过**，而不只是有没有**写过**？"——找运行痕迹优先于读文档。
- 本轮会话本身就是实证侧矿：门禁呈报实际发生 = 门禁机制运行的实证；写后必验实际执行 = 该纪律落地的实证——比翻历史记录更快。
- 警惕信号：核实结论只引用文档位置、无任何运行痕迹——一律降档为"部分实现"，不心存侥幸。
- ROI：双侧比对一次成型核实表；不比对则每个环节都可能被"文档已实现"误导，审计时返工。

## Applicability Boundaries

- 适用：核实机制/流程/能力的真实实现状态（SDD 环节核实、平台能力盘点、交付前自检、审计口径场景）。
- 不适用：单文件落盘验证（属"写后必验"两步验证法范畴，工具层问题）；价值判断类问题（好不好用——本条只判"有没有"，不判"好不好"）。
- 与《治理机制必须事件驱动才有活性》分工：那条管**设计时**保证机制有活性（触发时点/加载通道/事实源三件套）；本条管**核实时**判定机制实现状态。设计在前，核实在后。
- 边界：运行痕迹只能证明"实现过"，不能证明"长期稳定运行"——后者需跨会话多次观测；仅文档无实证的降档结论是保守判定，宁降勿高。
