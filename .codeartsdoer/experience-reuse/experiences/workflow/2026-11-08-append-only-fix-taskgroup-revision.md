# 已交付物缺陷修复重新进入任务规划：追加式修复任务组修订而非改写既有清单

## Scenario

SDD/门禁类分阶段流程中，**已交付的编码产物**（如单文件自包含 HTML 页面）被用户打回修复，诉求通常混合两类：功能缺陷（必须修，如交互失效）+ 体验/视觉增强（应该做但别喧宾夺主，如布局留白）。此时正确流程位不是跳过规划直接改代码，也不是推倒重建任务清单，而是**重新进入编码任务规划阶段**，在既有 tasks.md 基础上做追加式修订：保留原任务组存档，文末追加修复任务组，版本号升位（v1→v2）。规模参照：单人会话内规格级任务清单（数十至数百行），修复组 3~4 个。

## Key Signals

- 修复诉求中功能缺陷与视觉/体验增强并存——天然要求分块、分优先级、设前置门禁，而不是一锅炖。
- 上游已完成实锤根因诊断（行号级证据、真实渲染截图），规划阶段若重新诊断即浪费；若不核实就引用则可能引用过期证据。
- 任务清单既有组已含检查点与执行记录——推倒重建会销毁执行历史，改写既有组会篡改记录。
- 旧验证体系对本次缺陷类型失明（如 mock 掩盖类盲区导致"满分冒烟"后仍交付缺陷）——修复规划若沿用旧验证契约，同类缺陷复检依旧漏网。

## Essence

修复规划的要害是三个"显式"加一条顺序纪律：

1. **修订形态显式**：任务清单是执行记录载体——追加而非改写。打回针对的是产物，不是流程与既有规划，故既有组原样保留（保历史、保检查点留痕），新组只追加。
2. **证据来源显式**：引用上游已完成的根因诊断作为规划输入，但动笔前必须实核诊断与交付物现状一致（行号、症状吻合），防止引用过期或转述失真的证据。
3. **验证升级显式**：把根因教训固化为新断言/新查项随修复组一并落盘（如新增"mock 注册表与页面真实 id 双向比对"一查），旧断言全量回归且禁止人工补录迁就——修复了缺陷但验证体系原地踏步等于埋雷。
4. **顺序纪律**：先保底修复缺陷、后做视觉增强；保底修复组的完成检查点是增强任务组的前置门禁；预算约束（单轮 ≤20 分钟）写入规划。

ROI：相比推倒重建，追加式修订保留全部既有考证与检查点成果（省去整轮重写）；相比直接改代码，规划层修订强制带上验证契约升级与红线核查（避免修完同类缺陷再次漏网）；先保底后增强保证即使预算耗尽，缺陷已修复（可用性优先于美观）。

## Approach

1. **判定修订形态**：打回诉求是"修复+增强"而非否定原规划 → 追加式修订（保留原组、文末追加修复组、版本升位）；打回针对规划本身 → 走整版重构（继承/作废/升级，见 related 的 rejection-driven 篇）。
2. **动笔前实核证据**：完整读取上游规格/设计/任务清单三份文档 + 打开交付物实核根因指认的行号与症状，确认诊断与现状一致后再引用。
3. **修复子任务自带根因锚**：每个修复子任务标注根因证据（行号、症状吻合点）；采用最小修复面方案（如补缺失 id 而非重构交互层），并显式声明零改动范围（数据层、交互协议、既有文案）。
4. **验证契约升级内置**：把根因教训固化为新断言/新查项（静态解析产物真实结构 vs mock/预期注册集合双向比对一类），随修复组落盘；在最终版本对全部新旧断言做全量回归。
5. **顺序门禁与预算**：保底修复组置最优先，其完成检查点作为后续增强组的准入条件；把"先修缺陷后增强"和单轮预算写进规划正文，防止执行阶段顺序漂移。
6. **呈报即止**：规划阶段产出"新增任务组摘要（编号、子任务、验证断言清单）"即止，不执行编码，显式声明编码由下一阶段承接并等待确认。

## Faster Next Time

- 判据口诀：打回的是**产物** → 规划层增量修订（追加组）；打回的是**规划本身** → 整版重构（继承/作废/升级清单）。
- 修复任务组模板四件套：根因锚 + 最小修复面 + 零改动红线 + 验证断言升级——规划时照单落位，不漏项。
- 反模式：①绕过规划直接改代码（丢失验证升级与红线核查机会）；②推倒重建任务清单（销毁执行历史与检查点留痕）；③修复与增强混在一个任务组无先后门禁（增强未完缺陷未修）；④沿用旧验证契约不做升级（同类缺陷复检漏网）。

## Applicability Boundaries

- 适用：SDD/门禁类流程下已交付编码物被要求修复；根因诊断已由上游完成且可实核；原任务清单需保留执行历史与检查点记录。
- 不适用：①根因未知（先走定位诊断，规划随后）；②打回针对规划本身（走 rejection-driven 整版重构）；③执行已实质完成后上游升版的对齐登记（走终态标注对齐篇，性质是"对齐口径"非"新增规划"）；④仅一两处小修且无新断言价值（直接定点改 + 回归更快）；⑤修订点是对既有内容的改写而非新增（走标注式增量修订 + grep 计数核验篇）。
- 与相邻经验分工：《标注式增量修订+grep 核验》管"改既有内容怎么留痕核验"；《上游升版后任务清单终态对齐》管"既成事实怎么登记不改判"；本条管"追加新修复组的前瞻性规划"——三者按修订性质选型，不混用。
