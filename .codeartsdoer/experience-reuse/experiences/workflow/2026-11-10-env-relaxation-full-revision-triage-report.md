# 环境约束放宽的全量自主修订模式：口径全局切换+删/增/降级/保留四分类+变更点清单呈报

## Scenario

SDD 流水线 design 阶段门禁前，用户对已确认的 spec/design 提出前提性约束变更："环境约束全面放宽：取消多层嵌套隔离，允许 Windows/Kali 本机直接运行（代理本机改、弄坏重装自负），四不红线保留"，同时授权"自主评估当前项目文档（含 spec.md、design.md 等全部相关文件），按需全量修订，不限制仅改某一步，不限制改动范围，不预设修改方案"。工作流语境：单人协作、阶段门禁制、spec 与 design 存在需求-设计追溯表联动、修订完成后须呈报变更点等用户确认。区别于逐条打回修订（意见明确、范围小）与规格重做（以旧文档为基线继承）：本次是授权范围大、但有一条"红线保留"硬约束的自主全量修订。

## Key Signals

- 变更是**前提性**的：旧口径术语（"隔离仿真环境"）贯穿两份文档数十处（实测 72 处落位），不是局部条款。
- 用户授权"不预设修改方案、该改哪改哪"——范围授权，但同时点名必须保留的红线集（四不红线），授权有底。
- 文档体系存在跨文档追溯表：spec 口径一变，design 的追溯行必然悬空，联动刷新是隐含验收项。
- 用户此前偏好授权自主执行而非逐处请示——全量修订+结构化呈报替代逐处确认。

## Essence

前提性约束放宽的正确动作不是"改用户点名的章节"，而是三步闭环：①**口径贯穿范围量化**——先统计旧口径术语在全部相关文档中的落位数，作为修订完成度的验收基线（改完必须对得上）；②**四分类处置**——删（只服务被取消前提的结构性机制，能删则删）、增（放宽解锁的新能力显式新增）、降级（结构上无法强制的条款降为建议且守线点转移）、保留（指定保留的红线原样不动，仅同步环境措辞）；③**变更点清单呈报**——按"改了哪些/删了哪些/新增了什么/降级了什么/保留了什么"五段输出，让用户一次看清"放宽了什么、守住了什么"。核心约束：授权放宽的是环境前提，不是守线目标——红线内容与红线措辞要分开处理，措辞随口径同步，内容分毫不动。

## Approach

1. **量化旧口径贯穿范围**：grep 统计旧口径术语在所有相关文档中的出现处数，登记为修订基线（本例两文档 72 处落位）。
2. **四分类处置逐类落位**：
   - 删：只服务被取消前提的机制性条款（嵌套隔离机制、虚拟机端口转发、"禁止降级到非隔离环境"类禁令）整体删除；
   - 增：放宽解锁的新能力显式立条（如"Kali 未就绪时经用户决策可切 Windows 本机等效环境"——原'无降级回退'的反向）；
   - 降级：结构上无法强制的条款降为建议，并显式转移守线点（见姊妹条守线转移经验）；
   - 保留：用户点名保留的红线逐条核对，只同步环境措辞（"隔离环境内"→"本机仿真环境"），禁止项与验收条件不动。
3. **跨文档联动刷新**：spec 与 design 同步升版本（修订记录各加一条），追溯表逐行刷新与口径变化相关的行（本例 12 行），零悬空。
4. **残留核查**：修订完成后 grep 旧口径术语，确认残留仅存在于修订记录历史区（本例 4 处，属正确保留的历史引用），正文零残留。
5. **五段变更点清单呈报**：改了哪些章节（表）→ 删了哪些条款 → 新增了什么 → 降级为建议的条款 → 原样保留未动的部分；单列"降级为建议"段让防线变化有知情权。

## Faster Next Time

- 一句话检查：约束放宽修订收尾先 grep 旧口径术语——残留只在修订记录历史区才算干净，正文有残留即有矛盾条款。
- 红线核对法：呈报前把用户点名的保留项逐条列一遍并在文档中定位（本例"四不红线四项禁止+验收条件、禁真实外连公网红线、模型只规划不直控、防御配对强制"原样保留），防止措辞同步时顺带弱化守线内容。
- 反模式：只改点名章节（旧口径在其他文档残留，spec/design 口径互相矛盾）；把红线措辞与守线内容一起改掉；变更点清单只写"改了什么"不写"删了/降级了什么"（用户无法判断放宽是否越过红线）。
- ROI：一次全量修订+五段清单呈报，替代逐处请示确认的 N 轮往返（用户授权自主执行的偏好下尤其划算）；修订与验证一轮完成，追溯表零悬空避免后续阶段发现断链返工。

## Applicability Boundaries

- 适用：前提性/环境性约束变更（运行环境、隔离形态、性能口径）引起的跨文档全量修订；用户授权自主修订但指定必须保留的红线集；有追溯表联动的 spec-design 文档体系。
- 不适用：局部小修（1-2 处定点改即可，全量流程过重）；用户给出逐条明确修改意见的打回场景（走打回驱动修订流程）；守护目标本身被取消的场景（红线随目标一起删，无保留项）。
- 与相邻经验分工：规格重做/扩展的口径差异分流与继承纪律见 2026-11-10-spec-redo-diff-triage-inheritance-discipline（以旧文档为基线的重做场景）；多轮打回的继承/作废/升级取舍见 2026-11-07-rejection-driven-doc-revision-strategy；强制条款降级后守线点如何转移见姊妹条守线转移经验；修订标注与 grep 核验的通用方法见 2026-11-06-annotated-incremental-revision-grep-verify。
