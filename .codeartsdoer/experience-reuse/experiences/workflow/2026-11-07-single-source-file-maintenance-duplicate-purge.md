# 可删除副本场景的单一源文件维护制：删重复件+同名禁现+检索命中只引用

## Scenario

单人 + Agent 长期协作工作区的文档治理。用户在文件管理器中发现同一份协作公约类规范文件散落多处（项目 docs/、notes 浓缩版/、平台 rule 目录），产生"同一个文件七八个副本，到底哪个是对的、哪个是错的"的强不满，随后以强指令下达治理要求：指定一份标准文件为唯一源，删除其余重复件，此后**只维护这一份**；同名文件禁止再出现；检索命中同名文件时最多用引用方式；机制永久生效。

## Key Signals

- 用户以"你应该维护一份""我以后就朝这个地方找东西"表态——唯一源落点已被用户明确指定，不是 agent 可自选的技术决策。
- 情绪化强指令（连续否定+脏话）是多副本漂移成本积累到临界点的信号：此前每次"顺手复制一份"都被放过，用户终于在需要找文件时爆发。
- 副本清单实查确认存在 ≥2 份同内容文件，且无平台托管/定稿证据等不可删约束（与 2026-11-06 权威分层经验的前提相反）。
- 用户明确要求"不能写到定规矩里头"——治理机制要走 skill 分装通道，不能膨胀规矩正文。

## Essence

多副本治理先做**可删除性分流**：副本均可自由删除 → 走本条的物理去重+唯一源制；副本含平台托管件/定稿证据等不可删项 → 走 2026-11-06 权威分层+指针化条（零删除）。可删场景的单一源制有三根支柱，缺一即复发：①**唯一源指定**——由用户裁决哪份是标准件，agent 不得自作主张换位；②**同名禁现**——堵住增量复发通道：任何后续产出禁止使用与唯一源相同的文件名，这比"劝自己别复制"可判定、可检查；③**检索命中只引用**——读取侧纪律：检索到非唯一源的历史副本时只引用唯一源路径，不复制其内容。机制固化载体用配套 skill（触发+动作+指向唯一源三要素），并诚实标注 skill 触发非 100%、规矩条为主兜底——治理的强制性来自用户裁决与检查规则，不来自对触发率的乐观假设。

## Approach

1. **实查副本清单**：全项目搜同名/同内容文件，列路径清单（含平台托管件，标注可改性），逐份确认当前内容差异。
2. **确认唯一源与可删除性**：唯一源按用户指定落点锁定；平台托管/证据类副本不删（按权威分层经验另行定角色）；其余副本确认可删后删除。
3. **立增量禁令**：唯一源文件名注册为"同名禁现"——后续任何新文档（含 agent 生成的转述、摘录、浓缩版）不得使用相同文件名。
4. **立读取侧纪律**：检索命中同名文件时，内容以唯一源为准，历史副本只作引用指针（路径+版本），禁抄全文。
5. **机制分装 skill 固化**：只含"触发时机+动作+指向唯一源"三要素的极简 skill；同步在交付摘要中标注触发非 100%，由规矩条/检查规则兜底；不写入规矩正文。

## Faster Next Time

- 触发前置：发现同一内容 ≥2 份全文副本即启动可删除性分流，不等用户在找文件时爆发——多副本每多存活一天，漂移差异就多一分，最终对齐成本更高。
- ROI：存量一次删除 + 增量一条禁令，消除此后每次"改一处漏两处"的手改成本与"哪份是对的"的仲裁成本；机制本身控制在三要素极简形态，避免治理机制自身成为新的维护负担。
- 警惕信号：用户说"我以后就朝这里找东西"= 唯一源路径已被裁决，此后任何"放别的位置更合理"的想法都是违规换位；同名文件再次出现 = 增量禁令失效，优先查"哪个生成环节绕过了禁令"。

## Applicability Boundaries

- 适用：副本均可自由删除的文档治理场景（用户项目内的笔记、浓缩版、手工副本等）。
- 不适用：副本含平台托管文件（不可手改、会被覆写）、用户定稿证据（不可删）等场景——走 2026-11-06 权威分层+指针化条，两场景可混合存在（可删部分删除、不可删部分定角色）。
- 边界：同名禁现约束的是文件名级别；不同名但同内容的新副本不在此禁令内，需靠引用制与生成纪律补充——完全防漂移还需定期副本清单复查。
- 证据边界：本条机制在本 session 结束时处于 spec 固化阶段（删除动作待执行），机制长期有效性待后续修订周期检验。
