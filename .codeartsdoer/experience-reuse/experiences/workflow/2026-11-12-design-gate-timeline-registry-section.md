# design 文档门禁时序登记章：多门禁体系状态总表（三态枚举）+ 执行链位置图集中登记

## Scenario

SDD 流水线 design 阶段（spec-design-agent 角色），上游 spec 含多门禁体系且语义各异：前置实测类门禁（本次已过）、学习考核类门禁（登记为编码/部署执行阶段的前置门禁，设计期只登记不判定）、附录暂挂裁决项（等用户裁决）。派工单明示"design 须在门禁时序中如实登记其为执行阶段的前置门禁"。工作流语境：单人协作、阶段门禁制，design 产出后由 tasks 阶段（另一执行主体）消费。

## Key Signals

- spec 中出现多套门禁编号体系（如 G-PC×N + L1~L4 + 附录暂挂项），状态互不相同——有的已过（附用户裁决日期）、有的属执行期前置、有的悬置待裁决。
- 派工单出现"在门禁时序中如实登记""未过禁编码部署"等表述——登记完整性本身是 design 验收项。
- 门禁条款散落在 spec 多个章节，若 design 仅在对应机制小节顺带提及，tasks 拆解时门禁极易漏映射或状态误判。

## Essence

多门禁体系下，design 对门禁的职责不是复述门禁内容，而是给出**每张卡点在任务执行链上的坐标与当前状态**。将门禁登记从"各章提及"提升为独立成章：一张四列状态总表（门禁编号/状态三态/判定依据与日期/下游消费方）+ 一张执行链位置图（各门禁插在任务序列哪个节点之间）+ 位置说明。状态用三态枚举——✅ 已通过（附裁决留痕）/ ⏳ 执行阶段前置（设计期只登记、执行期才判定）/ ⏸ 暂挂待裁决——tasks 阶段即可把门禁行直接映射为任务依赖节点，无需回读 spec 重推状态。

## Approach

1. **盘点**：从 spec 全文提取门禁清单（编号 + 语义 + 当前状态依据），三类口径分开：已过门禁引用裁决留痕（含裁决日期），前置门禁标注其阻断的动作（如"未过禁编码部署"），暂挂项指向裁决承接章。
2. **状态总表**：四列——门禁/状态（三态枚举）/判定依据与日期/消费方（谁在什么动作前核查它）；每行判定依据必须指向裁决或实测留痕，禁自行改判状态。
3. **执行链位置图**：PlantUML 画出任务执行序列，标注各门禁插入点（如"先学后干门禁 → 编码部署"），配位置说明逐条文字化（防图解析歧义）。
4. **自检联动**：设计自检章加一条门禁完整性核对——spec 门禁编号全部在总表出现、无新增无遗漏。
5. **摘要必报**：交付摘要把"门禁时序登记结果"列为必报项，让用户一眼核验状态判定。

## Faster Next Time

- 三态枚举（✅已过/⏳执行前置/⏸暂挂）直接复用；第四态"不适用"通过省行表达，不造新态。
- 执行前置门禁的登记措辞固定为"执行阶段前置（未过禁 X）"——禁止写成"已通过"，那是执行期结论。
- tasks 拆解时把总表行一一转成显式门禁任务节点（依赖边指向它），本表即拆解输入，零重推。
- 反模式：把门禁原文整段复制进 design（复述且双源漂移风险）；把暂挂项标成"已解决"；总表只有状态没有判定依据（状态不可审计）。

## Applicability Boundaries

- 适用：spec 含 ≥2 类门禁体系、或含执行前置门禁、或含暂挂裁决项的 design 阶段；门禁状态需要跨阶段（design→tasks→执行）传递的场景。
- 不适用：单门禁简单特性（机制小节一句话注记即可，独立成章属过度流程）；门禁全部已过且无执行期判定（只需一段状态说明）。
- 相邻经验边界：workflow/2026-11-07-design-stage-large-spec-inheritance-discipline 管"承接完整性三纪律"（实读/追溯表/预设承接），其追溯表防漏机制与本表互补——追溯表防"条款漏承接"，本表防"门禁漏登记与状态误判"；workflow/2026-11-10-task-stage-coverage-count-gate-dependency-lock 管 tasks 阶段把门禁落成依赖锁，本表是其直接输入。
