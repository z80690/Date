# 先验复用的复核三查清单：数值结论按当前基数重算、索引反查兜底、全文实读定性质

## Scenario

高频周期性触发的增量更新流程（本例每日定时 Wiki 增量更新，个人项目、变更面极小的常规档）：本轮 state.json 报告的 version_token 前进（198→213）但 changed_files 与上一轮完全相同，执行者按先验复用经验（来源：2026-11-09-repeat-changed-set-reuse-prior-round-verdicts）先按上轮结论收敛判定面，再逐项复核。约束：沿用必须以"复核一致"为前提，但"复核"若无固定操作清单，执行口径会漂移——有的只看文件名，有的只读片段，漏检项以静默方式通过。

## Key Signals

- 上轮判定留痕中含**数值型结论**（如"变更 2/288 ≈ 0.7% < 30% 走常规档"）——这类结论依赖两个输入：变更数与仓库基数。跨轮之间仓库文件总数在增长（288 → 349），基数漂移，上轮占比对本轮不再成立，即使变更集合完全相同。
- 变更文件路径在既有索引（wiki-index / 检索映射）中反查为 0 命中——这是"该文件不属于任何已覆盖文档修订面"的独立证据通道，与路径前缀归属判定互相独立，可作兜底。
- 文件 diff 表现为**纯追加模式**（本次变更仅为文件末尾追加一条新日期的执行条目与例行观察）——文件性质（工具运行时日志）未变，与上轮"成因 1 过滤"的定性一致；若 diff 出现语义修改（改写既有条目、结构变化），先验必须推翻。
- 三项复核的执行成本极低（重算占比、一次索引反查、一次文件全文读取），远低于重走全量三级归属判定的成本。

## Essence

先验复用的"实读复核一致"需要落到**固定三查**，且三查各覆盖一个独立失效通道：**① 数值重算**——凡留痕结论含基数依赖的数值（占比、比例、计数），一律用当前仓库状态重新计算，上轮数值只作对照不作本轮依据；**② 索引反查兜底**——用变更路径反查现有索引/检索映射，确认归属判定的反例通道为空；**③ 全文实读定性**——读变更文件全文（而非片段）确认本次 diff 的性质是否仍与上轮定性一致。三查全过才沿用先验；任一查不一致，以实读结果为准并推翻对应先验项。

## Approach

1. **提取先验面**：从上轮留痕（update_context.filter_note、成因标注、骨架结论、update_plan）中列出本轮拟沿用的每一条结论，区分"定性结论"（文件性质、归属、过滤理由）与"数值结论"（占比、计数、阈值比较）。
2. **查一：数值重算**：统计本轮变更计数与当前仓库文件总数，重新计算占比并与阈值比较；与上轮数值对照，解释差异来源（本例：基数 288→349 且变更数 2→1）。
3. **查二：索引反查**：在索引文件（如 wiki-index 的 section_code_paths / code_refs）中反查变更文件路径，确认 0 命中；若反查命中，说明变更文件已被某篇文档覆盖，先验的"不在修订面"结论失效，需转入小节修订评估。
4. **查三：全文实读**：读取变更文件全文，识别本次 diff 模式（纯追加 / 语义修改 / 结构变化），与上轮定性比对；纯追加同性质 → 定性沿用，语义变化 → 推翻先验重走归属判定。
5. **收敛与留痕**：三查全过 → 宣布先验沿用成立、修订面为空（或按上轮修订面）；把"沿用先验 + 三查结果"写入本轮判定留痕（filter_note、update_plan），保证下一轮仍可提取先验，形成跨轮收敛链条。

## Faster Next Time

- 三查合计 3 次读取 + 1 次计数，数分钟内完成，替代重走"规模分级 → 三级归属 → 成因补判"的全量判定链路；每日定时增量场景下判定成本随轮次持续收敛而非线性重复。
- 预警信号：只要看到"上轮留痕里有 X/288 这类带分母的结论"，立即触发查一——分母（仓库基数）是跨轮最易漂移的量，且漂移是静默的（不报错、不显眼）。
- 反模式（不应使用）：a) 变更集合不重复（新文件或新路径出现）时套用本清单——那是首轮判定，不是先验复用；b) 用"结论方向没变"代替重算——方向相同不代表数值仍低于阈值，基数据增长可能把 0.7% 抬到 3%，虽仍低于 30%，但换一个更敏感的阈值就会翻档；c) 只读文件头部片段代替全文实读——纯追加型日志的变更在文件末尾，片段读取会漏看。

## Applicability Boundaries

- 适用：周期性/高频增量流程中，本轮变更集合与上轮完全相同（version_token 前进但 changed_files 路径与 status 集合不变），且上轮留有结构化判定留痕的场景。
- 适用：任何"先验结论含基数依赖数值"的复用场景，不限于规模分级（如覆盖率、命中率、占比类指标）。
- 不适用：变更集合有新成员时的首轮归属判定；上轮无结构化留痕可提取的场景（此时无可复用先验，须全量判定）；一次性非重复任务。

## Evidence or Examples

- 本轮实例（项目 Date，每日定时 Wiki 增量更新）：state.json version_token 198→213，changed_files 仅 1 个文件 `.workbuddy/memory/automations/dec4f4ef-…/memory.md`（modified），与上轮（token=198）同一文件。
- 查一：上轮留痕 2/288≈0.7%；本轮重算 1/349≈0.29%（仓库文件总数已增长至 349），仍远低于 50% 重建阈值与 30% 降级阈值 → 常规档，且差异来源可解释。
- 查二：wiki-index.json 反查 `.workbuddy` 路径 0 命中。
- 查三：文件全文实读确认本次变更仅为末尾追加"2026-11-10 17:19 执行"条目与例行观察（逐日签到执行日志：命令、退出码、积分余额），文件性质与上轮"工具运行时日志、成因 1 过滤"定性一致。
- 收敛：修订面为空，阶段 3+4/5/6 无实际工作；"沿用上轮先验 + 实读复核一致"写入 progress.json 的 update_context.filter_note 与 stage_2.update_plan，留痕闭环。
