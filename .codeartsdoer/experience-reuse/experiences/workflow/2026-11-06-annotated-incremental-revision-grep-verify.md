# 既有已确认文档的增量修订：统一补充标注落位 + grep 计数闭环核验

## Scenario
已确认/定稿的规格或规范文档收到用户的增量修改意见（常为语音转写的多条修改点），硬约束：只改相关章节、其余已确认内容零改动、修订须可追溯、禁止整篇重写。触发条件：修订点清单明确（如 3 个主题修改点），文档较长且含编号条款体系与交叉引用。典型规模：单人会话内的规格级文档（数百行）。

## Key Signals
- 用户意见逐条列出但同时要求"其余部分认可不动"——改动边界必须显式，漏改或越改都构成违约。
- 文档已有编号条款与交叉引用（门禁、验收条件、数据约束/清单字段多处引用同一概念）——一个修改点会派生多处落笔位置，只改正文必漏。
- 修订完成后若靠人工重读全文自证，成本高且不可量化。

## Essence
增量修订的要害是"改动范围显式化 + 完成度可量化"。给每处修订内嵌统一的机器可检索标记（如【用户补充 YYYY-MM-DD】），修订结束用 grep 统计该标记的总数与行分布，与修改点清单逐条比对——一次检索即可证明"改了哪些、派生位置是否补齐"，替代人工重读全文，形成低成本闭环证据。

## Approach
1. 动笔前完整读取原文档一遍，摸清章节结构、编号体系与交叉引用，预判每个修改点会派生落笔的位置（正文条款之外还有异常场景、验收条件、数据约束等）。
2. 把修改点按主题分批 edit（如每批 5-7 处），未提及的章节一律不碰；每处修订文本内嵌统一标记【用户补充 日期】。
3. 派生位置同步带标，保证"标注数 ≥ 修改点数"且每处命中的位置可解释归属哪个修改点。
4. 收尾核验：grep 标记字符串，核对总命中数与行分布是否覆盖全部修改点及派生位置，把命中列表直接作为修订完成证据与总结附件呈报。

## Faster Next Time
- 标记即追溯：修订处自带日期标记，后续任何人 grep 一次即可圈出本次改动范围，无需依赖 diff 历史。
- grep 计数核验是零成本闭环：比重读全文快一个量级，且能暴露"只改了正文、漏改派生引用"这一最常见遗漏。
- 分批 edit（主题分组）降低单批失败后的重放成本，比一次性巨型重写安全。

## Applicability Boundaries
- 适用：有明确修改点清单的增量修订；文档含交叉引用与派生落笔位置；用户要求可追溯或其余内容冻结。
- 不适用：大面积结构性重构（应重写文档并走重新确认流程）；用户要求清理既有标记的场合（改用变更日志等其他追溯手段）。
- 标记格式宜沿用文档既有标注风格或先自行声明，避免与新旧标注混杂导致核验口径不清。

## Evidence or Examples
- 实例：kb_arch_foundation/spec.md 收到 3 个语音修改点（仓库嵌套防护、学习材料质量门槛、规则草稿极简交付）；两批 edit 共 12 处落笔；收尾 grep "【用户补充 2026-11-06】" 命中 16 处，覆盖正文条款/异常场景/验收条件/数据约束等派生位置，修订一次闭环。
- 命中行分布清单作为修订总结证据呈报用户审阅；全程未触碰未提及章节。
