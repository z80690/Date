# 授权安全演练类派工单的需求规格四件套模式

## Scenario

用户派发授权攻防演练/渗透模拟类研发派工单（本机+隔离靶机环境，如框架部署+OPSEC 隐藏+流量检测），要求进入 SDD 需求规格阶段。此类派工单的安全约束多为口语化叙述（"只打自己机器""不许外头""抓包验证"），若直接写成普通功能需求，红线会散落在正文里不可验收。工作流规模：单人 Agent 会话，spec 阶段一次成文、用户门禁确认后停驻。

## Key Signals

- 派工单含攻击性动作描述（探测/伪装/C2 模拟/流量隐藏）与"仅本地/禁止公网"类纪律声明；
- 派工单要求废弃某些既有工具/资产，而这些资产是近期刚建立并验收的，存在裁决冲突；
- 用户语音补充中混有强情绪约束（"禁止你攻击别人""只做演练"），暗示红线权重极高、误判代价不可接受。

## Essence

把模糊安全要求转成可验收条款的关键是四件套结构：①**目标白名单**——逐条枚举允许的网络目标（回环/虚拟网卡子网/官方靶场等），白名单外一律拒绝，把"不许打别人"从口号变成可判定规则；②**红线条款**——禁公网外连+越界即停的语义定义（终止动作/阻断外发/告警留痕/等待裁决），而不是只写"禁止"；③**可量化判定**——成败指标全部数字化（明文命中=0、公网 IP=0、异常外连=0 等），任一不满足即判失败须整改重跑，消除"隐藏成功"这类主观表述；④**待裁决附录**——所有与既有资产/历史裁决冲突的事项（废弃口径、接入方式、就绪方式、工具使用范围）集中列附录，明文"禁自作主张"，把决策权留给用户。同时冲突背景须如实登记（新单按新口径执行、不回溯旧裁决），防止文档回潮。

## Approach

1. 逐条扫描派工单，把每个安全相关叙述归入四类之一：允许范围→白名单、禁止行为→红线、验证标准→量化判定、无法自决事项→待裁决附录。
2. 编写白名单：枚举每一条允许目标（如 127.0.0.0/8、::1、虚拟网卡子网、局域网自建资产、官方靶场地址），默认空集的条目标注"须用户拍板"。
3. 编写红线：每条禁止行为附越界即停语义四动作（终止动作/阻断外发/告警留痕/等待裁决），不写无语义的"禁止"。
4. 编写量化判定：每个成败声明转成可测量指标（计数=0、TLS 有效、日志干净等），并写明"任一不满足判失败+整改重跑"。
5. 冲突资产处置：在 spec 背景区如实登记冲突（"A 资产是 X 日刚验收的既有资产，本单要求废弃"），废弃的具体口径（停用 vs 卸载）列待裁决附录，正文禁写处置动作。
6. 全文用 EARS 句式（When/While/Where/If + 系统应当），确保每条可验收。
7. 阶段纪律写进文档头：本阶段落盘经确认即停，未确认禁入设计与编码。

## Faster Next Time

- 拿到安全类派工单先做四类归组再动笔，避免红线散落正文不可验收；四件套可直接作为 spec 章节骨架复用。
- ROI：一次成文通过用户审阅的概率显著提高——待裁决项前置集中呈报，避免用户在实现阶段才暴露分歧导致整篇返工。
- 警示信号：spec 里出现"隐藏成功/合规/安全"等主观词而无数字指标，即为量化判定缺失；出现对既有资产的处置动词（删除/卸载）而无待裁决标注，即为越权风险点。

## Applicability Boundaries

- 适用：任何含攻击性动作的授权演练/渗透模拟/红蓝对抗类任务的 spec 编写，也适用于其他"高约束+强红线"场景（如生产变更、数据操作类派工单）。
- 不适用：纯防御分析、无攻击动作的安全加固任务（红线可简化，白名单意义下降）；模糊闲聊或未授权的攻击性请求（后者应拒绝而非写 spec）。
- 局限：白名单与量化指标的具体取值依赖任务上下文，本经验提供的是结构模式而非取值模板。
- 相邻经验边界：2026-11-10-dual-use-research-safety-redline-paired-clauses 处理"双用途研究的可迁移攻击能力与对外基础设施合规红线"（条款内容视角），本条处理"授权演练派工单的模糊安全要求转可验收条款的四件套结构"（spec 骨架视角）；待裁决附录是 2026-11-10-evaluation-report-decision-authority-clause 决策权归属条款化在高红线场景的具体落位。
