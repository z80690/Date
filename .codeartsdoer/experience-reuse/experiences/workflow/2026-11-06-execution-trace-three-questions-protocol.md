# 执行过程可查性协议：三问三答映射 + 随动作即时落盘

## Scenario
Agent 长期协作工作流（单人 + Agent、多阶段 spec 流水线）中，用户提出可观测性质询："我现在怎么查你的执行过程？只能查你层层的规划文件吗？能满足需求吗？"——规划文件（spec/design/tasks）写的是"计划做什么"，用户真正缺的是"实际做没做、做到哪、东西在哪"的查询入口。这不是单次汇报问题，而是需要协议化的过程记录机制。

## Key Signals
- 用户问"怎么查你的执行过程"且现有答案只有"翻规划文件"——说明计划文档与执行事实混为一谈。
- 执行记录靠会话结束前"回忆式补写"——补记必然遗漏中途的偏差、失败尝试与冻结时刻。
- 同一件事（执行状态）散落在执行记录、汇报文本、规划文件多处且版本不一。

## Essence
执行可查性的本质是把"查过程"收敛为**三个固定问题的固定答案通道**：做了什么（变更日志一行/次）、做到哪（事实表状态字段 + SX 阻塞态）、产物在哪（索引路径）。关键约束是**即时落盘**：记录随动作发生而写，不靠批量补记、不靠定时汇总——否则记录本身退化为又一份死文档，与机制活性要求冲突（见 2026-11-06-event-driven-mechanism-liveness-single-fact-source）。

## Approach
1. 定义三问三答映射表并写入机制文档：
   - "做了什么" → 变更日志区追加一行（日期 + 条目 + 动作 + 触发来源）；
   - "做到哪" → 单一事实表的状态字段 + 阻塞态标记（SX + 编号 + 一句话原因），禁止在多个文档抄写状态；
   - "产物在哪" → 知识索引的条目路径，保证一句话定位到文件。
2. 每个写动作完成后立即同步对应通道（当日完成即当日记录），明文禁止"任务完结后统一补记"与"定时汇总"。
3. 查询侧设加载上限：回答执行现状只读"事实表状态 + 最近变更日志若干行 + 目标条目路径"，不全量加载历史轨迹。
4. 阶段汇报复用同一通道：汇报文本直接引用三通道现状，不另造第二份过程记录。

## Faster Next Time
- 收到"过程可查/你怎么证明做了"类质询时，先给三问三答映射表再谈其他——三问之外的信息默认不给。
- 警告信号：发现自己在会话尾部"补写执行记录"→ 说明即时落盘已失效，立即改为随动作写入。
- 检查信号：同一执行状态出现在 ≥2 处文档 → 立即收敛到事实表单一字段。
- ROI：协议落盘后用户一句话即可自查进度与产物位置，消除"逐层翻规划文件"与"反复询问现状"两类往返；本会话中执行记录随任务 1–12 逐步追加，中途冻结/恢复（见 2026-11-06-mid-execution-append-subtask-freeze-commit）均有据可查。

## Applicability Boundaries
- 适用：多阶段长任务、需要人类审计或跨会话续作的 Agent 工作流；交付物包含治理机制的项目。
- 不适用：一次性小任务（单条汇报即够，协议是纯开销）；已有成熟 CI/日志系统的代码工程（应复用既有审计通道）。
- 反模式：把三问三答写成事后汇总报告；用规划文件的状态复选框代替事实表；查询时全量重放轨迹。

- 实证：2026-11-06 Date 项目 kb_maintenance/kb_arch_foundation 会话。用户质询"我现在怎么去查你的执行过程……我只能查你的层层规划文件吗？能满足需求吗？"后，spec v2 §5.9 固化"执行轨迹可查"章：三问三答协议、即时落盘（禁批量补记/定时汇总）、查询加载上限。
