# 多阶段流程的阶段推进指令时点语义消歧：按当前未闭环项解释，回溯阶段指令=对齐修订、停驻位指令=终判授权

## Scenario

带编号阶段与门禁链的多阶段流程（如 SDD 四阶段：需求规格→设计→任务规划→执行，叠加 M1–M7 门禁链），执行已实质走完（六门放行、M7 提交候选停驻待人工终判）之后，用户连续下达多条"进入下一阶段"指令，字面分别指向**早已完成的阶段**（"进入下一阶段：实现方案创建""进入下一阶段：编码任务规划"）以及**终判停驻位**（"进入下一阶段：任务执行"）。规模参照：本单 spec v5 / design v3 / tasks v2 三文档、八任务组 34 任务、六门禁证据在档，三条指令在 40 分钟硬限内全部一次收敛。

## Key Signals

- 指令字面语义与状态机当前位冲突：指令指向的阶段产物（design.md/tasks.md）早已定稿甚至已按其执行完毕——机械重做=推翻既成事实+审计断链+大量返工；机械拒绝="该阶段已完成"=违背用户推进意图。
- 推进指令到达前，上游基线已发生变更（如 spec 因用户新指令修订至 v5），而下游文档（design/tasks）仍停留在旧基线——用户说"进入下一阶段：设计"的真实意图大概率是"让设计跟上新基线"，而非重建设计。
- 流程停在唯一一处人工终判停驻位（提交候选待授权、禁自动提交），用户此时发推进类指令——若不解释为授权，流程在此永久悬挂；主智能体已连续多轮呈报"表态即执行"。
- 痛点信号：呈报循环里反复出现同一句"等待您终判"，而用户以阶段指令而非"通过/不通过"作答——用户不关心流程术语，只关心往前走。

## Essence

阶段推进类指令的语义**不由指令文本单独决定，而由"指令到达时流程状态机的当前位 + 未闭环清单"共同决定**——同一句指令在不同时点含义不同。判定准则是"按最小未闭环项解释"：指令指向已完成阶段（回溯）→ 解释为"上游基线已变，需对齐同步修订"（减法修订，非重做）；指令指向终判停驻位 → 解释为"对该停驻事项的推进授权"（终判=通过），前提是该停驻动作已在停驻声明中明确列为待授权项且属既定授权边界内；指令指向当前正常待办阶段 → 按常规语义进入。解释结果必须随执行呈报显式声明（"本次=对齐修订而非重做"/"本次推进=终判授权=通过"），让用户能立即纠正误判。

## Approach

1. **先读状态再解释指令**：收到"进入下一阶段：X"先查状态机当前位、各阶段产物版本、未闭环清单（含停驻位声明），禁止见指令就直接调用对应阶段子代理重做。
2. **三分判定**：a) X < 当前位（回溯）→ 判定为对齐修订：定位上游基线变更点（spec 版本、新指令），对下游文档做减法同步（生效时点切割、被取消项保链不删行、终态注记），禁改既有判定结论；b) X = 当前停驻位且该位已声明"等待人工终判"→ 判定为终判授权，显式声明"本次推进=终判授权"，随即执行该停驻位声明的既定动作（如按候选清单提交）；c) X = 当前正常待办 → 常规进入。
3. **语义解释显式呈报**：执行摘要开头一行声明判定结论与依据（"您的设计指令经判定为对齐同步修订，基线 spec v4→v5，既成判定零改写"），给用户即时纠偏入口。
4. **授权解释的边界核验**：仅当停驻声明已明确列出待授权动作（提交/收工/放行）且动作在既定红线内时，才可把推进指令解释为授权；越界不可逆动作（删除、外发、改规则文件等）不适用本消歧，仍须显式确认。
5. **对齐修订联动减法纪律**：回溯型对齐沿用规则收紧轮的减法工具（全局注记代逐处改写、保链改写、生效时点切割），修订量与基线差异成正比而非与文档篇幅成正比。

## Faster Next Time

- 收到任何阶段推进指令，第一动作是读状态不是读指令——状态机当前位 + 未闭环清单 30 秒内可定位指令真实含义，避免整轮误判。
- 识别"终判停驻 + 推进指令"组合立即兑现授权并执行，不要再追加一轮"请确认是否通过"——用户用行动投票，重复请示违背授权偏好（P5 类信号）。
- 对齐修订前先列"基线差异点清单"（新版 spec 改了哪些条款），按清单落笔，修订量可控（本单 design 6 处编辑、tasks 24 处编辑即完成对齐）。
- 反模式：见"进入下一阶段：设计"就重调设计子代理从头重建（推翻已放行门禁证据）；对停驻位的推进指令再发一轮确认请示（流程悬挂+用户被反复拉扯）；把终判授权扩大解释为"后续所有动作免确认"（越权执行红线动作）。

## Applicability Boundaries

- 适用：带编号阶段/门禁链/状态机的多阶段流程，在执行中后期或完结后收到推进类、回溯类阶段指令的场景；用户惯以阶段指令代替门禁术语作答的协作模式。
- 不适用：首次进入流程或各阶段均无产物的早期（指令语义无歧义，直接常规进入）；用户明确说"重做/推翻 XX 阶段"（这是推翻指令，走重新闭合模式，不是对齐修订）；停驻动作未在停驻声明中列明或属越界不可逆动作（授权解释不成立）。
- 与相邻经验的分工：《规则收紧类指令的最小破坏性落盘》管规则收紧指令**怎么落盘**（时点切割/全局注记/两清单），本条管推进指令**怎么解释**（时点消歧三分判定）；《任务清单对齐修订终态标注》是本条判定为"对齐修订"后的下游执行手法（终态注记怎么写）；《全权授权自执行检查》管授权**放宽**后的门禁执行权转移，本条管授权语义从阶段指令中的**识别**；SDD 阶段分支路由经验管"哪个阶段调哪个子代理"的静态路由，本条管指令到达时点的动态语义。

## Evidence or Examples

- 三轮实战（源会话 ses_e48cafc3effeTPRi3rutvWPKyY，特性 sdd_agent_refactor）：①"进入下一阶段：实现方案创建"→ 判定为 design v2→v3 对齐（对齐 U6 七条/spec v5：M5 门禁行保链改写、新增 §2.1.3-9 极简纪律落位、追溯表对齐注），6 处编辑落盘验证通过；②"进入下一阶段：编码任务规划"→ 判定为 tasks v1→v2 对齐（M5 组标注已取消保链、§1–§8 终态注记、§10 终态一览），24 处编辑；③"进入下一阶段：任务执行"→ 判定为对 M7 8.2 终判停驻位的授权（终判=通过），随即执行候选清单精确暂存（52 文件，+5051/−33，G2 排除项零混入）→ 提交 `fa81dd6`，中文提交信息无乱码，特性关闭。
- ROI：三条指令均一次收敛、零返工；避免了"重做 design/tasks 两阶段"级别的时间浪费（重做意味着推翻六门禁证据与既成判定），且流程未在终判位悬挂——从指令到提交落库在硬限内完成。
- 边界实证：提交动作本身在停驻声明中已明确列为"待您终判授权（通过=执行提交+登记归档）"，故"任务执行"指令可安全解释为该授权；同一会话中经验库增量文件按既定排除范围留在工作区未随特性提交（不循环提交），授权解释未越出声明边界。
