# SDD 规格重做/扩展的口径差异分流与继承纪律（覆盖/冲突分流→三段式改写→路径稳定→回顾显性化）

## Scenario

SDD 流水线 spec 阶段（spec-requirement-agent 角色）承接"重做/扩展"类派工单：用户明确要求"在上一阶段生成的既有规格基础上重做/扩展"，同时补充了新类目、新约束与新的完成口径。旧规格文档仍在、路径仍被上游引用。单人协作、每阶段产出须用户确认后推进的门禁文化。区别于首次生成（无旧文档可比对）与纯改造类派工单（对象是机制而非规格文档本身）。

## Key Signals

- 派工 prompt 明示"须在其基础上重做/扩展"——继承完整性是隐含验收项，从零重写即违约。
- 新派工单对旧规格的多处口径**已给出明确新值**（如实例数量、评估范围、环境策略），差异本身不需要用户再裁决。
- 新派工单引入旧规格完全没有的模块（新类目、新红线、新门禁），且部分新约束与旧条款字面抵触（如旧"≥3 实例" vs 新"只跑通 1 个"）。
- 文档目录/文件名与新定位出现偏差（旧名只覆盖旧定位的一个子集）。

## Essence

重做 ≠ 从零重写，也 ≠ 逐处裁决。核心动作是**差异性质分流**："新派工单已就该差异给出明确新口径的叫覆盖，没给新口径、新旧要求互斥的才叫冲突"——覆盖型直接按新口径改写，冲突型才转裁决单流程。覆盖改写必须**显性可审计**：每处差异按"旧口径 → 新口径 → 处理方式"三段式落账，收尾在产出摘要中固定输出"口径差异处理回顾"。同时执行两条继承纪律：旧规格未被覆盖的章节（术语、角色、边界）原样继承保留，定位升级时旧核心产物**降级为子项/首例**而非删除；文档路径保持稳定，命名偏差登记为审阅项待用户拍板，不擅自改名。

## Approach

1. **双清单前置**：通读旧规格全文，同时把新派工单的全部约束/红线/顺序要求逐条编号建索引（零遗漏），两份清单在手才动笔。
2. **差异性质分流**：逐条比对新约束 × 旧规格条款，对每处差异先判定性质——互斥冲突（新旧都成文且无新口径可依）→ 转《派工单协作中的冲突裁决单与人工门禁前置模式》的裁决单流程；扩展/覆盖型（新派工单已明示新口径）→ 直接进入改写，不产生裁决往返。
3. **口径差异三段式**：每处覆盖型差异写成"旧口径 → 新口径 → 处理方式"，处理方式从五个枚举中选：改写覆盖 / 定位降级（旧核心产物降为子项、首例）/ 规则拆分（一条旧规则按新维度拆成多条）/ 按对象分工（同一资源在不同对象下分别定策略）/ 全新新增（旧规格完全缺失的模块）。
4. **继承改写**：改写只发生在有差异的条款上；旧规格中未被任何新约束触及的章节原样继承。定位升级类派工单（旧定位是新定位的子集）必出"定位降级"处理，且降级后旧产物的能力描述保留、只是层级下调。
5. **路径稳定**：文档落盘路径与目录名保持与旧规格一致（上游引用不破坏）；命名与新定位的偏差单独登记为一条审阅项（附改名建议），推迟到本次审阅环节与用户一并拍板。
6. **回顾显性化**：产出摘要末尾固定加"口径差异处理回顾"段，逐处列出覆盖行为（旧口径→处理结果），让用户审阅时可逐项核对"改了什么、为什么改"，未提及的差异即视为继承未动。

## Faster Next Time

- 分流判据一句话版："新派工单已给出新口径的叫覆盖，没给的才叫冲突"——先分流再动手，避免两类错误：把覆盖型拿去裁决（用户已明示再问一遍是负担）、把冲突型擅自覆盖（越权代行需求方决策）。
- 三段式差异表在动笔前一次成型，写规格时照表逐处落位，防漏防漂；写完逐处勾销。
- ROI 实测：5 处差异全部判定为覆盖型，零裁决单往返一次成稿落盘；对比逐处裁决每处至少一轮对话的成本，本例省 5 轮。
- 反模式：把"重做"理解成从零重写（旧规格有效内容静默丢失）；覆盖无回顾段（用户无法核对覆盖行为，只能全文重读）；顺手按新定位改目录名（上游引用断裂）。

## Applicability Boundaries

- 适用：SDD spec 阶段"在既有规格基础上重做/扩展"类派工单；新旧差异以扩展/覆盖为主、无或极少互斥冲突。
- 不适用：首次生成规格（无旧文档可比对，无差异可分流）；存在互斥冲突需用户裁决的场景（转裁决单流程）；design 阶段承接规格（承接纪律见 design 阶段三纪律）。
- 与相邻经验的分工（三者构成 spec 阶段冲突/差异处理完整分流）：派工单 vs **规则层**（公约/注册表/机制文档）的意图冲突 → 《SDD 规格阶段实查期的规则冲突显式化》走裁决项随规格呈报；派工单 vs 已确认规格的**互斥冲突** → 《派工单协作中的冲突裁决单与人工门禁前置模式》走裁决单+门禁前置；派工单 vs 旧规格文档的**覆盖型口径差异** → 本条直接按新口径改写+回顾显性化。同一任务中三者可能先后出现，先分流再路由。
- 约束盘点、约束→EARS 条款翻译、门禁编号切分等"首生成"侧方法由《约束型派工单到 EARS 门禁化规格》承担，本条只管重做场景的增量动作。
