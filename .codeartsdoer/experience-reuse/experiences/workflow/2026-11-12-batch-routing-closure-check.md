# 大批量变更文件分流归因的分组闭合校验：分组求和等于总数才算裁决完整

## Scenario

增量更新流程中变更文件量大（本例 247 个）且多数未被既有映射直接命中时，需把全部变更文件按归属分组裁决（命中既有文档 / 第三方克隆 / 按约定跳过 / 待补判后再路由）。分组来源多元：脚本反向查找输出、目录计数、逐文件实读。只要漏判或错计一组，后续修订就会遗漏真实受影响内容或为无关文件空跑。

## Key Signals

- 分组计数的证据源不统一：既有"变更清单口径"（state.json 列出的 added 文件）与"磁盘实况口径"（目录实际文件数）并存——本例磁盘 prepared/DVWA 下有 257 文件，而变更清单里只有 216 个（其余非本轮变更）。两口径混用会立刻产生"对不上"的假象。
- 脚本输出只给了聚合数字（unmatched_count=230）而无分组明细时，分组闭合只能靠回读输出文件核对明细。
- 差值哪怕只有 1 也是有效信号：本例"差 1"回读后修正为分组计数口径错误（把磁盘 257 当变更清单 217），闭合后 17+8+216+4+2=247 ✓。

## Essence

分流裁决的完整性不靠"感觉都判过了"，而靠**算术闭合**：所有分组计数之和必须等于变更总数。闭合失败不一定是漏判，更常见的是**口径混用**——先用一行决策规则锁死唯一口径（一切计数以变更清单为准，磁盘实况只用于性质判读），再回读明细修正分组。闭合通过后才允许进入派工/修订；闭合是裁决阶段的完工门禁，不是事后补充统计。

## Approach

1. **锁定唯一口径**：宣布"分组计数一律取自变更清单文件（逐条 path 列举）"，目录/磁盘计数只用于判定目录性质（是否第三方、是否运行时数据），不参与求和。
2. **初步分组**：命中组（脚本输出 affected_docs 附带的 changed_files）+ unmatched 组（脚本标 needs_further_judgment 的全部路径）。
3. **unmatched 再分流**：按目录前缀/性质证据（README 特征、运行时数据特征、目录池约定）拆为第三方克隆、按约定跳过、待补判三组；待补判组逐文件实读归因。
4. **闭合校验**：Σ(各分组计数) 对比变更总数；不等 → 回读脚本输出文件的 unmatched 明细，逐条核对，优先排查口径混用（本例：磁盘 257 ≠ 清单 216，修正后闭合）。
5. **闭合后产出分流表**：每组一行（数量 + 裁决 + 证据），作为派工与修订的输入；后续任何"跳过"裁决必须能在分流表中找到归属组。

## Faster Next Time

- 一行决策规则：unmatched 裁决动笔前先做求和闭合——Σ分组 ≠ 总数时禁派工，先回读明细查口径混用。
- ROI：一次求和（分钟级）替代"漏判一组后返工整轮派工"的风险；本例差值 1 的排查成本约一次明细回读，换来 247 文件全量裁决的可信度。
- 早期信号：磁盘目录文件数与变更清单条目数一比对即知口径差（257 vs 216），在初步分组阶段就应察觉，不必等到闭合校验才发现。
- 反模式：拿磁盘实况数给"变更组"计数；闭合失败直接怀疑脚本 bug 而非自查口径；闭合通过后又在派工阶段临时新增"跳过组"而不重新闭合。

## Applicability Boundaries

- 适用：任何大批量条目按属性分流的场景（变更文件归属裁决、批量告警分诊、批量文档路由），凡"分组来源多元 + 总数已知"即可用。
- 不适用：小批量（≤10 条）直接逐条人工判即可，闭合校验收益低于成本；分组边界本身模糊、需定性研讨的场景（闭合只能验完整性，不能验正确性）。
- 前提约束：闭合校验只保证"没有漏项"，不保证"每项归因正确"——归因正确性仍靠实读证据（本例第三方裁决靠 README 实读）。
