# 设计文档按用户多条疑问修订的落点映射与实查纪律

## Scenario

规格/设计类长文档（数百行、含交叉引用与版本头）收到用户 N 条修订疑问，每条是复合要求："补一节内容 + 给出可执行验证方法 + 与上游规格条款对齐 + 版本号递增 + 输出逐疑问修订摘要"。修订面广、独立落点多，逐条串行编辑耗时且易漏联动。

## Key Signals

- 修订指令逐条编号且带"不得回避"约束。
- 部分疑问指向底层机制定性（如"某通道是否真支持零新增"，必须实查而非推断）。
- 文档已有稳定章节编号体系，修订以"新增小节/段落增补"为主，不动既有编号。

## Essence

修订质量取决于三件事的闭环：**逐疑问→落点→证据的映射完整性**、**实查先于断言**、**编辑批量化+收尾机械验证**。其中实查结论必须按三档如实呈现，防止"为了闭合疑问而夸大定性"：

1. 证据确凿项 → 写文件路径+机制描述；
2. 边界定性项（如"规程式检查点而非推送总线"）→ 如实写局限，不美化成"事件回调"；
3. 未实测项（如"派工直连路径首次使用"）→ 挂到后续验证轮实测，并更新风险条目。

## Approach

1. 动笔前将上游规格与本设计文档**双全文读毕**（超长文档分段读），并列出每条疑问的目标落点章节。
2. 实查型疑问先查底层（读运行规则/配置/机制文件取证），实查结论按三档如实落笔；查证结果反向决定设计结论，而不是先写结论再找依据。
3. 每个新增节/增补段统一打标"（vN 新增，疑问K）"，修订头部集中记录"疑问→落点章节"映射，保持双向可追溯。
4. 只增不删：既有章节不重写；其余章节的联动修改（门禁表、追溯表、风险表、目录树）以**追加指针**方式引用新增节，不复制内容，避免双份事实漂移。
5. 编辑批量化：同一文件的多个编辑点，只要 oldString 互不重叠且各自唯一，可**一轮并行发起**（实测一轮 8 个全部成功）；仅当插入新章节导致后续编号顺延时，才需按编号从大到小排序。
6. 收尾机械验证：用 grep 按"vN 新增，疑问K"标记扫描全文，核对每条疑问的落点是否真实命中（本次 8 处命中）。
7. 输出四列修订摘要（疑问|落点章节|核心内容|新增/增补类型）+ 实查结论单独呈报，停在本阶段等待用户确认。

## Faster Next Time

- ROI：本次 782 行文档、4 条复合疑问、约 20 处编辑点全部一次成功零返工；并行编辑比串行省约一半往返轮次。
- 反模式：不先实查就写"已验证支持"；把未实测结论写成定性结论；为闭合疑问把"规程式检查点"夸大为"事件回调"。
- 判定顺序记忆：先实查→再映射→后动笔；先并行编辑→后 grep 验证→再摘要呈报。

## Applicability Boundaries

- 适用：设计/规格/机制类 Markdown 长文档的多条疑问修订，修订点互不重叠、以新增和增补为主。
- 不适用：需大范围编号顺延的重构式修订（应改用"从大到小顺序编辑"模式）；小规模单点修订（直接单次编辑即可，无需全套流程）。
- 前提：修订指令逐条编号且上游规格条款号稳定可引用。
- 与相邻经验分工：《标注式增量修订+grep 计数核验》（annotated-incremental-revision-grep-verify）管"用户补充标记式修订的统一标注落位与计数核验"；《打回理由逐条映射修订动作》（rejection-reasons-to-revision-actions-mapping）管"打回场景的修订动作固化与附录留痕"；本条管"多条疑问的疑问→落点→证据映射与实查三档呈现"——三者同为逐条修订纪律，按触发源（补充标记/打回/疑问）选型，"打标+grep 收尾核验"手段三篇通用。

## Evidence or Examples

- 实测（2026-11-08 会话，sdd_agent_refactor design.md v1→v2）：4 条疑问全部落点命中；实查项（事件通道 H3/H7 定性）依据运行规则文档取证后按三档写入；同文件一轮 8 个并行 edit 全部成功；收尾 grep "v2 新增"命中 8 处落点；版本头、门禁表、追溯表、风险表、目录树联动点均以指针方式增补。
- 实查示例：某机制实查定性为"规程式动作检查点，非文件监视/事件回调/轮询"，承载性结论成立但如实注明"派工直连路径属首次使用，挂后续验证轮实测"并同步更新风险条目——此为三档呈现的样板。
