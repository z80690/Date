# AI 零直改规则文件的权限豁免边界：人工修改建议清单模式与旧承载"解绑不删除"处置

## Scenario

项目裁决"规则文件（SKILL.md/.mdc 等一切规则文件）由人工最终修改，AI 仅提建议不直改"（用户裁决 U6-6），而新需求（审查门禁 P3C→Ruff 替换）字面目标含"更新相关配置：技能描述、规则约束、SDD 审查环节"——若逐字执行必触直改红线。单人协作、规格先行阶段，需要在 spec 中把"谁来改、改什么、旧文件怎么办"一次性定界，避免实施阶段踩线或需求空转。

## Key Signals

- 派工单含"用户已裁决基线"区，逐条列出"AI 零直改规则文件、只产人工修改建议清单"类裁决。
- 同一派工单的任务目标又含"更新相关配置/技能描述/规则约束"——裁决与目标字面冲突。
- 旧承载有明确文件路径（技能目录、脚本、外部底座），且用户明示"旧文件不删除"。

## Essence

AI 修改权限按**文件新旧二分**豁免，豁免边界本身就是可执行规则：

1. **既有规则文件 = 人工终改域**：AI 零直改，只产"人工修改建议清单"（逐文件逐条：文件路径 + 修改点 + 建议措辞），清单随 spec 交付。
2. **新建文件 = 新能力注册域**：新技能、报告、spec 产物属新资产，不受人工终改限制，AI 正常落盘。
3. **旧承载处置 = 解绑 + 冻结标注，物理保留**：删除与解绑是两个动作——解绑靠"新流程条款 + 新承载接管"实现（旧技能在规格中声明停用/不再作为某类流程的门禁），文件本体不删，保留可回退性与审计线索。

多数"更新规则约束"类需求可由**新建承载文件**实现语义更新，既有文件仅列清单——这是化解"目标与裁决冲突"的默认解法。

## Approach

1. **识别落点**：对需求中每项"更新/替换/解绑"动作，先定位其落点文件（既有 or 新建）。
2. **既有文件转清单**：落点为既有规则文件的动作，转化为人工修改建议清单条目（文件路径+定位段+建议措辞+理由），不落盘改动。
3. **新建文件直接写**：落点为新建承载（如独立新技能）的动作，正常落盘，并在 spec 中声明其"新能力注册"属性。
4. **旧承载写解绑条款**：规格条款显式写"解绑 + 冻结标注 + 物理保留"，禁删除；标注语义（停用原因、生效日期、替代承载指针）随条款落盘。
5. **清单可执行化**：建议清单条目须细到"改哪一段、改成什么"，人工终改者按条采纳即可，无需再读全文件。

## Faster Next Time

- 二分口诀："**旧文件出清单，新文件直接写**"。
- 遇"更新规则约束/技能描述"字样，第一问："语义更新能否由新建承载实现？"——能则既有文件降级为清单，冲突即消解。
- 反模式：以"需求要求更新"为由直改既有 SKILL.md/.mdc；把"解绑"执行成"删除"；建议清单只写"建议更新 XX 技能"（无路径无措辞）导致人工终改无从下手；新承载与旧承载职责边界未写清，形成双轨并存歧义。

## Applicability Boundaries

- 适用：有"AI 不直改规则文件"类裁决、规则变更需人工审批的项目；含旧机制退出但用户明示保留文件的需求。
- 不适用：用户明示授权 AI 直改的场景（如特批流程放行）；新建文件同样受人工终改限制的项目（此时建议清单范围扩大到全部落点）。
- 边界：豁免边界以用户裁决原文为准，"新能力注册豁免"是本次裁决的语义，非普遍公理——换项目时先确认裁决措辞。
