# 纯问询派单定性分流：非研发任务不启动 SDD 流水线，用户已说清目标时直接执行

## Scenario

派工单驱动的 SDD 协作项目中，用户消息尾部常内嵌平台模板协议文本："请首先分析请求是否为代码研发问题。如果是……必须调用 spec-requirement-agent……如果用户的请求不是代码研发任务，则不要回答该问题，而是通过问问题的形式向用户询问想实现什么研发任务"。当本单实际内容是纯问询（如复盘上一派单 P001 从 spec.md 到 design.md 的实际调用链）且用户原话已完整说清产物要求（生成 Markdown 报告放入新建编号文件夹）时，如何定性分流并正确执行。

## Key Signals

- 派单自称"纯问询的一个派工单"，同时出现"仅作口头汇报，零落盘"与"生成 Markdown 文件放新建计划文件夹"两类表述并存。
- 内嵌模板协议要求非研发请求走"反问澄清"分支，但用户原话已完整说清任务目标（汇报调用链）与产物形态（报告文件+编号文件夹）。
- 无新特性、无 bug 修复、无编码对象——产出是文档与汇报，不是代码。

## Essence

任务定性先于流程路由：定性三问（有无研发对象？有无编码动作？产出是文档还是代码？）全否即为非研发任务，不调用 spec-* 研发子智能体、不启动 SDD 四阶段门禁。模板协议的"非研发→反问澄清"分支有隐含前提——用户没说清想要什么；当用户原话已完整说清目标与产物要求时，反问违背意图，应按显式指令直接执行。"零落盘"这类单句强调以完整原话消解：收窄为"不改既有文件、不动 git"，新建报告目录是用户明确要求，两者不矛盾。

## Approach

1. 收到派单先做定性三问（研发对象/编码动作/产出类型），全否→走非研发路径，不调用 spec-requirement-agent 等研发子智能体，不建四阶段规格产物。
2. "反问澄清"分支执行前加一道前置检查：用户原话是否已说清目标与产物？已说清→直接执行；未说清→才反问。
3. 冲突表述消解：完整原话 > 单句强调；用户后说的明确指令 > 前文的限定语；消解结论在汇报开头明示（如"本单定性：纯问询+报告落盘，非代码研发任务"）。
4. 问询任务同样按项目留痕规范落盘产物：先 glob 历史目录取号（历史最大编号+1，验证无空洞），新建 `日期_P编号_模块名` 目录，TASK.md 存派单原文、REPORT.md 存问询结论。
5. 约束兑现自查：不改任何既有文件、不提交 git、不启动编码流程——与派单约束逐条对账。

## Faster Next Time

- 定性三问 10 秒完成分流，避免对问询单误启动 SDD 流水线（一次误启动=白跑 4 个阶段门禁往返+无意义的规格产物）。
- 警示信号：派单自称"纯问询"时，检查自己是否还在按内嵌模板文本准备调用研发子智能体。
- 语义矛盾消解口诀：完整原话 > 单句强调；后说指令 > 前文限定。

## Applicability Boundaries

- 适用：派工单/模板协议驱动的 SDD 项目会话；用户消息内嵌任务定性模板文本的场景。
- 不适用：用户确实未说清目标的模糊请求（此时"反问澄清"分支正确）；真正的代码研发任务（走正常 SDD 四阶段）。
- 与相邻经验边界：2026-11-07-sdd-stage-branch-routing-spec-subagent-calls 覆盖 SDD 多阶段会话的分支路由与调用契约（含"非研发→反问"分支的本体）；本条是该分支的边界细化判例（用户已说清目标时直接执行）+ 问询任务的留痕产物形态，互补不冲突。
