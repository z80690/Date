# 改造类需求的剃旧上新硬绑定：换绑前新逻辑仅验证态，放行门禁以剥离验收为硬前置

## Scenario

需求含"旧机制退出 + 新机制启用"双重语义（换框架、换流程、换注册机制），spec 阶段需要同时条款化"删旧"与"上新"。若两者只写成并列条款，典型事故是：新逻辑已放行干活而旧逻辑还挂着（旧路径残留），或旧逻辑剃净了但新逻辑没接上（能力真空），以及新旧并行无主次、谁都不算唯一事实。

## Key Signals

- 需求出现"去掉旧的/换成新的/不留路径/不挂旧脚本/只留新机制"类退出+替换表述。
- 旧机制有具体挂载点（脚本、钩子、注册表条目、配置引用），不剃会残留活路径。
- 测试要求含"新逻辑跑通 + 新旧对比"——对比测试天然需要旧逻辑暂存，存在"对比完忘剃"的时序缝隙。

## Essence

剃旧与上新不是两条并行任务，而是门禁级先后绑定关系，三条绑定规则缺一不可：

1. **换绑规则**：旧逻辑剥离验收通过后，才把新逻辑同批换绑为唯一主干；换绑前新逻辑一律标注"仅验证态"，可用于验证/对比测试，不得作为派工主干。
2. **不放行绑定**：新逻辑的放行门禁以"旧逻辑剥离验收"为硬前置（不剃老逻辑不放行新逻辑），门禁条目显式引用剥离验收条目编号。
3. **异常兜底**：换绑挂接失败预设分支（回退验证态+呈报），禁止半挂状态（新逻辑部分挂接、旧逻辑部分残留）收工。

本质是把"新旧切换"从一个动作拆成"验证态 → 剥离验收 → 换绑 → 放行"的受控状态机，用门禁引用关系锁死先后顺序。

## Approach

1. 分别条款化：spec 中"旧逻辑剥离"与"新逻辑启用"各写成独立验收条款，各给可判定标准（旧逻辑 grep 零命中/新逻辑注册实证）。
2. 增设换绑条款：剥离验收通过 → 同批换绑新逻辑为唯一主干；换绑动作与验收动作绑为原子步骤，禁止跨轮分离执行。
3. 放行门禁声明硬前置：新逻辑放行门禁条目引用剥离验收条目编号，未过即不放行，并在门禁全景表中可见。
4. 定义过渡态语义：换绑前新逻辑只允许验证/对比用途，明确"验证态≠可派工"，防止对比测试期间顺手用新逻辑干活。
5. 预设异常分支：换绑挂接失败 → 回退验证态并呈报，禁半挂收工。

## Faster Next Time

- 收口三问：旧逻辑删净了吗（grep 零命中）？新逻辑接上了吗（换绑实证）？放行门禁引到剥离验收了吗（编号引用）？
- 警惕信号：需求含对比测试要求时，旧逻辑必然要暂存——必须在 spec 里显式写"对比测试用的旧逻辑仅存于隔离副本，主干换绑不受其影响"，否则时序缝隙必出。
- 反模式：新旧逻辑并行无主次；放行门禁只验新逻辑自身；换绑与验收分两轮执行导致半挂态；为对比方便把旧逻辑留成常驻。

## Applicability Boundaries

- 适用：改造/替换/迁移类需求（旧机制退出 + 新机制启用），且项目有门禁式流程文化。
- 不适用：纯新增功能（无旧逻辑可剃，绑定规则空转）；有意灰度双跑的需求（旧逻辑保留是有意设计，此时绑定关系应改写为"主备切换门禁"而非剥离门禁）。
- 证据强度边界：本篇为设计层规则（spec 条款实证），换绑执行尚未实测，执行层证据待后续阶段补充。
