# 子代理落盘自述须主代理实测复验后才采信

## Scenario

主代理通过 Task 工具派发子代理（如 spec-requirement-agent / spec-design-agent 等文档产物型子代理）生成阶段文档，子代理在返回结果中自述"文件已生成落盘并验证通过，N 字节 / M 行"。该自述属于子代理的口头汇报，主代理若直接采信并向用户呈报，存在幻觉路径、空文件、内容不符而未被发现的风险。适用于"子代理产出文件型交付物"的所有场景。

## Key Signals

- 子代理结果中出现"已生成落盘并验证通过"或类似自述性结论；
- 自述给出具体量化值（字节数、行数）但无原始命令输出佐证；
- 主代理上下文中没有任何本会话直接产生的针对该文件的实测输出（读文件/列目录）。

## Essence

子代理的运行上下文与主代理隔离，其"验证"发生在子代理自身上下文内，主代理无法直接采信；且模型自述数值可能与磁盘实际状态偏差（幻觉、写失败、路径拼写差异）。唯一可靠判据是主代理用自己会话内的工具对磁盘做独立实测，并把实测值与自述值比对一致后才采信。这是"汇报 ≠ 事实"原则在主/子代理协作中的落点。

## Approach

1. 收到子代理落盘自述后，先取其声明的三要素：绝对路径、字节数（或行数）、关键内容特征（如文档标题/头部片段）。
2. 主代理用独立工具实测存在性与大小：PowerShell 下 `Get-Item <path> | Select-Object Name,Length`，或等价的文件读取工具。
3. 实测内容特征：读取文件头部（前 20~40 行）确认文档身份正确（标题、版本号、关键章节存在），排除"路径对但内容是空壳/错文件"。
4. 三项逐一比对自述值：路径一致、大小一致（允许 ±0，字节数是硬指标）、内容特征匹配。任一不符即判子代理交付失败，退回重做或主代理接手修复，不得向用户呈报自述值。
5. 比对全部一致后，才以"已落盘并通过复验"口径向用户呈报，摘要中引用实测值而非自述值。

## Faster Next Time

- 把"子代理自述 → 主代理实测复验"固化为流水线的标准检查点：任何 Task 型子代理返回文件交付物时，无条件执行 `Get-Item` + 头部读取两步，成本约一次工具调用，避免向用户呈报虚假交付。
- 警示信号：只要呈报文本里的数字来源于子代理文本而非自己会话内的命令输出，即视为未复验。
- 反模式：仅凭子代理说"验证通过"就宣布交付；用子代理上下文里的截图/输出当主代理证据。

## Applicability Boundaries

- 适用：主代理/子代理（Task 工具）分离的 Agent 平台通用模式；文档、配置、脚本等一切文件型交付物；平台无关。
- 适用：CodeArts Agent 类主/子代理协作场景（本经验实证平台）。
- 不适用：主代理自己直接写文件的场景（写后自验即可，无需此纪律）；子代理只返回分析结论不落盘的场景（改为要求结论附原始证据）。
- 局限：字节数一致只能证明"文件如实落盘"，不能证明内容质量合格；质量审查仍需主代理或用户阅审。
- 相邻经验边界：2026-11-07-subagent-delivery-spot-check-acceptance 处理交付物的内容级抽验（grep 关键条款落位、占位条款识别），本条处理存在级/身份级实测复验（字节数+头部身份三项比对）——完整验收先实测落盘（本条）再抽验内容（那条）；2026-11-07-write-receipt-not-proof-of-persistence 是"汇报≠事实"在主代理自身写盘场景的落点，本条是其向主/子协作场景的延伸。
