# 免运行判定框架挂载状态：三层只读核验 + 排除法定性挂载方式

## Scenario

派工单要求"核对底层框架是否已挂载，确认编码任务强制调用约束是否生效"，同时明确禁止执行任何真实编码。这类核查任务（挂载状态/生效性确认/环境体检）与编码任务、调试任务的区别在于：**结论必须可信，但取证手段受限**——不能靠实跑功能链路来验证，只能在只读前提下构建证据链。

## Key Signals

1. 派工单出现"核对/确认/核对状态"类动词且伴随"不执行编码/不写业务代码"约束——先按非研发任务定性（不启动 SDD 流水线），再进入核查流程。
2. 底层能力在工具层搜不到（`tool_search`/grep 框架名无命中）——这是"非 MCP 工具/非独立命令"的排除信号，而非"未挂载"的判定信号。
3. 单一证据源都只能证明局部：文档写了 ≠ 挂载了，脚本存在 ≠ 约束生效了，注册表标 true ≠ 运行时真的 enabled。

## Essence

**核查契约是分层的，先定层再取证**。"挂载态"核查的成立判据是"证据链完整 + 待命可触发"，不要求运行痕迹；这与"实现完成度"审计（必须有运行痕迹，仅文档一律降档"部分实现"）和"功能可用性"验收（必须黑盒样例实跑出检出）是三种不同契约。混用契约是最大误区：免运行核查任务里实跑功能属于违规，把"已挂载但未运行"判成"未实现"属于误判。

挂载态的取证结构是**三层交叉**，任何单层都不足以支撑结论：

| 层 | 证明什么 | 取证手段 |
|---|---|---|
| 规则层 | 约束条款存在且有原文出处 | 读公约/规则文件，摘条款原文与行号 |
| 注册表层 | 封装载体已注册且运行时可见 | 项目事实表（如技能状态文件）+ 运行时清单回读（如 listSkills）双源核对 |
| 物理层 | 底座资产真实存在 | 五项存在性核验：底座目录、核心产物、依赖集、规约/配置文件、封装脚本 |

## Approach

1. **任务定性前置**：核查类派工单先判"是否代码研发任务"，非研发则不进 SDD 流水线、不调规格子代理，直接执行核查。
2. **规则层取证**：读项目公约/规则文件，找到约束条款原文（如"编码必审未过不完工"），记录文件与行号；规则层无条款则约束不存在，无论技术层多完备，结论都只能是"已挂载但无强制约束"。
3. **注册表层双源核对**：读项目事实表（如 ProjectSkillStatus.txt）确认声明状态；再用运行时清单工具（listSkills）回读 enabled 状态。两源一致才采信；清单不覆盖该类实体时按枚举边界处理，"查不到 ≠ 未注册"。
4. **物理层五项存在性核验**：用单命令批量断言一次拿全（key:value 输出），五项为——底座根目录、核心产物目录/classes、依赖 jar 集、规约/配置文件、封装脚本（如 review-code.ps1）。任一项缺失即挂载不完整，逐项如实报告而非只给汇总。
5. **排除法定性挂载方式**：工具层搜索框架名无命中 → 排除 MCP/独立工具；规则文件中无框架名 → 排除常驻规则注入；在技能注册表命中 → 定性为"项目技能封装 + 事件触发式"。定性结果决定后续核查动作的触发时机预期。
6. **约束链完整性核验**：规则条款 → 封装技能的 SKILL.md 门禁语义（如 exit 0/4）→ 流程挂载点（如 SDD 执行步的审查环节），三级逐级核对。链上任何一环缺失，约束即不生效。
7. **边界如实声明**：结论必须区分"已挂载（待命）"与"已实际运行"。本次核查会话无编码动作、链路未触发属正常状态，写明"链路待命未触发"而非含糊其辞。

## Faster Next Time

- 核查清单模板：① 定性任务类型 ② 规则层摘条款原文 ③ 事实表+运行时清单双源核对 ④ 五项物理存在性批量断言 ⑤ 排除法定性挂载方式 ⑥ 约束链三级核对 ⑦ 区分"挂载/运行"写边界声明。全程只读，约 5 分钟内闭环。
- 警告信号：取证时发现自己想"跑一下看看"——立即停，这是把挂载态核查混同功能态验收的契约错位信号。
- 证据指针留痕：结论中每个"已确认"都附证据指针（文件路径+行号、工具回执、核验输出 key:value），供后续会话免重查直接引用。

## Applicability Boundaries

- 适用：任何"确认某框架/技能/能力是否已挂载、注册、约束是否生效"的免运行核查任务；适用于码道类技能注册机制（落盘即扫描 + ProjectSkillStatus + listSkills），方法结构平台通用。
- 不适用："能力是否真的能干活"的黑盒验收（需构造违规样例实跑，见 testing 类既有经验）；"改造是否完成"的实现度审计（需运行痕迹双侧比对）；"运行时注册验证"（MCP 等需新会话重载验证的实体不适用只读快照结论）。
- 前提约束：注册表/清单工具与事实表在本项目可见；若平台无运行时清单通道，注册表层退化为单源（事实表）+ 结论降级标注"单源证据"。

## Evidence or Examples

- 本次实证（P3C 挂载核查，2026-11-08）：规则层命中公约第 6 条"编码必审未过不完工"（`.codeartsdoer/rule/项目协作公约.mdc:6`）；注册表层 `ProjectSkillStatus.txt` 中 review-code=true 与 listSkills 运行时 enabled 双源一致；物理层五项核验全 PASS（refs_p3c_dir: True / pmd_classes: True / pmd_dep: 24 个 jar / ruleset: True / skill_script: True）；排除法：`tool_search "p3c"` 无命中、公约中无 P3C 字样 → 定性为项目技能 `review-code` 封装 + 事件触发式（非 MCP、非常驻规则）。
- 约束链实测：公约第 6 条 → `review-code/SKILL.md`（exit 0/4 门禁语义）→ SDD 执行步第 4 步审查环节必调；边界条款：仅 Java 变更强制，非 Java 变更须豁免语义标注留痕。
- 历史佐证：p3c-pmd 2.1.1 底座于 2026-11-07 通过 214/214 官方测试验收（在档既有经验），证明"挂载"结论可与"历史功能验收"证据互链但不相互替代。
