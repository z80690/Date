# 用户打断执行死循环的四段执行协议：停止路线+按清单回滚保留有效成果+按新方向重执行+收尾条件对齐

## Scenario

长会话中对某条技术路线（实例：Electron 应用便携化 + MSI 诊断）连续十余轮尝试未调通，且每轮失败后仍在同一路线内做变体重试（换启动方式/换解包工具/换日志参数），形成执行死循环。用户发出结构化打断指令：停止该路线、回滚本轮无效产物、切换到指定新方向（包管理器/便携 zip 渠道）、给出收尾条件。

## Key Signals

- 同一症状下连续 2-3 轮修复尝试**没有产生新的根因信息**（报错不变/失败点不变）——这是死循环的先行指标，出现即应自检换路，不等用户打断。
- 用户打断指令的典型结构四段齐备：①【停止 X】（点名违规路线）②【回滚垃圾产物/保留有效成果】③【新方向（具体渠道/方法）】④【收尾条件/底线】。
- 打断指令中出现"违规"定性（如"当前死磕 X 是违规"）——说明该路线已被用户否决，任何该路线上的进一步尝试（包括"备注式收尾"）都不再被接受。

## Essence

被打断的死循环处置是四段固定动作，与"平台工具禁用类 Doom Loop"（首结果采信+停止调用）不同：这里的核心是**路线级止损**——①立即停止被打断路线的一切调用（含变体与"再试一次"）；②按用户清单回滚，回滚对象=该路线产出的无效脚本/下载残留/失败现场，保留对象=用户明示或默示认可的有效成果（如已完成的目录归拢），边界模糊时以"用户指令是否点名保留"为准；③新方向严格执行用户指定渠道，不夹带旧路线的"顺手尝试"；④对齐收尾条件后立即转入执行，不为弃路写长篇诊断报告。

## Approach

1. 读到打断指令先解析四段：停止对象、回滚清单、新方向、收尾条件——四段各自成为待办项，缺一不可。
2. 停止：被打断路线不再发起任何调用（含诊断、验证、"确认一下"类变体）；已排队的该路线动作全部取消。
3. 回滚：逐项核对用户点名的无效产物（探测脚本/下载残留/失败目录）用删除工具清理；用户明示保留的成果（实例：根目录归拢）**明确豁免**并在汇报中列出"保留项"；删除前确认路径在授权范围内。
4. 重执行：按新方向指定的渠道/方法直接开干（实例：winget/scoop 装 Tor + 便携 zip 路线），新方向执行中如遇同类失败信号，按既定换路判据自行降级，不再等待第二轮打断。
5. 收尾：逐条对照打断指令的收尾条件输出结果（完成/未完成+原因），主动附上本轮死循环的教训归因（哪一步该早停），供后续自查。

## Faster Next Time

- 自查触发器：同一失败点连续第 3 次出现且报错无新信息 → 强制换路并显式声明"换路及理由"，不等用户打断。
- 回滚两分法：用户点名"垃圾/无效/回滚"的 → 删；用户点名"保留"或已获认可的阶段成果 → 留并在汇报列明——不确定的归属列入汇报请示，不擅自删。
- 打断指令=最高优先级路由：收到后第一个动作是解析四段结构，而不是对被打断路线做最后辩解或补救。
- 汇报格式对齐收尾条件逐条回应，教训归因一段带过（用户要结论不要忏悔录）。

## Applicability Boundaries

- 适用：任何执行路线陷入重复失败后被打断的会话；用户以【打断+重定向】句式下发指令的场景。
- 不适用：平台侧工具禁用类 Doom Loop（走关联经验 doom-loop-triggered-recovery-protocol 的首结果采信协议，无回滚与新方向环节）；用户仅表达不满但未给新方向时（此时先确认新方向再执行，勿自选路线）。
- 边界：本协议管"被打断后怎么执行"；"如何在被打断前自我止损"靠换路判据（连续无增量即换）；回滚操作受平台删除工具能力与授权范围约束，超范围项如实呈报。
