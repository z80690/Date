# 超单次读取上限的上游大文档须 offset 分段续读至行数覆盖自证，尾部截断即漏联动点

## Scenario

SDD 流水线中"动笔前必须完整读取全部上游产物"的场景：派工单要求先读完 spec.md 与 design.md 全文再生成下游产物（如 tasks.md）。上游文档体积不受控——design 类文档常含裁决矩阵、接口契约、对象模型、EARS 追溯表、设计自检等章节，轻易超过 50KB。单次读取工具对超大文件有约 50KB 的截断上限，超出部分**静默丢弃、无报错**，执行者极易在只读到前半的情况下误判"已读完全文"。

## Key Signals

- 体积信号：列目录或上游派工单显示文件字节数超 50KB（如 54KB+），即触发分段策略，不等截断发生后补救。
- 派工单预警信号：上游指令明确写"约 XXKB——超 50KB 单次读取上限，必须用 offset 分段续读至全文读完，漏读尾部=漏联动点"，说明上游已知该文件超限。
- 结构信号：SDD design/spec 类文档的尾部常放 EARS 追溯表、对象关系与销毁策略、设计自检等**联动点密集章节**——恰是最不能漏的部分。

## Essence

读取截断是静默失败：工具不报错、不提示剩余量，截断点之后的章节直接消失在上下文里。对"下游产物要承接上游全部条款"的任务，漏读尾部等于漏掉承接义务，且在评审期才暴露、返工成本最高。因此"读完全文"不能靠感觉判定，必须用**行数覆盖自证**闭环：先探测总行数或从分页返回值确认截断点，再以 offset 续读到文末，最后自报"全文 X 行已覆盖（1-N 行）"作为读毕证据。

## Approach

1. **预判体积**：动笔前列目录看目标文件字节数，或直接采信派工单标注的体积；>50KB 即列入分段续读计划，禁止单次直读。
2. **首轮读取**：正常发起第一次 read（不指定 offset 或从 1 开始），从返回内容确认实际读到的截断行号（返回截断处即第一段末行）。
3. **offset 续读至文末**：以上一段末行号+1 为 offset 发起续读，循环直至返回"文件末尾"标记，段间不断链。
4. **行数覆盖自证**：读毕后明确自报覆盖证据（如"spec.md 358 行 + design.md 617 行，已读 1-400 与 401-617，双全文覆盖"），再宣布进入下一步。
5. **联动点回扫**：续读补上的尾部章节（追溯表/自检节）单独核对是否被下游产物结构承接，不留"读了但没用上"的悬空输入。

## Faster Next Time

- 动笔前一句话自检："本轮要读的上游文件里有没有 >50KB 的？"有则先规划分段，不要边读边发现。
- 读取结果里出现行号远小于文件实际行数（或内容止于中段章节）即静默截断征兆，立即续读，不要当"文件本来就到这"。
- ROI：分段续读仅多一轮工具调用；漏读尾部的最坏代价是下游任务清单缺条款映射、执行期回炉重写。
- 反模式：用"文件很长我大概看完了"代替行数自证；只补读尾部却不把尾部条款映射进产物；对多个超限文件只分段读其一。

## Applicability Boundaries

- 适用：任何"下游产物承接上游全文条款"的读取场景——SDD 各阶段上游产物、规则/机制文档、评审材料；文件越大、尾部章节含追溯/自检内容的收益越高。
- 不适用：小文件（<50KB）单次直读即可；只做主题检索的 grep/定位式读取（本就允许局部命中）；行数上限数值随平台版本可能浮动，以当次实际截断行为为准，不硬编码 50KB。
- 相邻经验划界：`workflow/2026-11-07-long-design-doc-chunked-write-structure-verify` 管"写"方向的分块落盘与结构校验，本条管"读"方向的分段续读与覆盖自证；`workflow/2026-11-06-spec-to-tasks-decomposition-pipeline` 的 Approach 第 1 步"完整读取全部上游文档"是本条的上位要求，本条是其在大文件场景的执行细则。
