# 跨会话接手规划前先磁盘实查刷新环境基线，已完成项标待验收而非重排

## Scenario

Agent 接手跨会话/多阶段任务（典型如 SDD 的 tasks 阶段承接前面会话的 spec/design 产物）时，派工单或上游说明中描述的环境状态可能已滞后：某依赖此前克隆失败、后来在另一会话已修复；某规则草稿已获批生效。若按旧基线规划，会把已完成工作重排一遍，或漏掉真正的剩余衔接项。本次触发场景：派工单明确声明"已更新环境事实（当日实查）"，其中一项此前反复失败的外部依赖已完成构建并通过全部测试。

## Key Signals

- 派工单/任务描述中出现"已更新环境事实""实查结果"字样，且内容与更早期记录矛盾（如早期"克隆 3 次失败"与现在"构建成功"并存）。
- 旧计划中存在依赖该环境项的任务，其前提条件已被外部会话改变。
- 任务描述直接给出处置指令（"对应任务须标注已完成待验收"），说明基线漂移已被上游确认，只需要传导。

## Essence

Agent 的计划只有锚定在"磁盘现状"而非"历史记录"上才不会与现实脱节；环境事实刷新后，已完成工作在新计划中的正确形态是"已完成待验收+剩余衔接项"，而不是删除或重做。Agent 运行环境与人类工作流的关键差异在于：Agent 的"知识"默认来自注入文本，而唯一权威是文件系统，两者不一致时必须以实查收敛。

## Approach

1. **识别基线漂移信号**：读到与早期记录矛盾的环境描述时，先停下，把矛盾项列成清单。
2. **磁盘实查验证**：对矛盾项逐一到磁盘核验（目录是否存在、构建产物是否存在、版本/状态文件内容），不靠转述文本下结论。
3. **刷新任务基线**：实查确认已完成的子任务，在新计划中标注"已完成待验收"，并只登记剩余衔接项（如本例剩余为"检查点挂接+注册表登记"），禁止重排或重做已完成部分。
4. **传导到下游产物**：刷新后的基线必须体现在规划产物（任务清单、计划文档）中，并注明实查日期，使后续阶段读到的是新基线。
5. **如实呈报变化**：在向用户呈报的摘要中前置说明基线变化及其对任务序列的影响，供裁决。

## Faster Next Time

- 接手任何跨会话规划任务的第一步固定为"基线核对"：派工单环境事实 → 磁盘实查 → 矛盾清单 → 基线刷新，形成固定四步。
- 警告信号：计划里出现"拉取/构建/安装 XX"类任务时，先查该依赖是否已就绪，再决定是保留任务还是降级为衔接项。
- ROI：避免对已构建通过（本次 214/214 测试全绿）的依赖重走一次克隆-构建流程；剩余工作量从整项任务缩小为 2 个衔接项。

## Applicability Boundaries

- 适用：跨会话、多阶段、有前置环境依赖的规划/执行任务；上游明确提供环境事实或计划内容与记忆/文档出现矛盾时。通用 Agent 模式，不限特定平台。
- 不适用：单会话内连续执行、环境无外部变更可能的小任务（实查是纯开销）；无文件系统访问权限的纯咨询场景。
- 反模式：只写"Agent 应注意核实环境"而不给四步判断序列；把本应归入 build-env 的构建故障误分类为本类经验（本条针对的是"规划基线过时"这一操作问题，不是环境故障本身）。
- 相邻经验边界：workflow/2026-11-06-memory-staleness-crosscheck-arbitration 管"记忆层过时"的三层仲裁（规则>最新知识库>记忆>推断），本条管"规划基线过时"的磁盘实查刷新——共同精神都是注入文本让位于磁盘现状，但处置对象与动作序列不同，不宜混用。

## Evidence or Examples

- 本例派工单声明：某 PMD 检测框架依赖已克隆并构建成功（Maven 构建 BUILD SUCCESS、官方测试 214/214 全绿），对应旧任务标注"已完成待验收"，剩余衔接项为编码检查点挂接与注册表登记；另有 10 条项目规则已从"草稿"变为"已生效"，对应任务性质同步改为"已生效+追认留痕"。
- 任务清单生成后 12 个主任务中相应任务均按新基线标注（来源：会话轨迹内嵌记录；"实查四步法"为对轨迹中处置方式的归纳，实查动作发生在上游会话，本会话证据为采纳与传导记录）。
