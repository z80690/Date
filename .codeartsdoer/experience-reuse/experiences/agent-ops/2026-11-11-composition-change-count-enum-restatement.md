# 构成性变更的篇数与枚举双轨联动重述：与状态刷新"数字不写入"判据相反

## Scenario

以只读 subagent 身份接收知识库索引型 Wiki 文档（描述"笔记层承载什么/如何组织"的索引型文档）的小节级修订派工：变更源是知识库 notes/ 目录**新增 2 篇工作笔记**（文件构成变化，非状态事实表刷新），受影响小节为概述与架构设计，两者正文均承载全局统计口径与构成枚举。派工单预置"主 Agent 已实读确认的现状事实"清单（文件总数与目录构成明细、新笔记名称/行数/定位、旧口径过期声明与新旧映射），并显式声明"写正文必须与此一致，禁止自行编造篇数或条目名"。任务边界：只输出结构化 patch JSON，禁止写文件。

## Key Signals

- 概述正文含"共 N 篇""沉淀四类学习成果与 N 篇工作笔记"式统计口径与分组枚举；架构设计正文含三层篇数分布与各层成员枚举——统计数字与枚举是这类索引型文档的**核心承载物**而非附注。
- 变更类型是文件 added（构成变化），不是状态表的日期/哈希/进度值刷新——"有数字变化"不等于"状态刷新派工"。
- 派工单单列"主 Agent 已实读确认的现状事实（权威结论）"：总数、目录构成、每个新条目的名称与定位，并附新旧口径映射（旧 20 篇/笔记 2 篇 → 新 22 篇/笔记 4 篇，旧 2 篇点名、新增 2 篇点名）与禁编造声明。

## Essence

**变更源分类决定数字写入结论，两类"数字"写入规则相反。** 构成性变更（新增/删除文档文件）改变的是索引型文档的核心承载物——统计口径与构成枚举，必须双轨联动重述（所有旧数字同步换算 + 新条目嵌入既有分组结构并点名），不能套用状态刷新场景"条数等状态值一律不写入简介正文"的结论。分界判据：回答"库里有什么、有多少"的**构成口径**是索引型文档的固有正文内容，构成变化必须跟随重写；回答"进展到哪了"的**状态值**（任务号、门禁进度、核验日期）才禁写入。subagent 对全局构成无法自行核验时，派工单预置的权威事实清单是唯一写入依据——禁止推算篇数、禁止杜撰条目名。

## Approach

1. **先判变更源类型**：对每轮修订派工先问"变更文件是知识库文件构成变化（added/deleted），还是状态事实表值刷新"——构成变更 → 走本条双轨联动；状态刷新 → 走行级再分层（见 fact-refresh-row-stratification-bracket-revision）。
2. **以权威事实清单为唯一写入依据**：派工单预置的实读确认清单（总数、目录构成、新条目名称/行数/定位）逐项对照采用；清单给出新旧口径映射就按映射执行，不自行推算、不编造条目名。
3. **数字与枚举双轨联动**：扫描小节正文中所有旧统计口径出现位置并同步换算（如 20→22 篇、笔记 2→4 篇）；新条目不是追加在枚举尾部，而是嵌入既有分组并点名（本例：学习成果 4 篇保持不变，工作笔记 2→4 且列出两篇新笔记名）。
4. **两层面分别重述**：概述按"承载什么/沉淀什么成果"的职责视角重述；架构设计按"分层组织 + 各层篇数分布 + 各层成员"的技术视角重述——同一构成事实两种表述，不复制同一句式。
5. **删旧不留残句**：旧分组计数、旧枚举成员整体替换为新口径，不做半句修补；改完逐项核对篇数、分组计数、条目名与权威清单完全一致后才输出 patch。

## Faster Next Time

- 判定口诀：见到数字变化先问"构成还是状态"——构成变更 → 数字与枚举必须联动重述；状态刷新 → 数字禁写入正文。
- 派工单要素扩展：在"变更文件最新全文 + 口径变化要点 + 受影响小节当前内容 + 符号骨架声明"四要素之外，构成变更场景追加第五要素——**主 Agent 实读确认的现状事实清单（新旧口径映射 + 禁编造声明）**，让 subagent 零实读也能保证事实一致。
- 警惕信号：小节正文出现"沉淀 N 篇""共 N 篇"而 patch 未换算数字、或新条目只追加不嵌入分组——输出前用权威清单逐项核对篇数/分组计数/条目名三项。

## Applicability Boundaries

- 适用：索引型/简介类 Wiki 文档（概述、架构设计小节）因知识库**文件构成变化**（新增/删除文档）触发的修订派工；只读 subagent patch JSON 模式；派工单预置权威事实清单的判定验证式执行。
- 不适用：状态事实表值刷新（走行级再分层，纯值不写入）；领域条目口径本身的大改版（走节级分流判定）；含代码符号的源码文件（用符号骨架而非行号锚点）；授权直改的普通文档编辑。
- 与相邻经验分工：`fact-refresh-row-stratification-bracket-revision` 与本条构成**配对对照**——同一"数字"在两种变更源下写入结论相反，选型以变更源类型为准；`wiki-section-tiered-revision-judgment-contract` 管通用节级分流（改与不改），本条管"已判 replace 之后怎么写"的口径映射细则；`wiki-section-revision-patch-json-mode` 管建议-合并分离与实读核实口径；`dispatch-brief-embedded-fact-pack` 管主→子事实包迁移的通用模式，本条是其"权威现状清单"要素在 Wiki 构成变更场景的实例化（追加新旧映射与禁编造声明）。
- 证据等级：单次实战闭环（2 小节判定 + 双轨联动重述 + patch JSON 与权威事实逐项一致）；合并应用结果在本 trace 之外，判据在多轮构成变更下的稳定性待复用检验。
