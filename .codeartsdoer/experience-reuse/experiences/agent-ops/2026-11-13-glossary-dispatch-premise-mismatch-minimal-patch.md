# 派工单预判是待验证假设：实现层强化不构成术语变更判零修订，声称存在的引用结构实读缺失时输出空集不虚构

## Scenario

以只读修订 subagent 身份接收领域术语表类 Wiki 文档的增量修订派工：变更源是一批源码实现层强化（裁决判定纯函数化、抓包会话事件驱动化、框架就绪常量更新）加状态事实表的值刷新。派工单内嵌两处预判：其一，判定倾向 line_number_only（正文不改仅刷引用）；其二，断言"文档内每节后有代码引用行（code_refs）"，要求按最新源码刷新行号。硬约束：只输出结构化 patch JSON，不写文件。

## Key Signals

- 派工单的预判是"倾向性判断"而非事实：明确写了"大概率 line_number_only，仅当业务概念本身变化才允许 replace_content"——预判正确也需要独立验证才能作为结论。
- 派工单断言的结构特征与实读不符：文档全文 71 行，各小节之后并无任何代码引用行，"每节后有 code_refs"不存在。
- 变更形态全部是实现层：函数签名重构为纯函数、执行时机改为事件驱动、常量表更新——没有任何一行改变术语定义所承载的业务语义。
- 若盲从派工单模板，最可能的产出是"为满足格式预期而虚构 code_refs 行号"。

## Essence

派工单内的预判与结构描述都是**待验证假设**，不是事实；两者失准时的处置方向不同但原则同一——**以实读为准，做最小输出**：

1. **实现层强化 ≠ 业务含义变化**。判定动作是把变更语义与文档已有术语定义逐条对照：若术语定义已覆盖变更内容（如"三类结论""会话连续不间断""未就绪如实拒绝"均已写在定义里），实现层强化只是定义的代码印证，正文不动 → line_number_only。这与"状态值刷新 ≠ 领域概念变更"构成零修订的第二种触发源：前者变更源是状态文档的值刷新，本条变更源是源码实现方式的演进。
2. **声称存在的引用结构实读缺失时，输出空集而非虚构**。code_refs 的存在性同样以实读为准：文档没有引用行就输出空数组，不为满足派工单预期编造"看似合理"的行号——错误引用会随 patch 合并进入溯源链固化传播，缺引用无害而错引用有毒。

## Approach

1. **实读全文先于一切判定**：把目标文档完整读一遍，建立"实际结构"基线；派工单对文档结构的任何描述（"每节后有引用行""小节格式为…"）只当线索不当事实。
2. **逐术语对照变更语义**：把每个变更点（重构/事件化/常量更新/状态值）与术语定义逐条对照，问"定义文本是否已表达这一变更的业务语义"；已覆盖 → 排除并留排除理由；真有新业务概念或定义语义改变 → 才允许 replace_content。
3. **变更源分类定流程**：状态值刷新 → 走状态刷新零修订判据；实现层强化 → 走本条逐术语对照；概念口径变化 → 走同层面分流判定契约。
4. **code_refs 按实读定存在性**：文档有引用行 → 逐条实读源文件刷新行号；文档没有 → code_refs 输出空数组，并在执行记录里注明"派工单预判与实读不符"。
5. **输出最小合法 patch**：line_number_only + new_content 为 JSON null（非 "null" 字符串）+ 按实读结论的 code_refs；零修订结论须有逐条排除记录支撑。

## Faster Next Time

- 判定口诀：变更行是"实现方式" → 逐术语对照定义 → 定义已覆盖即零修订；派工单说"有引用行" → 实读说了算 → 没有就空集。
- 一致性快查：在术语定义里找变更点的业务措辞（三类结论/连续不间断/如实拒绝），找得到就是"定义已覆盖"的直接证据，一轮目扫即可完成。
- ROI：一轮全文实读 + 一轮逐术语对照即可闭环；盲从派工单的两种失败方向（无谓重写正文、虚构引用行号）的修正成本都远高于实读成本。
- 反模式：把派工单的预判当结论照抄（这次预判对了没验证，下次预判错了也会照抄）；为 patch"看起来完整"补造引用；把代码实现细节（函数名/常量名）当业务术语写进定义。

## Applicability Boundaries

- 适用：定义/术语/概念类 Wiki 文档的只读 subagent 修订派工；变更源为源码实现层演进（重构、驱动方式改变、常量表更新）；一切"派工单提供预判 + 执行方须独立核实"的编排链路。
- 不适用：业务概念本身增删改（走同层面分流判定，replace_content）；变更源为状态事实表值刷新（走状态刷新零修订判据）；文档确有引用行且行号失准的场景（本条只管存在性判定，不管行号刷新）。
- 与相邻经验分工：`2026-11-09-glossary-status-refresh-zero-revision-criterion` 管状态值刷新型零修订（变更源=事实表），本条管实现层强化型零修订（变更源=源码），并把"引用结构存在性实读"补入同一处置框架；`2026-11-09-subagent-patch-code-refs-baseline-fallback` 管引用集"多退"（产出多于基线），本条管"缺不补"（基线缺失不虚构），两者合成引用集校验的"多退少补"闭环；`2026-11-08-wiki-section-revision-patch-json-mode` 管建议-合并分离与落盘契约，是本条输出形态的上游框架。
- 证据等级：单次实战闭环（正例固化：预判失准两形态均以实读裁决、终态 patch 结构合规）；无踩坑修复对照，判据稳定性待同类场景复用检验。
