# 声明"事件驱动复用既有通道"前必做承载性实查：触发形态定性+事件到检查位语义映射+投递边界如实报告

## Scenario

设计文档（design.md）已承诺"复用既有事件通道承载新流程事件、零新增通道、零定时器"，用户在审阅时追问："底层是否真支持？事件留痕机制如何落地？"此时通道清单盘点（设计前核查）已做过，但**承载性结论仍不能直接照抄**——必须实查底层钩子的真实触发形态，并把新事件的每一环映射到既有检查位的语义上，同时如实报告投递边界。这是通道盘点（列出平台支持什么）之后的下游一步：证明"我的事件序列在既有通道上真的走得通"。

## Key Signals

- 设计文档出现"复用 H3/H7""零新增通道""无定时器"类承诺，但文中无底层触发形态的实查证据（文件路径+机制描述）。
- 钩子名称（如 H3/H7）在多份文档中流转，名称一致≠机制清楚——可能只是"动作检查点规程"的别名，而非文件监视/事件回调/轮询定时器。
- 用户疑问聚焦"是启动时全量读还是走到哪步读哪步""是否真支持零新增通道"——凡设计声明与底层机制之间没有实查桥接，必被追问。

## Essence

承载性判定三步走，缺一则声明不可信：

1. **触发形态定性**：实读运行规则/钩子定义节/钩子挂载配置，把每个依赖的钩子定性为四类之一——文件监视 / 事件回调 / 规程式动作检查点 / 轮询定时器。定性结论必须附文件路径与机制描述，不凭名称推断。
2. **事件→检查位语义映射**：把新流程的每个事件逐一映射到既有检查位的语义上（如"事件流水属知识库写动作→落写前检查位；置信度刷事实表属事实变更→落变更后检查位"），全部映射成功才得出"零新增通道、零定时器"结论；映射不上的如实给事件式替代方案（仍禁自建定时任务）。
3. **投递边界如实报告**：规程式动作检查点**不是推送总线**——"唤醒"的物理载体是平台 subagent 派工（先流水记行→后派工），事件直连派工路径若属首次使用，须声明由后续验证轮实测，而不是含糊带过。

## Approach

1. 实读底层定义：运行规则中的通道结构节（如"3 类通道：平台原生/动作检查点/迁移守卫"）、机制文档的钩子定义溯源节、钩子挂载相关配置文件——三者交叉确认，以运行时规则为准。
2. 逐钩子定性并写证据表：钩子名→通道归类→真实触发机制（原文摘录）→是否定时器（核对禁用核验记录）。
3. 做语义映射表：新事件清单逐条→对应检查位→语义是否吻合→吻合则"可承载"，不吻合则给事件式替代。
4. 写承载性结论段：定性结论+映射结果+零新增/零定时器声明+投递边界如实段（"非推送总线，唤醒=派工动作，首次使用路径待实测"）。
5. 把边界声明同步进风险表（风险项=事件直连派工首次使用），供实施阶段核销。

## Faster Next Time

- 固定三问自查："钩子的真实触发形态是什么（附文件证据）？我的每个事件映射到哪个检查位语义？唤醒的物理载体是谁？"——三问答不全就补实查，不交付承载性结论。
- 纪律钩子/检查点别名体系下，名称流转多轮后机制易被"以名取义"——凡引用钩子做承载声明，一律回到运行时规则原文核对，不信名称、不信记忆、不信早期盘点结论。
- "零定时器"结论要用既有核验记录（定时任务禁用核验）作旁证，并指明唯一的既有定时性兜底（如反思窗口）"非触发主体"。

## Applicability Boundaries

- 适用：设计/spec 层声明复用既有事件通道、事件钩子存在别名体系或规程式检查点、平台无文件 watcher/webhook 的场景（码道 CodeArts Agent 实证）。
- 不适用：平台真有原生监听/回调能力时（直接用原生通道，无需语义映射）；全新搭建事件系统而非复用既有通道时（走通道盘点经验）。
- 边界：本方法只解决"设计层承载性声明可信"，不替代实施阶段的事件链路实测；映射成功≠投递路径已被运行验证。
