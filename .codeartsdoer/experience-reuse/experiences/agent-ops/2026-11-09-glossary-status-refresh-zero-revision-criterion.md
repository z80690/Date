# 事实源状态值刷新 ≠ 领域概念变更：术语表类小节逐条比对确认零修订，状态值禁入术语表

## Scenario

以只读修订 subagent 身份接收 Wiki 术语表（领域概念定义类文档）小节级修订派工：源变更文件不是概念口径文档，而是项目的"状态事实源"文档（单一事实源状态跟踪表）。变更内容为状态值刷新——提交历史、核验日期、机制状态、定时任务 ID、交付物路径、特性进度门禁、环境事实等，无任何领域概念定义的增删改。任务边界与常规修订派工一致：只做判定并输出结构化 patch JSON，禁止写入任何文件。

## Key Signals

- 变更文件的行级变化全部是"值刷新"形态：日期、提交哈希、ID（任务号/定时任务号）、状态枚举值、进度标记、核验记录——没有任何一行是"概念定义文本"的增删改。
- 派工单已内嵌判定预判：列出疑似相关的少数术语并给出"为何无需修订"的逐条排除理由（如术语定义与事实源导语/机制行逐字一致），subagent 的职责是验证预判而非重新发明判定。
- 术语表自带写法规范禁令：术语定义面向业务领域而非代码实现，禁止把代码枚举值/常量值/类名/内部状态值作为业务术语。
- 派工单给出候选 code_refs 行号集合，行号是否仍准确需实读源文件核对。

## Essence

**状态值刷新 ≠ 领域概念变更**。术语表类小节的正文只承载领域概念定义，而状态跟踪文档的刷新（日期、ID、版本、进度、核验记录）是项目状态跟踪/工具事实，不是领域概念——它既不触发已有术语定义的修订，也不得据以新增术语。因此判定动作从"分流改写"降级为"逐条比对确认零修订"：把变更内容与每个术语定义对照，疑似相关者逐条排除并留排除理由，结论倾向 `line_number_only`（`new_content` 为 null，仅核对 code_refs）。关键约束：这个"不改"必须以逐条排除过程为依据，而非默认跳过——排除记录本身就是"零修订结论"的可追溯证据。

## Approach

1. **先分类变更内容**：逐行看变更文件，判断变更属于哪类——概念定义/口径文本变化 → 走节级分流判定契约（同层面才改正文）；日期/ID/状态值/进度等值刷新 → 进入本条的零修订确认流程。
2. **逐条比对排除**：将变更内容与术语表中每个术语定义对照；对疑似相关者（定义文本引用了状态文档的导语、机制、顺序、条数等），逐字比对定义文本与源文件当前行——一致即排除并记录排除理由（如"定义与事实表第 N 行表述一致"）。
3. **新增术语把关**：变更中出现的一切新状态值（任务号、定时任务 ID、机制通道明细、进度门禁、工具版本）一律不得入术语表——它们是状态跟踪/工具事实，不满足"面向业务领域"的术语准入标准。
4. **code_refs 行号实读核对**：即使候选行号来自派工单，也逐一实读源文件确认行号仍指向所述内容；准确的维持原行号，未变更文档的引用不动。
5. **输出零修订 patch**：`action=line_number_only`、`new_content` 为 null、`code_refs` 为核对后的行号集合；排除理由与核对结论保留在执行过程记录中备查。

## Faster Next Time

- 判定口诀：变更行是"日期/ID/状态值" → 状态刷新 → 只确认不改写；变更行是"概念定义/口径文本" → 按分流契约走同层面判定。
- 警惕信号：术语定义与状态跟踪文档存在结构性依赖（如某术语的定义直接复述状态文档导语）时，不要直觉判"相关要改"——先逐字比对，定义文本与源行逐字一致就是排除，一致本身即证据。
- 排除记录即证据：逐条排除的理由要能回答"为什么 13 条全部不改"，零修订结论没有排除记录支撑就不成立。
- 行号核对成本极低（一轮实读）而收益直接：派工单候选行号若已失准，错误的 code_refs 会随 patch 一路带到合并与下游校验，返工成本高一个数量级。

## Applicability Boundaries

- 适用：术语表/领域概念/分类定义类 Wiki 小节，源变更来自状态跟踪文档（事实表、索引、进度台账等）的值刷新；派工单预置判定预判与候选行号的只读 subagent 场景。
- 不适用：领域概念口径本身变化（枚举增删、定义改写——走 wiki-section-tiered-revision-judgment-contract 的同层面分流）；含代码符号的源码文件（用符号骨架定位）；条目增删导致行数位移的场景（锚点需重新映射）。
- 与相邻经验分工：`wiki-section-tiered-revision-judgment-contract` 管"改与不改"的通用分流框架与判定预判式派工，本条是其领域特化——术语表类小节在状态值刷新场景下的零修订判据与新增术语禁令；`wiki-section-revision-patch-json-mode` 管建议-合并分离与落盘契约；`subagent-patch-field-drift-silent-content-loss` 管 patch 产出到脚本消费的字段归一校验。
- 与配对经验分工：`fact-refresh-row-stratification-bracket-revision` 与本条构成同源配对（同一状态事实表刷新源、同一轮派工批次）——那条管简介类/模块简介小节（正文承载机制结构描述，结论可为括注级增量 replace），本条管术语表类小节（正文承载领域概念定义，结论为零修订）；选型以正文承载物为准，先分清文档类型再套用对应判据，不要把"全零修订"或"括注级增量"任一结论跨文档类型照搬。
- 证据等级：单次实战闭环（13 个术语逐条比对、3 个疑似相关逐条排除、7 条 code_refs 实读核对、patch JSON 结构合规）；判据在多次"状态刷新触发术语表派工"场景下的稳定性待复用检验。
