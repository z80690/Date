# ST2 考核作答（执行代理，2026-11-07，50/50 全答）

## A 组：Agent 架构与分层

**A1** 核心动因：真实智能体任务的环境状态无法被完全观测（工具反馈滞后、环境动态变化、不可见状态），单步 MDP 的"全观测+单步决策"假设失效，必须用 POMDP 刻画时间延展+部分可观察。直接影响：既然状态不可全观测，agent 必须维护"信念状态"——记忆模块就是信念状态的载体，负责存储历史观测、压缩为可用上下文，并在决策时检索；没有记忆，部分可观测下每次决策都退化为盲猜。
**A2** 关系：规划是"面向未来状态的行动序列安排"（先想后做，产出计划），推理是"从已知信息推导结论"（如 ReAct 的思考步、因果推断）。区别：规划输出的是行动计划且显式考虑时序与依赖；推理输出的是判断/结论，不必然面向行动。不能相互替代：无规划的推理是"边想边撞"（短任务可行，长程任务迷失）；无推理的规划是"空转排期"（计划缺乏依据、无法纠偏）。二者是互补闭环：推理为规划供证据，规划为推理定目标。
**A3** 优先强化记忆模块。论证：POMDP 下环境不完整+延迟反馈，意味着单步观测信息量不足以支撑决策，agent 必须靠记忆保存历史观测（补全"部分"）、跨步积累信念（对冲"延迟"）。规划与工具依赖记忆提供的世界状态才能正确工作——没有记忆，规划在错误信念上展开、工具结果无法与前序动作关联。所以记忆是该场景的不可省略底座。
**A4** P2 的模块化子系统：认知模块（推理/规划）、感知模块（输入理解）、操作模块（行动执行）、记忆/世界模型、奖励处理、目标与情绪等价物。模块化优势：①可独立演进——替换记忆实现（如换向量库）不牵动整体；②可定位故障与审计——能力边界清晰，出错可归因到模块（单体大模型黑盒不可归因）；③上下文与成本可控——模块只加载所需知识。
**A5** 可维护性：巨型提示词是隐式耦合——改一处措辞可能破坏另一能力的行为（无回归边界）；模块化拆分后每个模块有独立契约（输入/输出/验收），可单独测试、单独回滚。能力演进：新能力（如加感知）在单体里意味着重写整个模板并回归全部行为；模块化下新增模块+注册即可，旧模块零改动——这正是本项目注册表"挂载不侵入"的设计依据。
**A6** 本质区别：参数级自进化改"模型权重"（训练/微调，改变模型本身，需数据管线+算力+回归评估）；经验级自进化改"模型之外的状态"（记忆条目、工作流、技能文件，模型不动）。落地成本：经验级只需读写外部存储+归纳逻辑，无需 GPU 训练、无需处理灾难性遗忘，可即时生效也可即时回滚（删条目）——本单的经验库与学习成果条目就是经验级进化的落地。
**A7** 三条判定标准：①与目标任务域的观测/动作空间匹配（网站训练选浏览器环境而非纯文本沙箱）——空间不匹配则训练信号无迁移价值；②反馈信号可程序化验证（可自动判分/判状态）——无法验证则 RL 信号缺失；③可复现+可重置（同一起点重放）——不可复现的实验结果不可信。这三条对应 RL 三要素：状态转移、奖励、可重复性。
**A8** 分层方案：可直接执行=只读操作（读文件、查询、列表）；需确认后执行=副作用可逆操作（写文件、创建条目——留痕+事后可撤销）；必须沙箱隔离=高危不可逆或外部影响操作（shell 执行、网络请求、删除）。依据：爆炸半径（blast radius）——只读无爆炸半径放行；可逆写有边界爆炸半径加确认；不可逆/跨边界操作必须隔离引爆。这与本项目"删除须用户批准+沙箱执行"纪律一致。
**A9** GUI 场景感知：输入=像素/截图/DOM 树/控件树（多模态），输出=结构化界面状态（元素位置、可交互性、文本内容）。本质差异：文本对话 agent 的感知=用户消息本身（已结构化）；GUI agent 感知需从原始信号中**结构化提取**（哪些是按钮、哪些可点），存在感知失真风险（OCR 误读、DOM 动态变化），且感知结果直接影响动作空间的可用集合。
**A10** 闭环模块：感知→记忆→推理/规划→工具执行→（环境反馈）→再感知，自进化由记忆积累+推理归纳驱动。只先落地一个：选记忆。依赖论证：记忆是唯一被所有其他模块依赖的底座——推理需要历史上下文、规划需要世界状态、工具执行结果要落记忆、自进化以记忆为原料；没有记忆，其他模块各自孤立（无共享信念）。本项目把"事实表+索引+变更日志"（记忆层）作为第一优先落地，正是该选择的实践。

## B 组：多代理协作与编排

**B1** 五维度：actors（参与者）、types（合作/竞争/竞合）、structures（对等/中心化/分布式）、strategies（角色型/模型型）、coordination protocols（协调协议）。区别：structure 描述"代理之间的连接拓扑"（谁跟谁连、消息走什么形状）；strategy 描述"每个代理扮演什么、如何决策"（角色分工与模型选择）。结构是网络层面，策略是节点层面——同一结构可配不同策略（中心化结构+角色策略=Router+Worker）。
**B2** 集中式：所有代理经中心协调者通信——通信成本 O(n)（星型，中心可见全局）、单点故障在中心；适合任务边界清晰、需要全局视角与一致决策的场景（任务分发、审批流）。分布式：代理间直连——通信成本可能 O(n²)（全连接时）、无单点但一致性难保证；适合并行子任务、容错优先、本地决策即可的场景（蜂群探索、辩论）。
**B3** 用五维度描述 Router+Workers：actors=1 个 Router+多个领域 Worker（如各技能代理）；types=合作（共同完成派工单，非竞争）；structures=中心化（星型：所有入站经 Router，出站也经 Router，Worker 间不直连）；strategies=角色型（Router=序点/分派/唯一对外汇报；Worker=领域执行，做完向上汇报）；protocols=结构化消息 schema（派工单格式+状态上报格式+验收标准），禁止自由文本传话。
**B4** 适合 AutoGen 对话驱动：目标开放、方案需要多视角碰撞、无固定流程的任务（头脑风暴、方案论证、代码联合评审——对话本身就是协作过程）。不适合：流程确定、需要审计与回放、对时延敏感的任务（对话轮次不可控→成本与时长不可控、决策不可追溯）。判断依据：任务是否需要"过程可控性"——需要过程可控（工单处理、合规审批）用结构化编排，需要"解空间探索"用对话协作。
**B5** 建模：状态={code_diff, review_comments, review_status(pass/fail), attempt_count, merged:bool}；节点=generate（生成）、self_review（自审）、merge（合并）；边：generate→self_review；self_review→merge（条件边：review_status==pass）；self_review→generate（条件边：review_status==fail，携带 review_comments 进状态供重写参考）；merge 为终止。状态字段：diff 内容、评审意见列表、判定结果、重试计数（防死循环，超阈值转人工）。
**B6** 核心优势：链式是单向无回路的固定管道，图式支持条件边+回路+任意拓扑——流程有了"控制流表达能力"。表达：人工介入=图中一个节点（human-in-the-loop 节点，暂停等外部输入再继续）；循环=回边（重试回路，带计数上限）；回退=指向早前节点的边（错误处理路径）。三者在链式里要么做不到要么靠 hack。
**B7** 选型：图式编排（J2 LangGraph）。三条理由：①任务确定性——工单分派规则明确（类型→队列），对话式的自由度是负资产；②可控性——合规场景要求每步可审计，图的节点/边即审计点，对话的多轮不可预测；③调试成本——图失败可定位到具体节点与转移条件，对话失败要回放全部轮次归因。对话式留给"工单内容生成"这类子任务（子任务内部用对话，外层用图）。
**B8** 协议设计不良症状：消息需要"人肉翻译"才能被下游理解（字段含义不一致）、同一信息在不同消息里格式漂移、下游解析失败率上升、对话变成"传话游戏"信息逐层失真。结构化消息优于自由文本：schema 化消息可机器校验（字段缺失即拒绝）、可版本化（schema 演进有据）、可归档检索（三问三答依赖结构化字段）——自由文本把结构信息藏在自然语言里，机器不可靠解析。
**B9** 触发链：①用户提交工单→事件 ticket.created→监听者=分派器（按类型路由到领域 Worker）→②Worker 完成→事件 ticket.resolved→监听者=回访器（发起回访）→③回访完成→事件 ticket.closed→监听者=归档器（H3 留痕）。轮询反模式：轮询空转浪费资源、引入固定延迟（最长=轮询间隔）、与状态天然解耦（漏处理竞态）；事件驱动则到达即处理、无空转、来源与消费解耦。本项目明令禁定时任务即此理。
**B10** 两条结构性预防：①中心化拓扑+唯一对外汇报权（Router 唯一出口）——Worker 间禁止直连，消息量从 O(n²) 降到 O(n)，风暴被拓扑物理阻断（P3 结构维度）；②图的边界节点+消息配额（J2）——把代理交互限制在显式图的边上，每条边设重试/消息上限，超限转 SX/人工，阻断循环回边导致的消息自激（P3 的协议维度+图的边约束）。

## C 组：工作流记忆与经验沉淀

**C1** workflow 与 trajectory 的区别：trajectory 是一次交互的完整动作序列（含试错、环境噪声、任务特定细节）；workflow 是从多次轨迹中归纳出的"抽象操作模式"（去掉了具体参数、失败分支、环境细节）。归纳丢弃：任务特定上下文、失败尝试、环境专有细节；保留：稳定有效的操作结构（步骤顺序、前置条件、成功路径的骨架）。
**C2** 离线模式：在训练样例集上预先归纳（触发=准备阶段；数据=标注轨迹/成功案例；适用=有历史数据积累、任务域稳定）。在线模式：在测试/执行时从当前查询即时归纳（触发=任务执行中；数据=实时轨迹；适用=新领域冷启动、分布漂移场景）。本项目对应：经验库既有条目=离线沉淀，派工单执行中的即时留痕=在线素材。
**C3** 失效检测与淘汰机制：①核验标记——每条工作流带"最后核验日期+验证环境版本"；②触发检测——网站改版事件（环境变更信号）触发受影响工作流标记"待验证"；③验证淘汰——下个任务命中该工作流时先小步验证，失败即置"已废弃"（禁删除，留失效记录+原因）；④选择性注入排除——已废弃/待验证条目不进入提示注入白名单。对应本项目机制：核验日期强制+状态机（现行/废弃）+H3 变更日志。
**C4** 两类性能损害：①上下文污染——无关工作流占据 token 预算，挤掉任务关键信息（信噪比下降，模型注意力被稀释）；②错误引导——过时/不相关工作流的步骤被模型误当作当前任务的正确路径（主动误导，比污染更糟）。这就是"选择性注入"+三级渐进加载（索引→浓缩→原文）存在的理由。
**C5** 加工流水线（≥3 步）：①轨迹采集——任务执行全程留痕（命令+输出原文，禁批量补记）；②归纳提炼——从轨迹中提取可复用模式（做什么/何时适用/坑在哪），过滤任务特定细节；③条目化登记——查重→按契约登记（五要素）→变更日志。三个必备字段：链接（可溯源）、核心要点与关键结论（浓缩）、最后核验日期（时效判据）——再加正/反例（本单实践超出三字段）。
**C6** 事件流保证可回放可审计：一切动作（命令、输出、决策）作为不可变事件顺序追加到流中——回放=按序重演事件；审计=每个结果可追溯到其前置事件链。对比内存变量：状态被覆盖后历史即丢失（不可归因），事件流保留完整因果链（谁在何时基于什么状态做了什么）——这正是本项目"即时落盘、禁批量补记、禁只存会话记忆"的架构依据。
**C7** 沙箱权限边界：放行=只读探测（ls、cat、版本查询）；先审计留痕=可逆写（文件创建、代码提交前的暂存）；拒绝或人工介入=不可逆/越界（rm -rf、网络外发、凭据接触、超出工作目录的写入）。编码必审设卡：代码写入动作（Write/Edit）完成后、进入提交前，强制触发 P3C 审查检查点——审查未过不进入下一环节（不完工），报告原文留痕；未就绪时呈报用户豁免，禁静默跳过。
**C8** 关系推测：任务环境越"结构化重复"（同类操作反复出现、成功路径可泛化），工作流复用收益越大（WebArena 的购物/社交操作高度模板化→+51.1%）；环境越多样异构（Mind2Web 跨站任务差异大），可复用比例低→+24.6%。判断：适合优先投入经验沉淀的业务=高频重复+流程稳定+成功可验证（如工单处理、例行运维、代码审查流水线）；一次性探索型任务收益低。
**C9** 治理流程：①查重合并——同主题条目按核验日期新者为主线，旧条目内容并入后置"已废弃"（禁删，保留演进链）；②矛盾仲裁——按写死顺序（规则>知识库最新文档>记忆>推断），知识库内部冲突以原文为权威（第三层），浓缩版服从原文；③唯一入口——全库索引是唯一登记与检索入口，引用方先查索引再读条目，禁止绕过索引直读（防读到未合并副本）。对应本项目：仲裁顺序写死+浓缩版冲突以原文为准+索引唯一入口。
**C10** 衔接方式：事件流既是执行记录也是经验原料——任务完结时，从事件流中抽取"成功路径+踩坑点"作为归纳输入（H5 经验提炼消费事件流），产出的经验条目登记回知识库（H3 查重落盘），下次同类任务经索引检索注入。额外收益：经验条目天然携带事件流证据链接（可溯源验证，防"凭记忆沉淀"），且经验提炼本身也是事件（被留痕），形成"执行→沉淀→复用"全链路可审计闭环。

## D 组：SDD 方法论与规范驱动

**D1** 规格解决的问题：AI 生成代码的漂移根因是"意图只存在于对话上下文中"——上下文一断/一长，生成即漂移。规格把意图固化为可复查的文件（验收条件可判定），每次生成动作前都可对照规格校准。约束漂移机制：规格是持久锚点——模型输出偏离规格即可被检测（验收条件不满足即拒绝），而不是依赖"记得住"。
**D2** 本质差异：①持久性——AGENTS.md 是仓库级持久规范（每次任务自动加载），prompt 是会话级易失；②协作性——AGENTS.md 是团队共享契约（所有人/所有会话同一套边界），prompt 是个人私有的（换个会话就丢失，团队成员各说各话）。这使 AGENTS.md 成为"制度化知识"而 prompt 是"个人记忆"。
**D3** 正确路径：①不直接写脚本——先读规矩（"禁自建定时任务"是规则层，最高优先级）；②识别诉求本质——"每天取外部接口数据"的真实需求是"定期同步"，合法实现=事件驱动替代（webhook、上游推送、按需拉取+留痕）或向用户申请规则豁免；③流程=提出变更提案（含场景）→用户裁决（改规则/给豁免/接受替代方案）→裁决落盘后再实施。直接写代码=违反规则+绕过 SDD，双重违规。
**D4** 平衡机制："自治"=agent 在阶段内可自主决定怎么做（方法自由）；"有界"=阶段的入口/出口被规格硬性约束（做什么与做到什么程度固定）。阶段划分把自由度封装在边界内：ST2 里你可以任意学习方法，但"考核 80 分"是硬出口。张力化解=每个阶段"目标固定、路径自由"——既避免全自由（失控）也避免全固定（僵化）。
**D5** 映射：需求→输入=用户诉求+约束；产出=spec.md（EARS 验收条款）；完成判定=用户确认规格无修改。设计→输入=spec；产出=design.md（架构+落盘格式）；完成判定=设计呈报+用户确认（预授权时对照冻结 design）。任务→输入=design；产出=tasks.md（可独立验收的任务+依赖顺序）；完成判定=任务清单覆盖对照表齐+用户确认冻结。实现→输入=tasks；产出=代码/配置/文档+测试证据；完成判定=覆盖对照全过+门禁四查+提交完成。
**D6** SOP 化优势：角色与流程预设即开即用（无需每次定义协作方式），产出物结构稳定（模拟软件公司交付链）。短板：SOP 是编译期固化的流程——需求变更时要改 SOP 本身（改流程=改代码/提示词），响应慢；而 P5 规范驱动把"变化点"外置为规格文件（改规格=改数据不改流程），且规格可由用户直接修订——变更响应只改一处数据。MetaGPT 的维护衰减反例也印证：SOP 框架自身演进缓慢时，下游被锁死在旧流程上。
**D7** 判断：不引入（或仅作参考阅读不作依赖）。三条依据：①安全更新断供——10 个月无推送意味着漏洞不修（依赖库 CVE 波及时无人响应）；②生态漂移——其依赖的框架版本演进后无人适配，未来迁移成本只增不减；③问题响应缺失——遇到 bug 只能自己 fork 维护，实际成本=成为该库的义务维护者。星数代表历史声望，pushed_at 代表当下生命力——选型看后者。
**D8** 内在关联：P5 的核心是"意图与事实有唯一可追溯的来源"——单一事实源是它在大厅状态维度的具体化：状态只存事实表一处，其他位置活引用，保证任何时刻读到的状态与真实一致。违反后果：多处抄录状态副本后，某处更新他处漏更→agent 基于过期状态做决策（如基于"已提交"旧副本重复提交、基于"测试通过"旧副本跳过审查）——状态分叉即事实分叉，审计链断裂。
**D9** 最小骨架：①身份与边界——"你是谁、能做什么、禁止做什么"；②规则优先级——"冲突时规则>知识库>记忆>推断，冲突必报告"；③知识库入口——"任务首动作=读索引，检索走三级渐进加载，禁全量塞上下文"；④提交纪律——"精确暂存、四查门禁、编码必审"；⑤上报协议——"异常/冲突/迁移/越权必呈报，正常静默留痕"。每节一句话职责，5 分钟可读完——这就是本会话规则的微缩版。
**D10** 质量闸门设计：触发条件=任何代码写入动作完成（Write/Edit 事件）且目标文件属提交范围；审查内容=P3C 静态规约（Java）+测试证据（可执行验证）；人工审查触发=审查发现 Blocker 级问题、或 AI 复核结论与静态结论冲突、或用户明示该文件高危；未通过处置=不完工（禁止进入提交环节）→修复→复检留痕→通过才放行；留痕=审查报告（范围/发现项数/严重级别/复核状态/命令原文）落入执行轨迹+变更日志。阶段化体现：该闸门是 ST5 编码阶段检查点（H6 四查之 G4），豁免须用户明示留痕。

## E 组：框架工程治理与反例

**E1** 内部二次开发：自定义 License 条款决定能否修改、能否内部分发——多数自定义协议允许内部使用，但要审查"修改是否须开源回馈、是否限定用途"。对外 SaaS：风险大——许多自定义 License（如 SSPL/BEL 类）对"托管提供服务"有专门限制条款，把产品包装成服务可能触发条款要求开源整个服务栈或需商业授权。结论：内部用看修改条款，对外 SaaS 必须法务审查"服务条款"边界。
**E2** 尽调清单：①License 正文全文（尤其"服务/托管"条款与专利授权条款）；②依赖树 License 兼容性（传递依赖的传染性）；③商标与品牌使用限制（改名要求）；④贡献回授条款（CLA/DCO，二次开发的修改归属）。最易忽视=**依赖树的传递 License**——大家只看主仓库 License，忽略其依赖可能是 GPL 传染（引入后污染自身产品）。本项目 G3 敏感排查时 License 审查即此理。
**E3** 四个可查证信号：①pushed_at 最近推送时间（维护心跳）；②open issues 响应速率与积压趋势（社区健康）；③release 节奏与 commit 频率（开发动能）；④贡献者分布（单人维护=bus factor 1）。star 误判原因：star 是历史声望的累计（一次性事件可刷高，如论文热度），不随维护衰减而减少——star 是存量指标，健康度需要流量指标。
**E4** 引入前体检流程：指标=pushed_at（>6 个月=黄灯，>12 个月=红灯）、open issue 积压比（增长趋势=红旗）、release 频率（>1 年无 release=黄灯）、核心贡献者数（bus factor）。阈值判定：红灯项≥1→不引入，仅源码级参考；黄灯→引入但锁定版本+准备 fork 预案。降级预案：发现衰减苗头→评估 fork 自维护成本 vs 替换成本→优先抽象隔离层（把框架封装在自有接口后，替换不扩散）——对应本项目"只读引用+隔离目录"思想。
**E5** 关系：三者是可复现构建的三层防线——锁定依赖版本（lockfile 固定输入）解决"依赖漂移"；固定构建环境（固定 JDK/OS/工具链版本）解决"环境漂移"；可复现构建（同输入同环境→比特级同输出）是前两者的验证结果。只锁版本不锁环境（Maven 中央仓库依赖在装了不同 JDK 的机器上行为不同）；只锁环境不锁版本（依赖悄悄升级）。Cairn 的 make all 依赖 GOPROXY 可达性，p3c 构建依赖 .m2 缓存——都是环境漂移的实例。
**E6** 三条方案：①WSL2——Linux 子系统直接跑 Unix 工具链，适用=日常开发（文件互通、性能好），代价=内存开销与文件系统跨界的性能陷阱；②容器（Docker）——环境镜像化彻底一致，适用=CI/构建标准化，代价=Windows 上需 WSL2 后端、GPU/USB 等硬件透传复杂；③CI 矩阵——本地开发 Windows+远程 CI 跑 Linux 验证，适用=团队协作（本地效率优先），代价=反馈延迟（推代码才知道 Linux 结果）。本单实践对应：make 在 Windows 直跑（mingw make）+sh 兼容缺陷用 PowerShell 等价执行=方案③的变体（等价验证+留痕）。
**E7** 事件流属于"审计追踪（audit trail）"保障机制。留痕在故障复盘的三个用途：①重建时间线——从事件序列还原故障发生链（哪个动作引入、何时扩散）；②定位变更点——对比正常与故障的事件流差异，锁定第一个偏离事件；③验证修复——修复后重放同类事件流验证行为一致（可复现性）。没有留痕的复盘只能靠会话记忆猜测——本单"无痕即违规"审计口径同源。
**E8** 最小闭环：①触发点=代码写入动作完成事件（Write/Edit 落盘即触发，动作内嵌检查点非定时）；②审查内容=变更文件范围跑 P3C 规约（Java）+静态结论为确定性依据，LLM 解释仅作参考须复核；③不通过处置=不完工（禁进提交）→列 Blocker 修复→复检留痕→通过放行；未就绪时呈报用户豁免留痕，禁虚假通过；④留痕载体=审查报告（范围/发现数/严重级/复核状态/命令原文）入执行轨迹+变更日志记行。本单 H6 四查（G4）即此闭环的落地。
**E9** 选型：J3 Dify（低代码平台）。理由：无专职研发团队→低代码把 agent 工程从编码降为配置；内部 RAG+工作流正是 Dify 核心场景（开箱即用，原型到生产快）；自托管满足内网要求。两个风险及对冲：①自定义 License 的商用边界风险→对冲=仅内部使用不对外 SaaS（内部条款通常宽松）+法务确认条款；②平台锁定（流程/数据在平台私有格式里）→对冲=优先用其标准导出能力+关键逻辑外置为 API/MCP 服务（服务与平台解耦）。若后续有专职团队且需深度定制，再迁 J2 图式编排。
**E10** 三条军规：①"引用前必查维护心跳，星数不等于生命力"——反例：MetaGPT 71.2k 星近 10 个月无推送，引入即接下维护债；②"License 看正文与传递依赖，别只看仓库名牌"——反例：Dify 自定义 License 的 SaaS 条款限制，若直接对外提供基于它的服务即违约；③"跨平台构建必须实测，'应该能跑'不算证据"——反例：Cairn 的 check-invariants 在 Windows make 下 sh 引号解析崩溃，未实测前 README 声称的 verify 流程是空中楼阁（本单以等价执行补验才闭环）。
