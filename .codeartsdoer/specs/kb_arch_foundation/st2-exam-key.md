## A 组：Agent 架构与分层

### A1（理解）
- 核心动因：智能体与真实环境交互后无法观测环境的全部状态——反馈有噪声、延迟、不完整，MDP 的"全状态可观测"假设失效，故需 POMDP 建模。
- POMDP 意味着决策必须依赖观测历史/信念状态，而非当前完整状态。
- 对记忆模块的直接影响：必须维护跨步的历史状态跟踪（工作记忆/上下文记忆），用记忆弥补观测缺口。
- 反面判据：若答"没有记忆也能在 POMDP 下最优"或"记忆只是存储历史文本、与可观测性无关"，判不达标。

### A2（理解）
- 规划：面向目标的行动序列编排——任务分解、子目标排序、前瞻；推理：对给定信息的逻辑推演——因果分析、演绎、反思评估。
- 关系：推理为规划提供中间判断（如反思发现计划缺陷），规划把推理结论组织为可执行序列。
- 不能相互替代：只有强单步推理而无长程序列管理会迷失子目标；只有规划无推理则计划出错无法自纠。
- 一句话判据：规划管"按什么顺序做什么"，推理管"判断对不对、为什么"。

### A3（应用）
- 优先强化：记忆/状态跟踪模块（工作记忆），并配合感知补全。
- 必要性论证：POMDP 下观测不完整，需以记忆维护信念状态；反馈延迟时行动只能基于历史推断。
- 不可省略性：无记忆则每次决策退化为对隐藏状态的猜测，出现重复试探与目标漂移。
- 加分项：提出把历史压缩为结构化状态（显式状态估计）而非堆原始文本。

### A4（理解）
- 子系统：记忆（短期/长期）、规划（任务分解与子目标）、工具/执行（外部接口）、感知（多模态输入）、推理/认知核心，P2 还含情感/动机等启发模块（答出 4 类以上即可）。
- 优势一：独立演进——单模块升级（换更强规划器）不牵动整体。
- 优势二：可测试可定位——故障可归因到具体模块，便于监控与调优。
- 加分项：资源按需配置、模块跨 agent 复用。

### A5（应用）
- 可维护性角度：单体提示词随功能膨胀后不可读、不可单测；模块化后各模块有清晰输入输出契约，可独立测试与评审。
- 能力演进角度：模块可独立替换升级（换检索器、换规划策略）；单体提示词任何局部改动都可能破坏其他行为，回归面大。
- 与 P2 呼应：脑启发架构即模块化分工，模块间以明确接口协同。
- 判据：答出"回归面/契约/独立演进"任意两个角度并有论证即达标。

### A6（理解）
- 参数级自进化：修改模型权重（RL/微调），需训练数据、算力、评估闭环，周期长，且有灾难性遗忘风险。
- 经验级自进化：不改权重，沉淀为记忆/工作流/提示资产，写入即生效。
- 成本更低的原因：无需训练管线；可即时更新；可审计、可回滚（删除条目即可）。
- 互补关系（加分）：经验级先低成本验证方向，成熟能力再由参数级固化。

### A7（应用）
- 标准一：接口标准化——兼容主流 RL 环境规范（gym 类 API），可接入现有训练栈。
- 标准二：可复现可评估——提供基准任务与指标，实验结果可复现。
- 标准三：能力覆盖与可扩展——覆盖目标能力（工具调用/长程规划/多模态）且支持注入内部业务任务。
- 加分项：维护活跃、许可证允许商用。
- 判据：三条标准需各附理由，仅列名词不给理由判半分。

### A8（应用）
- 直接执行：只读、无副作用操作（读文件、检索查询）。
- 需确认：低风险可逆写操作（写工作区文件、内部只增接口），经人工或策略确认后执行。
- 必须沙箱隔离：不可逆/外部影响动作（shell 执行、网络请求、删除、对外发送消息）。
- 分层依据：按"副作用可逆性 × 影响范围"分级——越不可逆、影响越大，管控越强。
- 加分项：全动作留痕审计；高危动作白名单+复核。

### A9（理解）
- 输入：截图/DOM 树/可访问性树/控件几何信息（多模态原始信号）。
- 输出：结构化场景表征——元素列表、界面状态、可交互点，供下游规划与定位使用。
- 本质差异：文本对话智能体的感知是被动接收语义级文本；GUI 感知需从像素/结构中主动还原语义与空间布局。
- 加分项：指出 GUI 状态随界面刷新快速变化，感知需按动作节拍主动获取。

### A10（综合）
- 协同闭环：感知获取反馈 → 记忆沉淀历史经验与失败 → 推理评估哪些经验值得固化 → 规划将经验纳入未来计划 → 工具执行验证新策略；自进化即此闭环的持续运转（答出 4 个模块及串联逻辑即可）。
- 先落地选择：记忆（经验存储与检索）。
- 依赖论证：记忆是其他模块进化的数据基础——无沉淀则推理/规划每次从零开始，能力再强也无积累素材。
- 判据：若选"推理/规划"但论证出合理的依赖替代链（如以环境日志外置替代记忆），可给部分分。

## B 组：多代理协作与编排

### B1（理解）
- 五维度：actors（参与者）、types（代理类型/能力分工）、structures（协作结构/拓扑）、strategies（协作策略/决策方式）、protocols（通信协议）。
- structures：静态组织形态——谁和谁连接（集中/层级/去中心）。
- strategies：动态协作方式——如何分工与做决定（投票、辩论、分工汇报、协商）。
- 一句话判据：结构回答"谁连谁"，策略回答"怎么一起做决定"。

### B2（理解）
- 集中式：连接数 O(n)、全局状态易维护、通信成本低；但中心节点构成单点故障与吞吐瓶颈。
- 分布式：无单点故障、局部并行度高；但潜在通信 O(n²)、全局一致性难、调试难。
- 适用：可分解且需要统一调度的任务→集中式；需要多方平等博弈（辩论/评审）→分布式。
- 加分项：工程上常取层级式折中。

### B3（应用）
- actors：1 个 Router + N 个执行 Worker（可含汇总节点）。
- types：Router 负责意图识别与分派；Worker 按领域异构（检索/写作/代码）。
- structures：星型集中式，Worker 间不直连。
- strategies：任务分解 + 独立执行 + 结果汇聚；Worker 不互相协商，冲突由 Router 仲裁。
- protocols：结构化任务单（任务 id、上下文、输出 schema）+ 异步消息回传。
- 判据：五维度逐一对号入座，缺一维度扣一档。

### B4（应用）
- 适合：开放探索、需多角色往复讨论收敛的任务（方案评审、头脑风暴、结对讨论）——路径不可预定义、中间讨论本身有价值。
- 不适合：流程固定、步骤确定、要求可回放可审计的流水线任务（ETL、审批流）。
- 依据：对话轮次不可控导致成本与延迟不可估、行为不确定；任务结构化程度与可控性要求是判断轴。
- 判据：两侧场景各至少一例 + 判断轴。

### B5（应用）
- 状态字段：当前代码产物、评审意见列表、重试计数/版本号、所处阶段标记。
- 节点：generate → self_review → merge。
- 条件边：self_review 之后按"通过/不通过"路由——不通过携评审意见回 generate，通过进 merge。
- 工程细节：回炉边必须带重试上限，超限转人工节点，防死循环。
- 概念判据：能说出"状态是全局共享单例、节点读写状态而非仅靠传参"。

### B6（理解）
- 核心优势：显式图结构使循环/分支/回退成为一等公民；单向链无法表达回炉与重试。
- 条件边表达分支；回边表达循环；检查点/中断点表达人工介入（human-in-the-loop），图可暂停恢复。
- 加分项：状态持久化 + 检查点使任意节点失败后可从最近检查点恢复。

### B7（综合）
- 结论：选 J2 图式编排。
- 理由一（确定性）：工单分派规则固定、分支可穷举，图可显式建模；对话式引入不确定误分派风险。
- 理由二（可控性）：图可设检查点、人工介入点、重试上限；对话轮数不可控。
- 理由三（调试成本）：图可视化、状态可回放定位卡点；多代理对话需逐轮翻消息，定位成本高。
- 加分项：疑难工单协商子环节可用对话式补充（混合方案）。

### B8（理解）
- 症状：语义歧义导致各 Worker 理解不一致；关键信息缺失引发反复追问；格式不定导致下游解析失败；责任不清导致无人响应。
- 结构化优势：schema 强制必填字段与类型校验，机器可路由、可校验、可存档。
- 论证：自由文本依赖模型理解，误差随代理数量逐跳放大；结构化在协议层消灭歧义。
- 加分项：协议还应定义超时、错误码、重试语义。

### B9（应用）
- 触发链：`ticket.submitted` → Router 监听分派（发 `ticket.assigned`）→ Worker 监听 assigned 处理（发 `ticket.resolved`）→ 回访服务监听 resolved 触达用户（发 `feedback.received` 归档）。
- 机制：每环节"事件即触发器"，监听者按订阅关系响应，处理结果再发新事件，链式推进。
- 轮询反模式论证：定时轮询空转浪费、延迟上界=轮询间隔、错过即丢失；事件驱动按需触发、近实时、天然留痕。
- 加分项：经消息队列/事件总线解耦，失败可重投。

### B10（综合）
- 措施一（P3 结构维度）：拓扑收敛为星型/层级，禁止全员互播，广播必经中心节点收敛——无直连则消息量上界 O(n)，风暴失去传播路径。
- 措施二（J2 图编排）：协作环节设固定轮次上限/终止条件/超时，条件边强制收敛到汇总节点——消息总量有硬上限，超限走降级分支而非继续互通。
- 加分项：协议层设每代理发言配额、重复消息去重。

## C 组：工作流记忆与经验沉淀

### C1（理解）
- 区别：轨迹是"一次怎么做的记录"，工作流是"这类任务该怎么做的模板"。
- 保留：成功的步骤骨架/意图序列、适用前置条件（precondition）、可参数化槽位。
- 丢弃：具体元素坐标、具体输入值、试错弯路、环境噪声等实例细节。

### C2（理解）
- 离线：部署/训练前批量归纳；数据来自预先收集或人工标注的成功轨迹；一次计算多次使用；适合任务类型稳定、可预采集的场景。
- 在线：部署后边运行边归纳；数据来自智能体自身轨迹；持续更新；适合环境变化快、无法预采集的场景。
- 权衡：离线质量可控但覆盖有限；在线自适应但可能归纳噪声，需置信度门槛。

### C3（应用）
- 失效检测：执行前验证 precondition（站点结构签名/DOM 特征比对）；执行后校验结果信号（任务是否成功），连续失败累计计数。
- 淘汰机制：失败计数超阈值 → 降级为"待复核"、暂停参与注入；复核后重写或删除。
- 注入侧配合：选择性注入只取高置信 + 近期成功的工作流；工作流版本化，环境改版触发批量重验。
- 加分项：淘汰动作留痕，防误删可回溯。

### C4（理解）
- 损害一：上下文窗口挤占——工作流挤占任务信息与推理空间，同时推高成本与延迟。
- 损害二：噪声干扰——无关工作流把模型带偏，错误动作率上升。
- 加分项：检索/注入延迟增加、指令冲突加剧。

### C5（应用）
- 流水线（至少三步）：①轨迹采集（事件流留痕）→ ②成功判定与筛选（只归纳成功或含教训的轨迹）→ ③归纳抽象（提炼步骤骨架、参数化、写 precondition）→ ④入库登记（去重、打标签、版本号）→ ⑤检索注入与效果回收。
- 三个必备字段：适用条件/precondition（何时可用）、步骤骨架（怎么用）、状态与来源（有效/待验证 + 溯源轨迹链接）。
- 加分项：触发关键词、置信度、最近验证时间。

### C6（理解）
- 机制：动作/观察/消息全部以不可变事件追加（append-only）到事件流，状态由事件重放推导，任意时刻可重建执行现场。
- 优势一：可回放——出错后重放事件序列精确定位决策链。
- 优势二：可审计——事件流即天然审计日志，动作来源与时序清晰；散落内存变量既难回放又难归因。

### C7（应用）
- 放行：沙箱内读操作、依赖安装、单测运行、写入沙箱工作区文件。
- 审计留痕：shell 命令、网络访问——先落盘记录再执行（事件流）。
- 必须拒绝/人工介入：删除宿主文件、改系统配置、对外发布（推送/发消息）、读取密钥。
- 编码必审设卡：代码写入产生"待审事件"触发质量审查，未过审变更不得合入主线，审查结论写入事件流。

### C8（综合）
- 关系推断：环境越稳定、任务重复度越高、流程越长程，工作流复用收益越大——WebArena 站点结构复杂、任务长程多步，复用空间大；Mind2Web 任务偏短程，基础模型已可完成，增益空间小。
- 业务判断：优先投入"流程固定的内部重复业务"（固定表单流程、周期性运维操作）。
- 反向判据：频繁变化/高度创新的任务不宜过度沉淀（沉淀会过期反成噪声）。

### C9（应用）
- 合并：按主题聚类，选覆盖最全/最近验证的一篇为主干，其余要点并入后归档删除。
- 仲裁：按信息源优先级（规则 > 知识库最新文档 > 记忆 > 自行推断）取高者；同层冲突以"最近验证时间 + 可复核证据"为准；无法裁决的标注"待验证"并记录冲突双方。
- 唯一入口：合并后更新引用方指向主干（活引用——引用路径不抄值），检索命中唯一条目；变更写入变更日志。

### C10（综合）
- 衔接：事件流是经验归纳的数据源与验证器——运行时完整留痕每任务事件流；沉淀机制订阅"任务完成"事件，触发对事件流的归纳加工产出经验条目。
- 闭环：经验条目注入新任务 → 新任务执行结果再以事件流留痕 → 形成"沉淀—验证—修订"循环。
- 收益：归纳有据（基于留痕而非事后追忆）；效果可度量（对比注入前后事件流中的任务成功率）。

## D 组：SDD 方法论与规范驱动

### D1（理解）
- 规格解决的问题：把"要构建什么"从对话中固化为可评审、可版本化的文档（需求 + 验收标准），成为唯一事实源。
- 约束漂移机制：实现偏离时可对照规格判定；验收标准先于代码存在，生成后可逐条对照验收。
- 加分项：规格让意图跨会话/跨代理传递一致，避免口头需求逐轮衰减。

### D2（理解）
- 定位：仓库内持久化的智能体行为规范（项目宪法），随任务自动注入的常驻上下文。
- 差异一：持久性——prompt 一次性；AGENTS.md 随仓库版本化，跨会话、跨成员生效。
- 差异二：约束力与一致性——定义边界/流程/纪律，人与 agent 共用同一套规则，新成员零引导对齐；一次性 prompt 各写各的、不可审计。

### D3（应用）
- 第一步：指出该意图违反 AGENTS.md 既有规范，禁止绕过规范直接实现。
- 第二步：回到规格层提需求——分析"为什么需要定时"背后的真实触发需求，评审能否用事件机制满足。
- 第三步：若确需修改规矩，走规范变更流程：修订 AGENTS.md + 记变更日志，之后再实施。
- 核心判据：规范先行、变更留痕、实现层不得私自突破边界。

### D4（理解）
- 有界：每阶段只允许做该阶段的事（需求阶段禁写实现、实现必须对照设计），范围被阶段文件与验收标准框死。
- 自治：边界内 agent 可自主探索实现细节，无需逐步请示。
- 平衡机制：阶段间设完成判定闸门——闸门内放权自治，闸门处受控切换；"何时放权、何时收权"被编码进流程。

### D5（应用）
- 需求：输入=原始需求；产出=spec（含 EARS 式验收标准）；完成判定=需求无歧义、可验收、评审通过。
- 设计：输入=确认的 spec；产出=design（架构/接口/数据流）；完成判定=设计覆盖全部需求条目、选型评审通过。
- 任务：输入=design；产出=tasks（可执行分解+依赖序）；完成判定=每项任务可独立验证。
- 实现：输入=tasks 单项；产出=代码+测试；完成判定=对照设计与验收标准逐条通过、审查留痕。

### D6（综合）
- SOP 优势：角色分工与交付物模板固化，产出结构稳定、流程可预测，冷启动即可跑通"公司式"开发。
- 短板：SOP 把流程写死在代理编排中，需求变更需同时改角色提示、流程定义、模板多处，传播成本高。
- 对比：P5 把变更锚点收敛到规格层——变更=改规格→重新生成下游，响应链更短。
- 判据：答出"SOP 变更传播面大、规范驱动锚点前移"即达标。

### D7（综合）
- 判断：不引入核心依赖（最多只读参考）。
- 依据一：无推送=安全漏洞无人修、issue 无人响应，线上风险无兜底。
- 依据二：生态冻结——依赖与平台升级后的兼容性无人保证，技术债持续累积。
- 依据三：社区撤离信号下 fork 自维护成本远超预期；代码质量是必要条件而非充分条件，可持续性同样必要。
- 判据：结论明确 + 三条依据各有实质论证。

### D8（应用）
- 关联：P5 以规格为唯一事实源；事实表纪律是同一原则在状态层的落地——单点存储 + 他处活引用，从根上消除多副本不一致。
- 违反事故：抄值副本不随源联动，下游基于过期值决策（按已废弃接口开发、按旧阶段重复执行）；排查时多源互相矛盾、无法判定真值。
- 结论判据：答出"单点存储改一处全局生效、活引用保证读取即最新"。

### D9（应用）
- 必备章节（每章节一句话职责）：
  - 项目定位与目标——说明这是什么、服务谁。
  - 技术栈与目录约定——用什么技术、代码放哪里。
  - 规范与禁令——明确禁止行为（如禁定时任务、禁抄值、编码必审）。
  - 工作流程——先规格后动作、一切触发走事件。
  - 信息源仲裁顺序——冲突时听谁的（规则 > 知识库 > 记忆 > 推断）。
  - 变更流程——改规矩的流程与日志要求。
  - 验收纪律——何时算完工、留痕要求。
- 判据：≥6 个章节且各配职责；含"禁令/仲裁/验收"三者任意缺失扣一档。

### D10（综合）
- 触发条件：代码写入/PR/diff 事件自动触发审查；凡触及冻结层（规矩层）、注册表、事实表的改动强制人工审。
- 审查内容：对照 design 与验收标准、规约底线质量、是否越界改冻结层。
- 未过处置：阻断合入 → 事件流记录不通过原因 → 回退实现阶段重做；连续不过升级人工接管。
- 留痕：审查结论（结论+原因+关联 diff）写入事件流/变更日志，与代码变更关联可追溯；未留痕视同未审。
- 判据：四要素齐全且体现"事件驱动 + 阶段回退 + 留痕"。

## E 组：框架工程治理与反例

### E1（理解）
- 内部二次开发：核对是否允许内部商用、修改、部署；是否要求保留版权/品牌标识；修改后再升级是否受限。
- 对外 SaaS：自定义 License 常对多租户/托管服务设限（要求商业授权或禁止变相提供同类服务），直接商用可能违约。
- 结论判据：内部自用风险较低，对外商业化需逐条核对并可能商业谈判；标准协议（Apache/MIT）无此类隐性限制。

### E2（应用）
- 清单（至少四项）：①License 全文逐条读（SaaS/多租户/商标限制）②贡献者协议（CLA/DCO 与修改版权归属）③依赖树 License 兼容性扫描（传染性协议）④商业授权触发条件与费用 ⑤条款变更历史与改版权力。
- 最易忽视：依赖树传递 License 兼容性——只看主仓库协议，忽略其依赖的传染性协议；（答"自定义 License 作者可单方改条款"亦可）。
- 判据：四项齐全 + 指出易忽视项并给理由。

### E3（理解）
- 四信号：①提交频率与最近提交时间 ②issue 响应时长与维护者参与度 ③发布节奏与 changelog 完整度 ④维护者人数与外部贡献者占比（巴士系数）。
- star 失真原因：star 是一次性关注行为，反映知名度不反映维护投入；可刷、可因热点虚高，与 issue 响应/发布节奏无因果。
- 判据：四信号须"可查证"（有具体观测对象），仅答"社区活跃"类空词扣分。

### E4（应用）
- 指标：最近 commit/发布日期、近 12 个月提交曲线、open issue 平均响应时长、维护者数量、fork 活跃度。
- 阈值：最近推送 >6 个月且 issue 无响应 → 红灯不引入；3–6 个月 → 黄灯需降级预案（J4 即红灯案例）。
- 降级预案：引入即 fork 存档、抽象隔离层（核心代码不直接依赖）、版本锁定 + 定期健康复查，触发衰减即启动替代选型。
- 判据：指标、阈值、预案三段齐全。

### E5（理解）
- 锁定依赖版本：消除"依赖漂移"（同一声明在不同时间解析出不同版本），是可复现的输入前提。
- 固定构建环境：统一 OS/工具链/环境变量，消除平台差异（"在我机器上能跑"的根源）。
- 关系：可复现构建 = 锁定版本（输入一致）+ 固定环境（过程一致）→ 产物一致；前两者是因，可复现是果，缺一环产物即不可比。
- 加分项：CI 产物哈希对比可机器验证复现性。

### E6（应用）
- 方案一 WSL2：Windows 内跑 Linux 用户态，适合日常开发；代价：文件系统性能损失、偶发网络/驱动问题。
- 方案二容器（Docker）：环境定义固化（Dockerfile），适合团队一致性与 CI；代价：Windows 需 WSL2 后端、GUI/设备访问受限。
- 方案三 CI 构建矩阵：Linux 构建交由 CI 执行，本地只编辑；适用无本地 Linux 条件；代价：反馈回路变长（每次验证需推送等待）。
- 判据：三方案各含"适用条件 + 代价"。

### E7（理解）
- 事件流属于"留痕（audit trail）"类保障机制。
- 用途一：定位——重放事件序列找到故障首次出现的决策/动作。
- 用途二：归因——区分模型决策错、工具执行错还是环境反馈错（事件有类型与来源）。
- 用途三：改进——基于留痕统计失败模式，沉淀为经验条目/测试用例防复发。

### E8（应用）
- 触发点：代码写入/PR 提交/diff 变更事件自动触发（事件驱动，不依赖人工记忆）。
- 审查内容：对照规格与设计、规约底线检查、越界检查（冻结层/注册表/事实表未被动过）。
- 不通过处置：阻断合入、事件留痕记录原因、回实现阶段修复后重新触发；未过不标记完工。
- 留痕载体：审查结论事件（结论+原因+关联 diff）写入事件流/变更日志。
- 闭环判据："未留痕 = 未审查"，四要素齐全。

### E9（综合）
- 选型：J3 Dify。
- 理由：低代码可视化编排 + 内置 RAG，无专职研发团队即可交付；MCP/skills 保留扩展空间；J1/J2 代码框架与 J5 运行时均需持续编码维护，人力不匹配。
- 风险一：自定义 License 对外商用受限 → 对冲：仅内部使用或提前谈商业授权。
- 风险二：低代码天花板与平台锁定 → 对冲：复杂逻辑外置为独立服务（API），平台只做编排；导出流程配置留迁移余地。
- 判据：选型 + 理由 + 两风险两对冲齐全。

### E10（综合）
- 军规一：License 先于代码——引入前逐条尽调。反例：自定义 License 平台被直接用于对外 SaaS 商用，面临违约与授权谈判被动。
- 军规二：活跃度重于 star——以提交/issue/发布节奏为准入门槛。反例：J4 高 star 但近 10 个月无推送，漏洞与兼容性问题无人兜底。
- 军规三：引入即隔离——抽象层 + 版本锁定 + fork 存档，外部依赖可替换可回退。反例：核心代码深度耦合衰减框架，替换成本失控。
- 判据：三条军规各配反例且反例与军规有因果关系；军规空泛（如"要谨慎选型"）扣分。
