# OLD 轮作答卷（roundId=OLD ｜ COMPARE_OLD ｜ 主智能体作答 ｜ 归档件）

> 作答依据：已三查官方材料原文（`learn/self-evidence/sources/sdd-cli-0009.md`、`sdd-bp-0011.md`）与学习成果条目。独立性声明：作答前未接触 OLD 轮 key 内容。

1. 【记忆】Specification-Driven Development；中文含义：规格驱动开发（模式）。
2. 【记忆】需求规格 → 技术设计 → 任务规划 → 编码实现，按此顺序完整推进。
3. 【记忆】`{项目根路径}/.codeartsdoer/specs/{产物文件夹名}/`（各阶段产物统一存放于此目录下）。
4. 【理解】三个效果：①保障每一步开发均有据可依；②实现过程可控；③历史可查。
5. 【理解】标准 SDD 工作流——智能体主导推进，用户在关键节点确认；斜杠命令模式——开发者自主调度命令、自主推进。
6. 【理解】主要动作：查看/评审智能体生成的文档，接受或拒绝（可提出修改意见让智能体修改）；进入下一环节的前提：当前阶段产物确认无误、符合预期。
7. 【应用】选标准 SDD 工作流。理由：官方适用场景列明"新项目从0到1启动——团队从需求分析、系统设计到SDD文档体系，构建完整的SDD开发流程"；智能体主导分步引导、流程固定，一次建立完整文档体系。
8. 【应用】增量修订路径：手动修改 spec.md → 依次执行 `/sdd-design` → `/sdd-tasks` →（需编码交付则）`/sdd-apply`；无需重新生成 spec.md。
9. 【理解】不互斥。官方明确两种模式可根据不同的项目阶段和团队角色灵活切换：新项目初期用标准工作流跑通框架建立文档体系，中期迭代切换斜杠命令模式做增量开发与局部重构。
10. 【应用】执行 `/sdd-tasks` 和 `/sdd-apply` 两个命令即可（spec/design 产物已由架构师提交）。
11. 【记忆】/sdd-new；输入参数=需求描述（文本）；输出产物=spec.md。
12. 【记忆】`{项目根路径}/.codeartsdoer/specs/{产物文件夹名}/spec.md`。
13. 【记忆】两类：业务行为、需求约束。
14. 【理解】关键区别：/sdd-new 的输入是需求描述且为**必选参数**；其余三个命令的输入是产物文件夹名且为**可选参数**（省略时系统从对话上下文自动推断）。
15. 【理解】由模型自主生成；受生成随机性影响，即使输入相同需求描述，输出文件夹名也可能不同；后果：产物定位漂移、跨阶段前置文件找不到、引用断链。
16. 【应用】两种途径：手动修改 spec.md、通过智能体修改（提出修改意见）；目标状态=spec.md 符合业务预期。
17. 【应用】四项修改意见：①登录成功后除 token 还需返回用户基本信息（昵称、角色）；②锁定时间 15 分钟改为 5 分钟；③补充限流机制，每分钟同一 IP 最多请求 10 次；④响应码统一业务码 20000。覆盖类别：返回内容补充、参数阈值修正、非功能约束（限流）、接口规范统一。
18. 【理解】确认 spec.md 需求理解准确后，单击"开始实现方案创建"进入方案创建环节。
19. 【应用】功能点：手机号/邮箱注册、JWT 登录认证、验证码发送、密码重置（四项）。
20. 【理解】后果：需求反复变化致 spec 反复重写、下游阶段产物连锁作废返工、开发偏离业务预期。规避方法（学习成果反例）：确认点前置（每阶段产物确认后再推进）+增量修订路径（改 spec 后重跑 design/tasks），禁带病确认。
21. 【记忆】/sdd-design；输出=design.md。
22. 【记忆】定义"怎么做"；内容类别：技术架构、实现方案。
23. 【记忆】输入=产物文件夹名，可选参数；省略时系统从对话上下文自动推断上一阶段的产物文件夹名。
24. 【记忆】必须存在目录（`{项目根路径}/.codeartsdoer/specs/{产物文件夹名}`）和生成的 spec.md——两者齐备。
25. 【应用】直接调用 `/sdd-design` 并输入产物文件夹名（如 user_auth）；得到 design.md（包含架构、接口描述）。
26. 【应用】处置步骤（按序）：①手动修改 design.md；②运行 `/sdd-tasks`；③运行 `/sdd-apply`。
27. 【应用】命令组合：手动修改 design.md 后执行 `/sdd-tasks` + `/sdd-apply`。无需重跑 /sdd-new：需求未变、spec.md 仍有效，增量修订只需重跑受影响的下游阶段。
28. 【理解】确认动作：查看生成的 design.md，确认技术方案合理；确认后单击"开始编码任务规划"进入编码任务规划环节。
29. 【理解】标准工作流：智能体自动串联推进，用户在阶段边界确认（接受/拒绝），流程固定不可跳过；斜杠命令模式：用户自主调用命令生成 design.md，自行决定何时推进哪个阶段，可跳过/重复任意命令。差异本质=推进主导权（智能体主导 vs 用户主导）。
30. 【应用】架构师：上午生成 design.md 并提交 Git；开发人员：下午拉取代码后基于该产物执行 /sdd-tasks 与 /sdd-apply 完成开发——design.md 经 Git 在两人间流转，各自承担不同命令段。
31. 【记忆】/sdd-tasks；输出=tasks.md。
32. 【记忆】基于 spec.md 和 design.md 两份文档生成；产物形态=可执行的步骤清单。
33. 【记忆】spec.md 和 design.md 必须同时存在。
34. 【记忆】功能定位：可执行的步骤清单（编码任务规划文档）。
35. 【理解】输入参数=产物文件夹名（可选）；自动推断依据=系统会从对话上下文自动推断上一阶段的产物文件夹名（延续同一产物目录）。
36. 【理解】在 `{项目根路径}/.codeartsdoer/specs/{产物文件夹名}/` 目录下查看 tasks.md；不符合预期时可手动修改或通过智能体修改。
37. 【应用】判断标准=任务拆解完整；确认后单击"开始任务执行"进入任务执行环节（按 tasks.md 逐项执行编码）。
38. 【应用】完整序列：在对话框输入"/"→在弹出菜单中选择"/sdd-tasks"→输入产物文件夹名称（如 user_auth）→生成 tasks.md 落至对应目录。
39. 【理解】tasks.md 处于四阶段链条的第三环（任务规划）：对上游承接 spec 的"做什么"与 design 的"怎么做"，把两者落成可执行步骤；对下游作为 /sdd-apply 逐项执行的直接依据——没有 tasks.md，apply 无从逐项执行。
40. 【应用】因为 tasks.md 是基于修改前的 design.md 生成的；design 已变，旧任务清单与新方案脱节。直接 /sdd-apply 会按过时任务执行，实现偏离修正后的设计。依赖关系上 tasks 必须反映最新 design，故必须重跑 /sdd-tasks 再 apply。
41. 【记忆】/sdd-apply；特殊说明=**直接在主智能体中执行**（命令表功能列加粗内容）。
42. 【记忆】输出=代码 + 更新 tasks。差异：/sdd-apply 是唯一产出最终代码文件的命令（其他三个输出过程文档），且同时更新 tasks。
43. 【记忆】spec.md、design.md、tasks.md 三份文件同时存在。
44. 【记忆】功能说明=按 tasks.md 逐项执行编码任务；按 tasks.md 文档、以逐项方式执行。
45. 【理解】依赖链：/sdd-design 前置=目录与 spec.md 存在；/sdd-tasks 前置=spec.md 与 design.md 同时存在；/sdd-apply 前置=spec.md、design.md、tasks.md 三份同时存在（/sdd-new 无文件前置）。
46. 【理解】依据出自 CLI 手册《SDD 命令概述》命令表的"注意"列——各命令的硬性前置条件（学习成果 M1-SDD-01 关键结论：阶段间硬依赖由命令前置条件强制，非外部纪律）。
47. 【记忆】①打开目标项目的根目录；②鼠标右键单击空白处，选择"在终端中打开"；③在终端输入 codearts 并回车，进入 TUI 开发环境。
48. 【应用】最少三条：`/sdd-design`（输入产物文件夹名→design.md）→ `/sdd-tasks`（→tasks.md）→ `/sdd-apply`（→代码+更新 tasks）。
49. 【应用】问题：违反 /sdd-apply 前置条件（要求 spec/design/tasks 三份同时存在），缺 tasks.md 时命令无法正常执行。正确路径：先执行 `/sdd-tasks` 生成 tasks.md，再执行 `/sdd-apply`。
50. 【应用】含义：开启后任务在沙箱环境内运行，AI 的高风险操作将被拦截，重要操作由 AI 自动审批执行（无需人工干预）。
