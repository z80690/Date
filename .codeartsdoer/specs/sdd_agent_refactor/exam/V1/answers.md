## 角度一：SDD 总纲（1–10）

1.【记忆】英文全称 Specification-Driven Development；中文含义：规格驱动开发（模式）。

2.【记忆】需求规格 → 技术设计 → 任务规划 → 编码实现，四阶段严格按此顺序递进。

3.【理解】目的：通过结构化流程保障开发有据可依、可控可查。两项保障作用：①实现过程可控（每步有据可依、流程结构化）；②历史可查（各阶段产物沉淀留档）。

4.【记忆】产物路径约定：`{项目根路径}/.codeartsdoer/specs/{产物文件夹名}/`——spec.md、design.md、tasks.md 各阶段产物统一存放在该目录。

5.【理解】官方特别提示：产物文件夹名由模型自主生成，受生成随机性影响，即使输入相同的需求描述，输出的产物文件夹名也可能存在差异。后果：跨阶段产物定位漂移（下一阶段找不到上一阶段产物、前置检查失败）或同名混淆。规避：固定产物文件夹名并在各阶段命令中显式传入统一名称（如本特性固定 specs/sdd_agent_refactor/）。

6.【理解】两种方式：标准 SDD 工作流与斜杠命令模式。主导差异：标准工作流=智能体主导流程串联，用户仅在关键节点接受或拒绝生成的文档；斜杠命令模式=开发者自主调度命令、自主推进流程。

7.【理解】新项目初期：选标准 SDD 工作流，用于快速跑通框架、建立完整的 SDD 文档体系；进入中期迭代：切换到斜杠命令模式，用于增量开发和局部重构（按需调用单个命令，不必重跑全流程）。

8.【记忆】对比表的维度：执行方式、灵活性、适用场景、适用角色（四个维度）。

9.【理解】标准 SDD 工作流适合：产品经理（快速验证想法）、独立开发者（做小型项目）；斜杠命令模式适合：架构师（需把关技术方案）、团队协作开发（企业级应用）。

10.【理解】机制依据=命令前置条件内建强制：CLI 手册命令表"注意"列规定 /sdd-design 必须存在目录和 spec.md、/sdd-tasks 必须 spec.md+design.md 同时存在、/sdd-apply 必须三份文件同时存在——文件不齐命令即无法执行。阶段依赖由此固化在平台命令机制内，不依赖开发者自觉遵守，故属官方内建约束而非外部纪律。

## 角度二：建需求 spec.md 阶段（11–20）

11.【记忆】输入参数=需求描述（/sdd-new + 需求描述）；属必选参数。

12.【记忆】输出产物文件名=spec.md；完整存放路径=`{项目根路径}/.codeartsdoer/specs/{产物文件夹名}/spec.md`。

13.【记忆】spec.md 定义"做什么"；功能说明涵盖：业务行为、需求约束等（定义做什么的信息）。

14.【应用】操作序列：①打开目标项目的根目录；②鼠标右键单击空白处，选择"在终端中打开"；③在终端输入 codearts 并回车进入 TUI 开发环境；④在对话框输入 `/sdd-new` + 需求描述并回车，生成 spec.md；⑤进入 `{项目根路径}/.codeartsdoer/specs/{产物文件夹名}/` 目录查看生成的 spec.md（不符合预期可继续修改）。

15.【理解】官方提供两种修改途径：①手动修改 spec.md 文件；②通过智能体修改（向智能体提出修改意见）。

16.【应用】四条修改意见：①登录成功后除了返回 token，还需要返回用户基本信息（昵称、角色）；②锁定时间 15 分钟太长了，改为 5 分钟；③补充接口的限流机制，每分钟同一个 IP 最多请求 10 次；④响应码不要用 200，统一使用业务码 20000 表示成功。

17.【应用】连锁后果：需求反复变化导致 spec.md 反复重写，已生成的下游产物（design/tasks）连锁作废返工，开发偏离业务预期。正确做法：确认点前置——查看生成的 spec.md、提出修改意见、修改后再确认，直到需求规格文档符合业务预期才进入下一环节；纪律要求=不带病确认（未确认不推进）。

18.【应用】最小改动操作路径：手动修改 spec.md，然后组合执行 `/sdd-design` 和 `/sdd-tasks`。无需重新生成 spec.md 的原因：登录逻辑修改属局部需求变化，spec.md 经手动修改后仍然有效，斜杠命令可只重跑受影响的下游阶段，无需重跑全流程。

19.【理解】确认动作：查看生成的需求规格文件 spec.md，提出修改意见让智能体修改，再次查看确认需求理解准确；确认后单击"开始实现方案创建"进入方案创建环节（智能体自动进入下一阶段生成 design.md）。

20.【理解】新项目从 0 到 1 启动的项目：官方场景描述为"新项目从0到1启动——团队从需求分析、系统设计到SDD文档体系，构建完整的SDD开发流程"。理由：标准工作流由智能体主导分步串联、流程固定不可跳过，能一次性建立从需求规格到任务规划的完整文档体系，为后续迭代打底。

## 角度三：建设计 design.md 阶段（21–30）

21.【记忆】可选参数（产物文件夹名）；开发者未显式给出时，系统会从对话上下文自动推断上一阶段的产物文件夹名。

22.【记忆】必须存在目录（`{项目根路径}/.codeartsdoer/specs/{产物文件夹名}`）和生成的 spec.md——两者缺一不可。

23.【记忆】design.md 定义"怎么做"；功能说明涵盖：技术架构、实现方案等（定义怎么做的信息）。

24.【应用】操作：直接调用 `/sdd-design`，然后输入产物文件夹名 user_auth；预期产物=design.md（包含架构、接口描述），落至 `.codeartsdoer/specs/user_auth/design.md`。

25.【应用】处置顺序：手动修改 design.md，再依次运行 `/sdd-tasks` 和 `/sdd-apply`。体现的灵活性：斜杠命令模式可灵活跳过或重复任意阶段、按已有过程交付件按需调用，无需重跑全流程。

26.【理解】架构师侧：上午生成 design.md 并提交 Git；开发人员侧：下午拉取代码后，只需在聊天框执行 `/sdd-tasks` 和 `/sdd-apply` 即可继续开发——两人经由 Git 中的 design.md 交接，各自执行不同命令段。

27.【理解】design.md 的功能定位=承载技术架构与实现方案（"怎么做"）；把关技术方案即把关 design.md 的质量与确认。斜杠命令模式下架构师可自主生成/修改 design.md 并提交，团队基于该产物继续下游命令——技术方案的控制点清晰落在 design 产物上，故适合架构师把关的场景。

28.【理解】用户动作：查看生成的 design.md，确认技术方案合理；按钮文案="开始编码任务规划"；确认后进入编码任务规划环节（生成 tasks.md）。

29.【理解】前提条件=spec.md 已存在（目录与 spec.md 齐备）。标准工作流中该前提由流程顺序天然保证（spec 确认后才进入方案创建）；斜杠命令模式下由命令前置条件机制保障——CLI 手册"注意"列硬性要求执行 /sdd-design 前必须存在目录和 spec.md，缺失则命令无法执行。

30.【理解】文档出处：官方最佳实践《SDD开发模式标准工作流与斜杠命令实践》标准 SDD 工作流节（确认 spec.md→"开始实现方案创建"、确认 design.md→"开始编码任务规划"、确认 tasks.md→"开始任务执行"）。同构点：官方侧=每阶段产物由用户确认（接受/拒绝）后才进入下一环节；本项目侧=每阶段产物落盘后主智能体呈报结论前置摘要并询问"是否需要修改文档"，确认权在用户、确认后才推进——确认门内建于阶段边界，两者机制同构。

## 角度四：建任务 tasks.md 阶段（31–40）

31.【记忆】可选参数（产物文件夹名）；未显式给出时系统从对话上下文自动推断上一阶段的产物文件夹名。

32.【记忆】硬性前置条件：必须同时存在 spec.md 和 design.md。

33.【理解】功能定位：可执行的步骤清单（任务规划文档）。基于 spec.md 和 design.md 两份输入文档生成。

34.【应用】完整操作：在对话框输入"/"，在弹出菜单中选择"/sdd-tasks"，然后输入产物文件夹名称 user_auth，生成可执行的步骤清单 tasks.md（落至 `.codeartsdoer/specs/user_auth/tasks.md`）。

35.【理解】确认动作：查看生成的 tasks.md，确认任务拆解完整；按钮文案="开始任务执行"；确认后进入任务执行环节（智能体按 tasks.md 逐项执行编码任务）。

36.【理解】官方提供的处理方式：可手动修改或通过智能体修改 tasks.md 文件，直到任务拆解符合预期。

37.【应用】沉淀三份过程文档：spec.md、design.md、tasks.md；三者均存放于 `{项目根路径}/.codeartsdoer/specs/{产物文件夹名}/` 目录下。

38.【理解】枢纽作用：spec.md 定"做什么"、design.md 定"怎么做"，tasks.md 把两者落成可执行的步骤清单；/sdd-apply 按 tasks.md **逐项**执行编码——没有 tasks.md，apply 便无执行单元。tasks.md 上游承接 spec+design 双输入、下游驱动 apply 逐项执行，是规划向实现转换单的枢纽。

39.【理解】/sdd-tasks 的前置（spec.md+design.md 同时存在）已被架构师提交的产物满足；执行 /sdd-tasks 生成 tasks.md 后，/sdd-apply 的前置（spec、design、tasks 三份齐备）也随即满足——两命令前置条件依次由既有产物与刚产生产物满足，故开发人员只需执行这两个命令即可合法衔接，无需重跑上游。

40.【应用】官方机制下 /sdd-tasks 会因前置条件不满足而无法执行（缺 design.md）。体现的设计原则：先规格后动作、禁跳阶段——阶段间硬依赖内建于命令前置条件，机制上阻止在产物缺失时跳步执行。

## 角度五：执行编码实现阶段与命令依赖（41–50）

41.【记忆】/sdd-apply **直接在主智能体中执行**（CLI 手册对其执行位置的特殊说明）。

42.【记忆】硬性前置条件：必须同时存在 spec.md、design.md、tasks.md 三份文件；输出产物=代码 + 更新 tasks。

43.【理解】功能说明：按 tasks.md 逐项执行编码任务。与 /sdd-tasks 产物关系：/sdd-tasks 的输出产物（tasks.md）正是 /sdd-apply 的执行依据——两者构成"任务清单生成→按清单逐项执行"的直接上下游关系。

44.【理解】依赖链条：/sdd-new（无文件前置，输入需求描述）→ /sdd-design（前置=目录+spec.md 存在）→ /sdd-tasks（前置=spec.md+design.md 同时存在）→ /sdd-apply（前置=spec+design+tasks 三份同时存在）。链条从机制上强制：需求规格先行→技术设计其次→任务规划再次→编码实现最后——每一阶段的输入都是上游产物，跳过上游则下游命令因前置缺失无法执行，开发顺序被机制固定。

45.【应用】官方支持。操作方式=直接调用 `/sdd-design`（输入产物文件夹名）开始设计，后续按需 /sdd-tasks、/sdd-apply。官方依据=斜杠命令模式适用场景之"已有部分文档：如果已手动写好 spec.md，想直接开始设计，直接敲 /sdd-design 完成后续流程"（场景选型节）。

46.【应用】增量修订操作路径：手动修改 design.md → 依次运行 `/sdd-tasks` 和 `/sdd-apply`。不需重跑 /sdd-new 的原因：需求本身未变，spec.md 仍然有效，变更只发生在设计层——增量修订只需重跑受影响的下游阶段（任务清单基于新 design 重新生成后再执行编码）。

47.【记忆】自动审批表示任务在沙箱环境内运行，AI 的高风险操作将被拦截，重要操作由 AI 自动审批执行（开启后相关操作无需人工干预）。

48.【应用】①打开目标项目的根目录；②鼠标右键单击空白处，选择"在终端中打开"；③在终端输入 codearts 并回车，进入 TUI 开发环境；④在对话框输入"/"，在弹出菜单中选择所需斜杠命令（/sdd-new → /sdd-design → /sdd-tasks → /sdd-apply）按需调用完成 SDD 开发。

49.【理解】对应关系：官方每阶段命令以"前置文件齐备"为执行前提（spec/design/tasks 缺失即拦截命令）；本项目门禁链 M1→M7 以"证据文件存在+检查单逐项全过"为放行前提（gates/ 证据缺失即拦截放行）。两者同为"前置产物/证据齐备才允许进入下一阶段"的机制化检查。出处：`notes/学习成果-SDD官方文档.md` M1-SDD-01 条目正例（"阶段前置条件检查模式可直接对应本特性门禁链 M1→M7 的前置依赖设计（每门禁以证据文件存在为放行前提）"，依据=CLI 手册命令表"注意"列）。

50.【理解】不矛盾，两者作用于不同层面。斜杠命令的"可灵活跳过或重复任意阶段"指**命令执行顺序可自由调度**——前提是所需产物已存在（如已手动写好 spec.md 可跳过 /sdd-new 直接 /sdd-design；编码中途改 design 后重复跑 /sdd-tasks）。"先规格后动作、禁跳阶段"指**产物依赖链不可绕过**——每条命令的前置条件（上游产物存在）由 CLI 手册"注意"列强制，缺失上游产物的"跳步"会因前置检查失败而无法执行。故：机制允许复用既有产物跳过重复生成，但不允许在产物缺失时强行执行下游命令——灵活调度与规格先行并行不悖，跳过的只是"重新生成"，跳不过的是"产物齐备"。
