## 角度一：SDD 总纲（1–10）

1.（记忆）英文全称 Specification-Driven Development；中文名称：规格驱动开发（模式）。

2.（记忆）需求规格 → 技术设计 → 任务规划 → 编码实现，四个阶段依次递进。

3.（记忆）①保障每一步开发均有据可依；②实现过程可控；③历史可查。

4.（记忆）两种使用方式：标准 SDD 工作流（智能体主导）与斜杠命令模式（开发者自主调度）。

5.（理解）官方定义 SDD 为"以规格说明为核心的软件开发方法"：开发者提供需求描述后，智能体依次生成规格说明、设计方案与任务规划——达成共识的时点在**编码之前**，就**任务目标及实施方案**达成共识，使开发者与智能体在动手写码前对齐预期，最终产出高质量代码。

6.（理解）执行方式：标准=对话框输入需求，智能体主导流程串联，用户在关键节点接受或拒绝生成的文档；斜杠=对话框调用命令，用户自主推进流程。灵活性：标准=流程固定、不可跳过；斜杠=可任意组合、重复执行单个命令。

7.（理解）四类适用场景：①新项目从 0 到 1 启动；②标准化要求高的正式项目（一致性、可验证性要求高）；③SDD 新手入门；④需求相对稳定的项目。新手入门归入该模式的原因：智能体按预设工作流分步引导、用户在关键节点确认，可快速建立完整链路而不易迷失。

8.（理解）官方明确两种模式**并非互斥**，可根据不同项目阶段和团队角色灵活切换：新项目初期用标准 SDD 工作流快速跑通框架、建立完整的 SDD 文档体系；进入中期迭代后切换到斜杠命令模式，利用四个命令做增量开发和局部重构。

9.（应用）走斜杠命令模式的增量修订路径：手动修改 spec.md（改登录逻辑），然后组合执行 `/sdd-design` 和 `/sdd-tasks`，无需重新生成 spec.md。理由：官方场景选型指出需求频繁迭代/不明确、需反复确认的项目适合斜杠命令模式，可只重跑受影响阶段，避免全流程重跑。

10.（应用）官方多人异步协作场景的命令组合：执行 `/sdd-tasks` 和 `/sdd-apply`（design.md 已由架构师生成并提交 Git，开发人员拉取后基于既有产物继续，无需重跑 /sdd-new 与 /sdd-design）。

## 角度二：建需求（11–20）

11.（记忆）/sdd-new。

12.（记忆）输入参数=需求描述（/sdd-new + 需求描述），为**必选参数**。

13.（记忆）输出产物文件名=spec.md；产物路径约定=`{项目根路径}/.codeartsdoer/specs/{产物文件夹名}/spec.md`。

14.（记忆）spec.md 定义"**做什么**"；内容包含业务行为、需求约束等信息。

15.（理解）第一步环境准备=进入 TUI 开发环境：①打开目标项目的根目录；②右键空白处选"在终端中打开"；③输入 codearts 回车。要打开根目录的原因：SDD 产物输出路径固定为 `{项目根路径}/.codeartsdoer/specs/`，项目根目录决定产物落盘位置，须在正确工程上下文中启动。

16.（理解）两种修改途径：①通过智能体修改（提出修改意见）；②手动修改 spec.md 文件。体现标准 SDD 工作流的**阶段确认机制**：每阶段产物须用户确认（接受/拒绝并修改至符合预期）后才进入下一环节。

17.（理解）修改意见四类：①登录成功后除 token 外还需返回用户基本信息（昵称、角色）；②账号锁定时间 15 分钟改为 5 分钟；③补充接口限流（每分钟同一 IP 最多请求 10 次）；④响应码不用 200，统一业务码 20000 表示成功。共同点：均为对业务约束与行为细节的**明确化和修正**，未改变需求整体方向。

18.（理解）后果：需求未澄清即生成规格会导致 spec 反复重写、已生成的阶段产物连锁返工作废（开发偏离预期）。官方规避路径：确认点前置（每阶段产物确认后再推进）+增量修订路径（修改 spec 后重跑 /sdd-design、/sdd-tasks），禁带病确认进入下一阶段。

19.（应用）`/sdd-new 请帮我开发一个用户注册登录模块，包含手机号/邮箱注册、JWT登录认证、验证码发送、密码重置功能`（官方实操示例原命令调用方式，产物落至 .codeartsdoer/specs/{产物文件夹名}/spec.md）。

20.（应用）处置：在当前阶段内提出修改意见，经智能体修改或手动修改 spec.md，直到需求规格文档符合业务预期（评审通过），再进入 /sdd-design。不能直接跳 /sdd-apply 的原因：①apply 的前置条件要求 spec.md、design.md、tasks.md 三份同时存在，缺 design/tasks 命令无法执行；②带病 spec 会连锁产生错误设计与任务，违背"每步有据可依"。

## 角度三：建设计（21–30）

21.（记忆）命令=/sdd-design；输出产物=design.md。

22.（记忆）输入参数=产物文件夹名（可选参数）；系统会从对话上下文自动推断上一阶段的产物文件夹名。

23.（记忆）必须存在目录 `{项目根路径}/.codeartsdoer/specs/{产物文件夹名}` 和生成的 spec.md。

24.（记忆）design.md 定义"**怎么做**"；内容包含技术架构、实现方案等信息。

25.（理解）因为该约束由命令前置条件**内建强制**而非依赖开发者自觉：CLI 手册命令表"注意"列明示执行 /sdd-design 必须存在目录和 spec.md（/sdd-tasks 须 spec+design 双齐、/sdd-apply 须三齐），文件不齐则命令无法执行——阶段依赖被固化在平台命令机制里，属官方内建约束。

26.（理解）官方操作：直接调用 `/sdd-design`，然后输入产物文件夹名称（如 user_auth），即可生成包含架构、接口描述的 design.md。体现斜杠命令模式"**可任意组合、重复执行单个命令**"的灵活性——可从任意已有产物切入流程，无需重跑全流程。

27.（理解）操作步骤：手动修改 design.md，再依次运行 `/sdd-tasks` 和 `/sdd-apply`。不需要重跑 /sdd-new 的原因：需求本身未变，变更发生在设计层，spec.md 仍然有效——增量修订只重跑受影响的下游阶段（设计变更→任务清单重生成→编码重执行）。

28.（理解）流转方式：架构师上午生成 design.md 并提交 Git；开发人员下午拉取代码后，只需在聊天框执行 `/sdd-tasks` 和 `/sdd-apply` 即可继续。适合原因：斜杠命令可按已有过程交付件情况按需调用、无需重跑全流程，天然支持跨人、跨时段的异步衔接。

29.（应用）命令调用：`/sdd-design user_auth`（或输入 /sdd-design 后按提示输入产物文件夹名 user_auth）；预期产物=design.md；位置=`.codeartsdoer/specs/user_auth/design.md`。

30.（应用）问题：违反 /sdd-design 前置条件（CLI 手册"注意"列要求必须存在目录和 spec.md）——命令无法基于不存在的 spec.md 生成设计，执行会失败/无法产出有效 design.md。正确处置顺序：先执行 `/sdd-new`（在 user_auth 产物文件夹下生成 spec.md），评审确认后再调用 `/sdd-design`。

## 角度四：建任务（31–40）

31.（记忆）命令=/sdd-tasks；输出产物=tasks.md。

32.（记忆）必须同时存在 spec.md 和 design.md 两份文件。

33.（记忆）基于 spec.md 和 design.md 生成；标准工作流中确认该产物后点击"**开始任务执行**"进入执行环节。

34.（记忆）按 tasks.md 逐项执行编码任务。

35.（理解）四阶段是**递进**关系：任务规划要同时承接"做什么"（spec 的需求约束/业务行为）与"怎么做"（design 的技术架构/实现方案）两个上游才能拆出正确任务。若仅有 spec，任务将丢失设计阶段的关键决策（架构、接口、实现方案），任务粒度与技术路线偏离既定方案。官方内建前置=spec 与 design 双齐备，正是递进理念的机制化。

36.（理解）官方允许：可手动或通过智能体修改 tasks.md（直到任务拆解符合预期）。该环节位于"查看生成的 tasks.md、确认任务拆解完整"这一确认点之后、"开始任务执行"确认动作之前——即处于 tasks 产物确认点与执行启动点两个确认点之间。

37.（理解）重跑原因：tasks.md 是基于修改前的 design.md 生成的，design 变更后原任务清单与新方案脱节，必须基于新 design 重新生成。不重跑直接 /sdd-apply 的风险：智能体按过时的任务清单执行编码，实现与修正后的设计不一致，产出偏离既定技术方案（且部分任务可能已无意义）。

38.（理解）确认动作序列：①查看生成的 design.md，确认技术方案合理 → 单击"开始编码任务规划"；②查看生成的 tasks.md，确认任务拆解完整 → 单击"开始任务执行"。各确认动作的推进条件=用户对当前阶段产物**明确接受**（人工确认通过）方可推进到下一阶段；不接受则修改后重新确认。

39.（应用）命令调用：`/sdd-tasks user_auth`；产物=tasks.md；位置=`.codeartsdoer/specs/user_auth/tasks.md`。

40.（应用）风险：产物文件夹名由模型自主生成、存在随机性，同需求不同阶段生成的文件夹名可能不一致——下一阶段命令找不到上一阶段产物（前置条件不满足，命令失败）或产物分散多处、引用断链。各阶段命令必须显式传入统一文件夹名的原因：确保 spec/design/tasks 三份产物始终落在同一 `.codeartsdoer/specs/{文件夹名}/` 内连续可引用，使每阶段的文件齐备性前置检查可满足、阶段间衔接可靠。

## 角度五：执行（41–50）

41.（记忆）/sdd-apply。

42.（记忆）必须同时存在 spec.md、design.md、tasks.md 三份文件。

43.（记忆）输出=代码 + 更新 tasks。不同点：前三个命令的输出都是过程文档（spec.md/design.md/tasks.md），/sdd-apply 是唯一**产出最终代码文件**的命令，同时更新 tasks（任务推进），输出物性质从"规划文档"变为"实现代码"。

44.（记忆）CLI 手册注明 /sdd-apply **直接在主智能体中执行**（区别于其他命令的常规调用说明）。

45.（理解）/sdd-apply 要求三份文件同时存在——三缺一即无法执行，这就是"先规格后动作、禁跳阶段"的内建体现：缺 spec.md=没有需求依据（做什么不明）；缺 design.md=没有技术方案（怎么做未定，实现必然偏离）；缺 tasks.md=没有执行清单（apply 无从"逐项"执行）。三份齐备才保障"每一步开发均有据可依"。

46.（理解）三份过程文档：spec.md、design.md、tasks.md。对后续迭代的价值：作为基线支撑增量修订（如需求变化只改 spec，再重跑 design→tasks→apply，无需从零开始）；承载设计决策与任务上下文，支撑多人异步协作（提交 Git 后他人可继续）；可审查、历史可查。

47.（理解）风险：产物文件夹名由模型自主生成、受随机性影响，同需求重跑可能产生不同文件夹名——apply 阶段若传入/推断的文件夹名与前三份产物实际所在不一致，前置条件（三文件同时存在）检查失败，命令无法执行或产物散落难追溯。规避方案（学习成果）：固定产物目录名——本特性即固定 `specs/sdd_agent_refactor/` 并登记知识库索引，各阶段显式传入统一名。

48.（应用）完整处置序列：①手动修改 design.md（修正设计问题）；②运行 `/sdd-tasks`（基于新 design 重新生成任务清单）；③运行 `/sdd-apply`（按新 tasks 逐项执行编码）。不涉及 /sdd-new（spec.md 未变，需求规格仍有效）。

49.（应用）①`/sdd-new` + 需求描述（必选）→ 输出 spec.md（落 `{项目根路径}/.codeartsdoer/specs/{产物文件夹名}/spec.md`）；②`/sdd-design` + 产物文件夹名（可由上下文推断）→ 输出 design.md（同目录）；③`/sdd-tasks` + 产物文件夹名 → 输出 tasks.md（同目录）；④`/sdd-apply` + 产物文件夹名 → 输出代码文件 + 更新 tasks（按 tasks.md 逐项执行）。顺序固定为 new→design→tasks→apply，前一阶段产物是后一阶段的前置。

50.（应用）判断：**不可行**。理由：依据官方前置条件，/sdd-apply 必须同时存在 spec.md、design.md、tasks.md 才能执行——跳过需求规格与设计直接写代码后调用 apply，会因三份产物缺失被前置条件拦截，命令无法执行；且阶段硬依赖由官方内建约束强制（design 须 spec 已存在、tasks 须 spec+design、apply 须三者齐备），SDD 的"先规格后动作"无法绕过。正确做法是走完整四阶段（或至少补齐三份过程文档后再 apply）。
