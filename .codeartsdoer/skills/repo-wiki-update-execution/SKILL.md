# repo-simple-wiki-update 执行适配契约（Windows PS5.1 / WSL bash + 纯文档仓库）

## 前置判定与核实
- **主 skill 的子 skill 未在 Skill 工具注册是常态**：repo-simple-wiki 要求以完全限定名（repo-simple-wiki:stage0-mode-detection 等）调用 7 个子 skill，Skill 工具报 not found 时**勿中止**——直接读取 skill 安装目录下 skills/<子skill名>/SKILL.md（本机=C:/Users/Administrator/.codeartsdoer/cache/system/skills/repo-simple-wiki/skills/）按其规则人工执行，各子 skill 自带断点续传与进度落盘规则（2026-11-13 实证：7 个子 skill 均未注册，读 SKILL.md 执行跑通全量流程）。
- 分支子目录：git 仓库用 `git rev-parse --abbrev-ref HEAD` 获取（本仓=master）；state.json 与 wiki 产物在 `.codeartsdoer/.codebase/branches/<分支>/` 下。glob 模式 `.codeartsdoer/**` 可能因点前缀目录被忽略而返回空——动笔前用递归 `Get-ChildItem -Force -Recurse` 实查目录真实内容，勿凭 glob 空结果断言"产物不存在"（2026-11-08 实证：glob 报空但 branches/master/docs 下 7 篇文档齐全）。
- 纯 .md 仓库（无代码文件）：extract_symbols.py 不支持 .md 扩展名 → 骨架文件生成但为空（status=warning, symbols=0），属预期而非故障。跳过符号骨架环节，subagent prompt 直接给变更源文件实文与定位摘要；阶段 2.5（切片）恒跳过（常规档）。
- architecture.json 的 `modules=[]` 需先查产物时间戳再下结论：产物生成时间早于本轮变更检测时间（state.json updated_at / changed_files detected_at）即产物过期，`[]` 不构成"无新模块"依据——实读抽验（读新目录的包入口/组装根文件 + extract_symbols 数符号）后再判（2026-11-11 实证：modules=[] 为 2026-11-06 产物，但 02_软件源码 为 27 文件结构化 Python 包，实读 cli.py 的 Base 组装根 + README 目录池声明 + extract_symbols 199 符号后判定构成新模块 software_src，走 3.2 新增文档流程）。temp/ 等临时目录按"不在 Wiki 关注层面"处理，判定依据对照项目事实表的入库排除清单（temp/ 在排除项中）。
- 工具运行时日志目录（如 `.workbuddy/memory/automations/` 的自动化签到执行记录）即使被 git 跟踪并出现在 state.json 的 changed_files 中，也判成因 1（不在 Wiki 关注层面）跳过：不属于治理机制/协作规范/业务术语任何关注层面，且 wiki-index 零引用；判定结论写入 update_plan.unmatched_files 的 judgment/reason 字段留痕（2026-11-09 实证：WorkBuddy 签到日志，实读确认后过滤）。同判成因 1 的还有**任务过程产物目录**：临时素材缓存/一次性探针脚本（2026-11-11 实证：temp/toutiao_* 26 个视频转写脚本与缓存——知识库索引中仅标注为"原始素材指针"、README 目录池 00-09 未声明该目录，非项目结构资产，不新建模块文档）。与知识正本同主题的**外部系统输入拷贝**亦同判成因 1：知识本体已在 notes 正本（如学习成果三篇），外部工具的检索输入拷贝（如 temp/cairn-kb-src/<skill名>/SKILL.md）不重复入档，reason 中写明主题对应关系即可；temp/ 下一次性文件（本地 MCP 配置/sqlite 验证探针/placeholder LLM 端点/env 生成脚本类）判成因 1 前逐一实读取证，勿凭目录名直接断言（2026-11-12 实证：temp/ 下 5 个新增逐一实读后判成因 1 跳过）。
- 同一变更集跨轮重复（version_token 187→198 两轮 changed_files 均为 .workbuddy 日志+notes/项目事实表.md）：上轮 progress.json 的 filter_note 与 update_plan 成因判定可沿用作先验，实读复核文件现状仍属同一性质即可快速判定，无需重新全量分析；先验不成立时以实读为准（2026-11-09 实证：token 198 轮沿用 187 轮 .workbuddy 成因 1 判定，实读复核后过滤）。

- **token 递增的零修订轮（全短路特例完整路径）**：version_token 递增但 changed_files 与上轮完全相同、reverse_lookup 报所有命中小节 hash_status=unchanged 时，判 token 递增仅为检测器状态推进（文件内容与上轮基线一致，hash 比对为权威），走全短路特例：new_modules/transfer_impact 为空且 unmatched 补判清零后，跳过阶段 3+4 subagent 调度，affected_docs 保持 completed 不动（hash 短路文档无需在 completed/pending 间搬运）。此时主技能字面要求的"调 fix_code_links.py 刷行号"为**无操作**——fix_code_links 仅支持逐文件 `--code-links-file` 模式（无 --wiki-root 全量模式），而全短路轮 wiki 目录下无 .code-links.json 可刷（上轮 build_index 已消费删除），且 hash 一致意味着行号无偏移；勿为走流程强行造空 .code-links.json，直接进阶段 6。build_index 输出**全 reused（updated 0 / added 0）即零修订轮的正常证据**而非异常（2026-11-12 实证：token 422→423 连续两轮同批 3 文件 hash unchanged，8 篇全 reused、69 code_paths 验证通过、format_errors=[]）。
- **零修订轮（affected_docs=0 型）的判定留痕迁移与基线复核**：变更文件完全不在任何模块路径与索引 code_refs 上（典型=工具运行时日志追加），reverse_lookup 报 affected_docs=0 + unmatched 全判成因 1 → update_plan 为空计划（四个数组全空），跳过阶段 3+4 subagent；但 3.5 校验链仍跑全目录复核基线（validate total=0 属正常——无 .code-links.json 残留可校；redact/lint 与上轮基线对比无回归即可，orphan warning 属全库遗留不阻塞），build_index 全 reused 为零修订轮正常证据。**Stage 6 清空 update_plan 前必须迁移判定依据**：流程要求 update_plan=null，而"同一变更集跨轮重复"的先验复用依赖上轮 update_plan 成因判定记录——把成因判定 note 迁移到 stage_2 的独立 `note_<token>` 字段（如 note_557）再清空，先验不随清空丢失；progress.json 各 stage 的轮次记录一律追加 `note_<token>`/`update_note_<token>` 新字段而非覆盖历史 batch_note，历史轮实证保留完整（2026-11-13 实证：token 557 轮 .workbuddy 执行日志追加 1 文件，成因 1 判定——实读为工具自动生成的纯追加式执行日志+module_tree 无模块路径涵盖+grep wiki 全目录 0 命中排除成因 2+路径一致排除成因 3——迁移至 stage_2.note_557，3.5 基线复核 validate passed/redact 0 可疑/lint 0E15W 与上轮一致，build_index 15 全 reused/216 code_paths）。
- **上轮中断于 Stage 6 之前的跨轮恢复路径**：progress.json 显示上轮 Stage 3+4/3.5 已 completed（修订已合并进 .md+.code-links.json）但 stage_5/6/7 仍 pending、update_plan 未清空、docs 树残留 N 个 .code-links.json、wiki-index.json 的 wiki_root 字段遗留指向旧分支（如 master，built_at 停留旧时间）时，本轮 version_token 不匹配按"重新开始更新流程"处理，恢复链四步：①旧 update_plan 判定与遗留状态摘要迁移至 stage_2 的 `note_<旧token>` 字段留痕后清空 update_plan（留痕规则见上条）；②旧 update_plan 的 `module_tree_pending_changes`（如 adapter extra_paths 追加 api）**继承写入本轮 update_plan 的同名字段**，Stage 6 合并 module_tree 时一并执行，防遗留改动丢失；③.code-links.json 残留交给本轮 build_index 正常消费——有该文件的文档重新解析 section_code_paths，等价于把上轮修订正式入网，勿手动删除；④wiki_root 遗留无须手动改，build_index 以 `--wiki-root <当前分支>/docs` 重建即覆盖修正。上轮已修订的文档本轮被 state.json 重复列入 changed_files（索引未重建故其 hash=unknown），subagent 复核正文已覆盖后判 line_number_only，merge 刷新 source_hashes——语义等价于上轮修订入网收尾，勿因此重复改正文（2026-11-15 实证：token 23 轮中断于 Stage 6 前，token 36 轮恢复，api/index.py 复判 line_number_only，build_index updated=2/reused=13/total=15、code_paths_verified=215、wiki_root 修正为 main/docs、adapter extra_paths+=api 落地、validate 2/2 通过）。

## 脚本参数契约
- **cb repo-doc 参数以当前安装版本为准**：skill 文档写的 `--skip-heavy-extraction` 在 cb 0.2.67 不存在（报 unrecognized arguments 仅回 usage，不执行），先 `cb repo-doc --help` 核实实际参数集，保留支持的 `--skip-cards` 降参执行，勿因参数不匹配中止预提取（2026-11-13 实证）。
- extract_changed_snippets.py 的 `--changed-files` 必须传 **JSON 文件路径**（脚本内部 `open()` 读取），传内联 JSON 字符串报 FileNotFoundError。变更列表先 write 落盘成 json 文件再传（如 `.codeartsdoer/temp/changed_files.json`）。
- **bash 工具实为 WSL 的会话**（命令输出带 `wsl:` 前缀警告即是）：`_wiki_cmd.sh` 内的 Windows 盘符路径必须写成 `/mnt/c/...`——`cd C:/Users/...` 报 "No such file or directory" 且整条链 `|| exit 1` 提前终止；相对路径（从仓库根出发）不受影响。此场景校验链用 .sh（每行一条命令，勿用续行符），勿沿用 .ps1 写法（2026-11-08 实证：首条命令 `cd C:/` 失败，改 `/mnt/c/` 后 reverse_lookup 正常；2026-11-09 两次实证：脚本内路径变量用 `/c/Users/...`、或参数位置直接写 `C:/...`——后者被 WSL python 相对拼成 `/mnt/c/<workdir>/C:/Users/...` 后报 can't open file——均改 `/mnt/c/` 前缀后全部通过）。
- **双 Python 解释器解析契约**：bash 执行 `_wiki_cmd.sh` 内的 `python` = WSL Python（认 `/mnt/c/` 路径）；bash 直接执行 `python <脚本>` 短命令 = Windows Python（认 `C:/` 正斜杠路径，脚本内硬编码 `/mnt/c/` 报 FileNotFoundError，traceback 路径显示 `C:\` 即 Windows Python 特征）。同一 bash 工具两种调用形态解析器不同、路径风格要求相反——进 .sh 的命令路径写 /mnt/c，**独立 Python 脚本内部硬编码路径务必 C:/ 正斜杠**（2026-11-11 实证：finalize_progress.py 内 /mnt/c 路径经 bash 直调两次 FileNotFoundError，路径改 C:/ 后一次成功）。**含 /mnt/c 路径的 python/python3 脚本命令即使 ≤231 字符也不可直连**——直连通道由 Windows Python 接管，/mnt/c 被解析为相对路径报 can't open file 'C:\mnt\c\...'；一律写 .sh 经 bash 执行以消除通道歧义（2026-11-11 实证：build_index.py 直调约 160 字符仍被 Windows Python 接管失败，写入 .sh 后一次通过）。
- **推荐执行模式：Python wrapper + JSON 任务单（与 .sh 通道二选一，优先本模式；2026-11-11 实证全程零脚本失败）**：一次性写 `.codeartsdoer/.codebase/temp/_wiki_runner.py`——常量 `SKILL_SCRIPTS`（skill 安装目录）与 `CWD`（仓库根，C:/ 正斜杠），读 `_wiki_job.json` 顺序执行 `subprocess.run([sys.executable, f"{SKILL_SCRIPTS}/{job['script']}"] + job["args"], cwd=CWD)`；此后所有阶段只改 `_wiki_job.json`（`{"jobs":[{"name","script","args"},...]}`），执行命令恒为 `python .codeartsdoer/.codebase/temp/_wiki_runner.py <job.json>`（约 60 字符，恒低于 231 上限）。优点：①`sys.executable` 与直调 python 同为 Windows Python，内部路径统一 C:/ 正斜杠，无需判断 bash 解析到 WSL 还是 git-bash，彻底消除双解释器歧义（同日实证：按 .sh 路径在脚本内写 C:/ 脚本绝对路径，被 WSL bash 相对拼成 `/mnt/c/<cwd>/C:/Users/...` 报 can't open file——bash 解析优先级 System32\bash.exe 在 scoop git-bash 之前）；②长参数（skill 脚本绝对路径+多参数）全进 JSON 文件，命令行恒短；③多 job 一单顺序执行（merge×2+validate、redact+lint 各一单跑完），减少 bash 调用次数且单条命令恒可直连。runner 与 job 单必须**同目录配对**，两种等价形态勿跨目录混放（混放会改了 job 单而 runner 读的是另一份）：①`.codeartsdoer/.codebase/temp/`——runner 以 job.json 文件路径作参数；②仓库根 `.codeartsdoer/temp/`——runner 自身读同目录 `_wiki_job.json`，执行命令无需传参（恒为 `python .codeartsdoer/temp/_wiki_runner.py`），job 结构 `[{"name","script","args","cwd"}]` 数组、args 全 C:/ 正斜杠、runner 以 sys.executable+capture_output 顺序执行并按 `===== JOB: <name> =====` 分段打印 stdout/stderr/exit 码（2026-11-13 实证：形态②全程 extract_symbols/reverse_lookup/预处理双脚本/merge+validate+redact+lint/build_index 共 9 job 零脚本失败；cwd 显式传仓库根防相对路径漂移）。
- modified 文件的变更行更直接的做法：`git diff -U6 -- <文件>`（若已提交则 diff 无输出，此时以当前文件实文与 wiki-index 现有记录对照得出新旧差异）。
- merge_section_patch.py：.code-links.json 不存在时自动创建，无需预建。
- **wiki JSON 一律走 Python 读取，勿用 PS5.1 ConvertFrom-Json**：PS 解析 wiki-index.json 报"传入的对象无效，应为':'或'}'"（文件本身为合法 UTF-8 JSON，中文路径/标题内容触发 PS5.1 内部解析器限制）；读索引/回读输出用 wrapper 同款 Python（json.load）或经 runner 落盘的 _last_output.json 用 read 工具读，勿在 PS 里 ConvertFrom-Json 后取字段（2026-11-12 实证：ConvertFrom-Json 失败但同文件 Python json.load 正常，乱码回显仅为控制台 GBK 显示层问题不影响文件本身）。

## subagent patch 流程
- subagent 把 patch JSON **写到文件**（`.codeartsdoer/temp/wiki-patches/<name>.json`，UTF-8 无 BOM）而非粘在返回消息里，防长 JSON 被截断；返回只带文件路径+各小节 action 决策摘要。
- subagent prompt 必须自包含：受影响小节当前原文、变更对照材料（新旧内容/新增文件清单与定位）、模板小节字数规范（架构设计 ≤300 字、其他每节 ≤200 字）、section_title 必须逐字复制 `## ` 后标题、code_refs 行号须实读源文件核实；主 Agent 可在 prompt 中附各小节的同层面预判（基于已读材料），但 action 最终决策要求 subagent 自行判断并为其预判负责。
- **主 Agent 落盘 patch 前必校验四处漂移**：①字段名——subagent 可能返回 `content` 而非规范要求的 `new_content`，而 merge_section_patch.py 只读 `p["new_content"]`，缺失时该小节会**静默按 line_number_only 处理、修订正文无声丢失**（不报错），落盘前统一改回 `new_content`；②引号——subagent 可能把原文直引号 `"..."` 漂移成弯引号 `“...”`，落盘时还原为原文风格；③null 字面量——line_number_only 的 `new_content` 必须是 JSON null，subagent 可能返回字符串 `"null"`，落盘前改回 null；④标题行——prompt 中以"## 标题 <!-- category:... --> <正文>"格式呈现小节时，subagent 可能把标题行整行复制进 replace_content 的 new_content，而 merge 的 new_content 直接替换标题行之后的正文（重组时用 title_raw 重建标题行），不剥离会产生重复标题行——落盘前剥离 new_content 首行以 `## ` 开头的标题行（2026-11-08 实证：4 个 subagent 中 2 个字段名漂移、1 个引号漂移；2026-11-09 实证：line_number_only 返回 "null" 字符串；2026-11-11 实证：3 个 subagent 中 2 个 replace_content 的 new_content 带标题行，剥离后 merge 5/5 无重复；均因落盘前校验而零损失）。
- **区间行号 `path:16-20` 被 validate 拒（报"缺少行号"）**：subagent 对 import 区间等连续行引用可能输出区间格式，validate_code_links.py 只认单行号 `path:line`。此类为确定性错误，无需纠正式重试 subagent——直接 edit 对应 .code-links.json 把区间拆成逐行多条单行号（2026-11-13 实证：关系小节 drill_round06_captured.py:16-20 拆为 :16/:17/:18/:19/:20 五条后 validate 4/4 通过）；预防=subagent prompt 中明确 code_refs 一律单行号格式、禁 `:a-b` 区间写法
- **line_number_only 的 code_refs 以 wiki-index 原值为基线**：先实读核对原引用行号是否仍准确，准确则维持原值。subagent 常把同文档其他小节的引用复制进来造成扩充——未实读支撑的引用一律裁剪回退，避免污染 source_hashes 基线（2026-11-09 实证：概述小节原 2 ref 被 subagent 扩成 4 ref，回退后 merge 通过）。同数量的行号**替换**（非扩充）若新行号有实文对应表述支撑（每个 ref 能指认正文中对应句），可接受（2026-11-09 实证：架构设计 refs :22/:24 被 subagent 实读后替换为 :21/:55，分别对应「仲裁顺序」与「写者约束」表述，采纳后 validate 2/2 通过）。
- **merge_section_patch 的 code_refs 是替换语义，subagent 子集 patch 落盘前必须做并集保护预处理**：merge 实现为 `existing_links[title]["code_refs"] = p.get("code_refs", ...)`——patch 给什么就整体替换什么，**空列表 `[]` 也会清空原引用**；而 subagent 返回的 code_refs 常是其重选的子集（2026-11-13 实证：P003演练适配器 架构设计原 6 锚 subagent 只回 3、business_term 两小节全回 []、知识库笔记架构设计原 14 锚只回 3），直接 merge 会使 build_index 后 section_code_paths 缩水、原锚点永久丢失。合并前写预处理脚本（放 .codeartsdoer/temp/）做并集合并：①新集合条目全部进入；②**同名文件（路径相同忽略行号）以新行号集合整体替换旧行号集合**——subagent 实读核实过的刷新行号为准，防"旧：55 与新：57 并集"留下过时脏锚；③**仅原集合有的文件保留原锚点**。两个伴随修正：④subagent 给出丢前缀短路径（实证：tools/prepare.py:71、vulnerabilities/sqli/source/low.php:11）时按原索引条目**后缀匹配映射回全路径**（workspace/02_软件源码/workflow_base/tools/prepare.py:71 等），否则 validate 报路径不存在；⑤无行号且原索引无此锚的条目（实证：imports.json 裸路径）剔除，防"行号必填"校验错。与上条"回退防扩充"互补：回退堵 subagent 多余引用、并集堵锚点丢失，两个方向都要做（2026-11-13 实证：6 个 patch 并集预处理后 merge×6 全成功、validate 6/6 通过、build_index 254 锚点——P003 capture.py:31 成因 2 补建锚与 models/errors/storage/config 原锚并存生效）。
- **hash_status=changed 的小节即使正文不改、行号不变也必须输出 patch 走 merge_section_patch**：source_hashes 只在 merge 时刷新；不发 patch 则下次 reverse_lookup 对该小节永远报 changed、无法进入 hash 短路，每轮增量都重复修订同一批小节（2026-11-09 实证：merge 输出 hashes_updated 确认事实表新 hash 已写入索引）。
- **merge 覆盖盲区**：merge_section_patch.py 只处理 `## 小节`，H1 标题与 frontmatter description 不在 patch 范围。若模块定位已变（如 notes 模块从 1 篇扩为 16 篇），主 Agent 需手动 edit 这两处，否则 build_index 从 description 提取的 title 会继续传播旧口径。

## 校验与索引
- 校验链顺序：merge_section_patch ×N → validate_code_links → lint_wiki → redact_secrets --check（经 Python wrapper 的 _wiki_job.json 一单跑完，见推荐执行模式）。**路径基准铁律：校验链与 merge 的所有路径参数必须写完整产物路径 `.codeartsdoer/.codebase/branches/<分支>/docs/...`，禁写 `docs` 简写**——`--wiki-root docs` 相对解析到仓库根 docs/（源文档目录），validate/lint/redact 会静默扫错对象且 rc=0 全绿（2026-11-12 实证：--wiki-root docs 时 lint files_checked=3 且列出的全是"官方文档-码道热门Skills清单"等根源文档、validate total=0，全绿为假象；同轮 merge 的 --wiki-file docs/... 直接 FileNotFoundError）。假绿识别特征：lint files_checked 远小于 8 篇产物、文件名含"-desktop0003"等根源文档命名——发现即改完整路径重跑。
- lint_wiki 的 orphan-page-candidate warning 若为全量生成即存在的全库遗留（无 [[module_id]] 双链），记入报告不阻塞；error 才需处理。
- build_index.py `--wiki-root <docs> --code-repo-root <repo> --language zh`：输出"已删除 N 个 .code-links.json"属正常（先消费后删除，非数据丢失）；更新/复用统计即增量生效证据；overview.md 与 WikiRetrieval.md 由其自动再生，读回验证 title/统计行是否反映修订。
- **全量直接写入文档的标题漂移（patch 漂移第⑤形态）**：zh 语言下 subagent 可能保留模板双语标题 `## 概述 / Overview` 原样（全量"直接写入 .md"场景高发，增量 patch 流程无此形态），其 code-links 又用纯中文 section → validate 报 wiki_section 与标题不匹配；修复方向=**edit 文档标题去英文段**（zh 规则+与同批文档一致），勿反向改 code-links 适配错误标题（2026-11-13 实证：应用框架与部署配置.md 六标题全双语，逐个去英文段后 validate 15/15）。
- **README 的 code-links 裸名错名**：subagent 生成复杂模块 README 时可能把 code-links 写成裸名 `.code-links.json`（缺 `README.` 前缀）——内容正确、validate 扫得到且通过，但 build_index 按 `<wiki文件名>.code-links.json` 同名匹配**吸收不到**，README 的 section_code_paths 缺失；validate 通过后仍须查 docs 树有无裸名文件，核对其中 wiki_file 归属后重命名（2026-11-13 实证：DVWA漏洞演练平台/ 与 项目工作区/ 各一个裸名文件，重命名为 README.code-links.json 后 build_index 15/15 全吸收）。
- **全量重建的旧残留清理**：降级/全量重建重置模块树与主题集合后，不属于新树的旧主题目录（project-knowledge 下旧 category 目录）与旧模块文档须在 build_index 前删除，防被全量索引成孤儿条目；两个 index.md 由阶段 5 重写覆盖无需预删（2026-11-13 实证：删 5 个旧主题目录+2 个旧 codebase 文档）。
- 收尾：progress.json 逐 batch 落盘（stage_3/4 的 pending→completed 移转在 merge+validate 通过后立即写，防中断丢失）；临时脚本用完删除，patch JSON 留 temp/patches/ 追溯（temp/ 为入库排除区）。
- **edit 改 progress.json 的边界陷阱**：oldString/newString 必须限制在单个 stage 块内部，勿跨 stage 边界——跨块时易出现 oldString 含相邻 stage 的开头键名行而 newString 忘带该行，导致 `"stage_4": {` 之类键名被吞、JSON 损坏（2026-11-08 实证，读回核实后修复）。**第二形态（2026-11-15 实证）：oldString 与 newString 结构范围不对称**——oldString 以目标 stage 块的完整闭合（`"pending"/"code_links_reviewed"/"quarantined"`+`},`）结尾，而 newString 只写到内部数组 `],` 就结束，遗漏闭合部分，stage 块未闭合直接接下一 stage 报 JSONDecodeError（如 Expecting ',' delimiter）；修复=按报错行号 read 定位缺闭合处，补回 `"pending": [], "code_links_reviewed": ..., "quarantined": [] },`；预防=oldString 起于哪层结构 newString 就必须在该层配对收尾（start/end 各自对称），改完立即 `python -c "import json; json.load(open(path, encoding='utf-8'))"` 验证。跨块/大面积改写二选一：整体 write 并完整保留 module_tree；或写独立 Python 脚本（内部路径 C:/ 正斜杠，见双解释器契约）json.load→改字段→json.dump(ensure_ascii=False, indent=2) 原子完成——update_plan 清空这类超长 JSON 块的修改 edit 无法精确锚定 oldString，Python 原子改最可靠，且可顺带做 WikiRetrieval 标记校验与 stage_6/7/顶层状态一并落盘（2026-11-11 实证：finalize_progress.py 一次完成 update_plan=null + stage_6/7 completed + status=completed）。每次改完用 `python -c "import json; json.load(open(path, encoding='utf-8'))"` 验证合法性再进下一阶段。
- **skill_manage 修改生成技能的通道差异**：edit 校验器按行解析 frontmatter，遇 `description: >-` 折叠样式会误报 "SKILL.md must have name and description in frontmatter" 而拒绝（frontmatter 实际完好）；patch 与 patch_frontmatter 的校验路径可正常处理该样式。改正文用 **patch**，改 frontmatter 用 **patch_frontmatter**，write_file 不能写 SKILL.md 本身（subpath 仅限 references/examples/scripts/assets）（2026-11-09 实证：edit 连续 4 次全拒，换 patch 全部通过）。
