# SDD 四阶段派工流水线

## 阶段序列（禁跳阶段）
1. 需求规格：调 spec-requirement-agent → 产出 spec.md（EARS 格式）
2. 实现方案：调 spec-design-agent → 产出 design.md
3. 任务规划：调 spec-task-agent → 产出 tasks.md（任务映射能力编号+验收对照表）
4. 任务执行：按 tasks 顺序实施，全程留痕

## 每阶段 prompt 必带要素
- 上游产物完整路径 + 明确要求"先完整读取"再动笔
- 用户已裁决基线逐条列出（防已否决方案回潮）
- 硬约束清单（禁定时任务、单一事实源、不删文件、禁改规则文件等）
- 要求"简要总结 ≤300 字、结论前置、简体中文、完成后等待用户确认是否需要修改文档"
- 禁止子代理自作主张：完成即停，确认权在用户

## 门禁与授权处理
- 每阶段产物落盘后：结论前置呈报摘要 + 问"是否需要修改文档"，不调 question 工具
- 用户中途追加子任务：冻结当前进行中流程（零写入），追加进 tasks.md 新任务组，经确认后恢复
- 用户全权授权（"一把到底/每个门禁自己卡"）：各门禁自行判定通过，豁免依据+记录留痕；冻结版文档=确认基线
- 唯一可中断呈报：事实性阻塞（工具链不可用/网络全断/磁盘满）
- **门禁约束"拍板前禁引入依赖"的实现策略**（G2 门禁实战 2026-11-11）：评估/选型类门禁要求用户拍板前不得引入第三方依赖时，编码起步即全标准库实现（urllib 代 requests、http.server 代框架、JSON 文件代数据库、unittest 代 pytest），把"依赖引入"整体推迟到拍板后——既有门禁语义保持可验收，拍板后按选型结论再做依赖替换。
- **G4 终验驳回含环境类整改的闭环**（2026-11-11 实战）：验收驳回单除代码修复外常含环境类动作（拉取并调通外部工具/目录结构归拢/架构反思文档）——按 tasks 收尾判据"驳回则按意见修复复测，不越门禁收尾"直接执行（用户打回单即执行授权，无需重新派工）：环境类动作证据逐项落盘（渠道探索证据链+验证 JSON），归拢/重命名类动作须同步刷新全部路径引用（代码推导、文档命令、索引登记）并整链回归后重提终验；驳回理由逐条对应整改记录（"打回理由↔整改动作"映射表口径）。

## 阶段推进指令的时序消歧（"进入下一阶段：X"，2026-11-08 实战）

- 收到"进入下一阶段：X"禁见指令直接调子代理重做：先核状态机当前位（各阶段产物版本、未闭环清单、停驻位声明），再按三分判定归类：
  - X < 当前位（回溯）→ 对齐修订：定位上游基线变更点，对下游文档做减法同步（生效时点切割、被取消项保链不删行、终态注记），禁改既有判定结论；
  - X = 当前停驻位且该位已声明"等待人工终判"→ 终判授权：显式声明"本次推进=终判授权"，随即执行该停驻位声明的既定动作；
  - X = 当前正常待办 → 常规进入下一阶段（本会话主路径）。
- 执行摘要开头一行声明判定结论与依据（如"您指令经判定为常规进入 ST3，基线 spec/design 未变"），给用户即时纠偏入口。

## 非编码派工单的入口分流与执行模式（仅核对/环境自检类，2026-11-09 实战）

- 分流判据：派工单明确"仅核对/不执行编码/不修改源码"且给出明确执行要求与交付物（反馈文件）→ 属运维核查单，**直接执行**；不调 spec-requirement-agent（非编码任务），也不以"非研发任务"为由反问用户想研发什么——反问仅适用于模糊闲聊/无明确动作的情形。
- 核查四层法（工具链挂载状态核查的实证路径，逐层只读）：①规则层——公约/规则文件全文实读，重点找"约束该任务的条款"；②注册双源——ProjectSkillStatus.txt 落盘态 × listSkills 运行时态交叉核对；③工具层——tool_search/工具检索确认有无对应 MCP/内置工具；④底座实存——Test-Path 逐一验证技能脚本/构建产物路径。
- 核查报告固定件：挂载状态三值结论（已挂载/未挂载/疑似未挂载）+ 加载机制一两句 + 约束确认（规则层→技能层→流程层三层链条）+ "派工单要求×规则条款"交叉比对表（逐条给核查结果与出处）+ 派工单原文代码块置于文末并附一两句含义解释。
- 核查动作只读化：全程禁执行被核查的审查/构建链路（如不实跑 PMD/Ruff 审查），只验路径与配置实存；"链路待命未触发"如实标注为正常状态，不算未挂载。

## 混合派工（非编码运维任务 + 编码任务同单）的职责隔离（2026-11-08 TASK-20261108-004 实战）

- 派工单同时含运维确认类任务（体验反馈/定时配置）与编码交付物时：运维任务可在编码门禁确认前先行交付（对话回复/系统级配置），编码任务严格等 spec 门禁确认后才动工——"等用户确认再编码"红线只约束编码任务，运维任务照常执行。
- spec 须设"职责边界 + 背景任务约束承接"条款：运维任务结论仅作编码产物的素材引用，不代替其对话确认本体；验收时交付物分开呈现（对话确认 vs 文件路径），防"把任务1/2 结果伪装成任务3 交付物"的混同。
- 状态变更类运维任务完成后同步项目事实表（如定时任务 ID/cron 表达式/持久化属性一行），保持单一事实源。

## 子代理落盘写后必验（v1 静默失败事故，2026-11-07）

- 并行派发落盘路径必须互斥（2026-11-12 P003 覆盖事故）：同一轮并行派发两个子代理（spec-requirement-agent 产 spec.md+pre_check.md 框架版、general 产 pre_check.md 实测版），两者 prompt 中落盘路径含同一文件 pre_check.md——后写者整文件覆盖先写者，实测版（21601 字节，含全部实测命令与证据）被框架版（4494 字节）静默吞掉。纪律：①派发前逐个核对各子代理 prompt 中的落盘路径清单，任一路径冲突即改串行，或改各自独立文件名（如 general 写 pre_check_evidence.md、由需求代理合并）；②有依赖关系（先实测→后填规格结构）的产物禁并行共写。
- 覆盖事故的发现与恢复（task_id resume 是数据恢复首选）：复验时子代理自述大小/行数与实测不符（自述 266 行/21601 字节 vs 实测 4494 字节）即怀疑覆盖，用 LastWriteTime 判定后写者；恢复不走重测，用 Task 工具带原 task_id resume 该子代理会话（其上下文仍保有完整实测结论与命令证据，零重测成本），恢复 prompt 四要素：①告知文件被并行代理的 v0.1 框架版覆盖、当前磁盘内容是什么；②先读现存文件全文（保留对方与 spec 对齐的结构与门禁编号）；③将自有实测结论填充进该结构替换"待实测"占位，若会话记忆与摘要不一致以会话实际实测为准如实标注；④版本升号+标注"实测填充版"→落盘后列目录+读文件验证→返回摘要。两轮内容合并，结构与证据双全。
- 子代理返回"已确认落盘"不可信：曾发生 spec-requirement-agent 声称落盘 spec.md、主智能体实测该目录 0 个文件，用户在资源管理器中看到空文件夹直接打回。
- **并行派工禁同文件双写（2026-11-12 P003 实证）**：两个子代理并行且产物路径相同（spec-requirement-agent 落 pre_check.md v0.1 框架版 与 general 落 pre_check.md 实测填充版）→后写者覆盖先写者，实测证据整体丢失（末次写入仅 4,494B）。修复路径=用原 task_id resume 被覆盖方会话重新落盘（指示其先读现存文件，把实测结论按现存框架结构填充，禁编造）。纪律：并行派工的落盘路径必须互异，或明确主从时序（框架版先落→实测方按框架结构填充），并在派工 prompt 中写明各自落盘文件互不重叠。
- 主智能体收到子代理返回后立即验证：列目录 + 读文件双确认存在且非空；失败重试 ≤3 次，仍失败则呈报路径与错误。
- 预防：调子代理的 prompt 里就写明"落盘后必须用列目录+读文件方式验证文件确实存在且非空，验证结果写入返回摘要"。
- 用户截图指定落点时先 Test-Path 实测：Windows 资源管理器地址栏会吞前导点（`.codeartsdoer` 显示为 `codeartsdoer`），截图路径 ≠ 字面路径，以实测存在的目录为准。
- 事件流水行追加换行失效（2026-11-08 V1 轮实战，子代理与主智能体侧均复现；**2026-11-12 P003 R1 轮同日三现复现（E2/E3/E4 两处拼接+主智能体 E3 追加一处），证明为高频稳定缺陷而非偶发**）：Edit 向表格文件追加新行时，实际生效结果可能是"新行以 `||` 拼接在上一行行尾"而非独立成行——markdown 解析时两事件挤进一个表格行。纪律：①追加前先重读文件最新内容（他人可能已写入）；②追加后必须重读确认新行为独立行（判定命令=`Select-String '^\\| E\\d'` 行首命中计数与事件数一致）；③发现拼接→拆行修复（oldString 含 `||` 拼接段整段替换为两独立行，内容零改动）+行尾加【复验注】说明修复动作，禁静默改写。（2026-11-12 P003 R1 轮三度复现：E2/E4 两处拼接，子代理侧与主智能体侧追加均高频失效——已成常态而非偶发；考核 events.md 每轮收尾主智能体必须 grep '^\| E\d' 全量计数复验，缺行即拆行+复验注，禁只信子代理自述"已记行"。）
- 截断式抽查=假缺失：用 `tail -1`/`Substring(0,160)` 类截断抽查长表格行，只能看到行首片段，拼接在行尾的内容被截掉→误判"事件行缺失"（本轮实际存在，重读全文才发现）。验证长行/表格行必须读全行或重读全文，禁用截断输出下"缺失"结论。
- 统计口径差异≠验证失败（2026-11-09 实战）：子代理自述行数（如 358 行）与主智能体实测（如 Get-Content | Measure-Object -Line 得 293 行）因换行符/末行统计口径不同而差异属正常——判定标准=文件存在且非空（Length>0），禁因行数对不上触发无谓重试；结构完整性改用 Select-String '^# ' 提取章节清单比对。
- 产物格式变体下的计数陷阱：同类产物逐轮的标记格式会变体（如层级标签 `1.（记忆）`/`1.【记忆】`/`**1.【记忆】**`）——沿用上轮正则计数会假 0。先读样本行探测格式（括号形态/粗体前缀/分隔符），再选匹配正则；兜底顺序=通用计数（如 `^\d+\.`）确认总数 → 细查标签分布 → 两级数字互相印证。
- 并行派工写同一落点=静默覆盖事故（2026-11-12 P003 实战）：两个子代理同轮并行且落盘路径相交（spec 代理写 v0.1 框架版、实测代理写 v1.0 实测版，同落 pre_check.md），后写者静默覆盖先写者——主智能体复验时才发现实测版 21KB 被覆盖为 4KB。预防：并行派工前核对两份 prompt 的落盘路径互不相交，相交则改串行或指定不同文件名；事故处置=resume 实测方子代理会话（复用 task_id），令其把实测结论填充进当前磁盘上的框架版结构（实测证据在子代理会话里，主智能体无权凭摘要编造细节），重落盘后再验。

## 考核轮执行闭环（出题官/批改官两官派工，R1/V1/OLD 三轮实战 2026-11-08）

- 轮次目录结构：`specs/<特性>/exam/<轮次>/{events.md, questions.md, key.md, answers.md, review-report.md}`；roundId 命名=正式考核 R<N>/可运行验证 V<N>/对比 OLD·NEW；events.md 六字段事件链（E1 出题→E2 出题完成→E3 作答完成→E4 批改完成），**先流水记行后派工**。
- 出题官派工契约要素：材料指针（逐轮同口径一致）+角度×题量+认知层级三级覆盖（均非 0）+题答分离两文件落盘路径+落盘后必验要求+完成即退；**范围红线承接用户裁决**（2026-11-12 P003 实战）：用户裁决废弃某路线/术语时（如方案 D 废弃黑板机制），questions.md 头部须显式登记范围约束（禁出被废弃内容题），出题官自查+主智能体读题复核+批改官附加核验三道防线；作答与批改以该声明为红线，被废弃内容零出现；批改官派工契约要素：批改包三件+仅援引 key 逐题三值判定+置信度公式（PASS=1/PARTIAL=0.5/FAIL=0，Σ题分/50）+≥80% 门禁二值结论+独立性声明。
- key 纪律：key 仅交付主智能体，禁混入题目文件、禁在返回摘要复述 key 内容；主智能体核验 key 格式时接触到的要点，须在作答卷头部如实声明接触范围，作答一律以材料原文为依据、不以 key 表述为准（批改官为独立上下文，判分独立性不受影响）。
- 验收机械复核：逐题判定表用 `^\| \d+ \|` 类精确行计数（排除汇总区/角度得分表的重复命中）；题号标记格式逐轮探测（`1.（记忆）`/`1.【记忆】`/`**1.【记忆】**` 变体，先读样本行再选正则）；批改官自述三值分布、逐题表计数、置信度算式三方互证一致才收。
- 事件代记机制：子代理无事件步骤（旧版 SOP）或追加动作失效时，主智能体代记事件行并标注"代记+原因"（如旧版无事件步骤=旧逻辑行为差异，如实留痕保多轮链路可比）；新事件行作独立表格行追加，追加后重读确认未与上一行拼接。

## 用户强硬指令的减法承接（U6 七条实战 2026-11-08）

- 用户在执行中途下达强硬指令（带时限/取消项/硬性数字，且常附"不满足即任务失败"）时：指令优先级最高（规则>知识库），先做 spec 极简修订（减法最小变更集）再继续执行，禁既成门禁回溯改判——已完成的轮次不追溯，用**一条全局注记**声明新口径的适用范围（如"题量 50→5 仅适用今后轮次"），禁逐处改写正文条款值（不反复改写）。
- 已取消的门禁：门禁表该行标"已取消（指令编号+日期）"，其下游硬前置改"由用户指令放行替代"；被取消轮次的半成品如实留痕中止行（如 ROUND-CANCELLED），产物留档备查不删。
- 规则文件类（SKILL.md/.mdc）修改在强硬指令下零直改：指令下达前已直改的文件列"待人工复核清单"（如实登记不回滚），今后的改法列"人工修改建议清单"——两清单落留档文件（如 SPEC_OPTIMIZATION.md，"本文件即留档"口径）。
- 时限型指令：收到即起算，流程按减法压缩并行推进；超时才写 TIMEOUT.md（已耗时长+进度）自停，未超时不动。
- 门禁证据统一载体（多特性复用）：specs/<特性>/gates/ 目录，每门一份 m<N>-<语义名>-gate.md，六段结构=标识/判定时间戳/检查单逐项结论（含证据指针）/放行二值结论/缺口清单/签署区；过程层（events.md 事件流水）与判定层（gate 文件）互存指针互证、互不抄录内容值。

## 裁决落盘纪律
- 用户裁决（含口语音频要点）逐条整理写入当前阶段产物，标注【用户裁决 日期】
- 已否决方案不得在后续版本回潮；修订处标【vN 日期】+修订说明
- 用户打回重进需求阶段时：打回理由逐条整理进新 prompt，并要求修订版规格含"打回理由↔修订动作"映射表（P002 spec 已执行此格式）

## spec 阶段增量补充模式（用户明示"不打回重做、只原地补"，2026-11-10 实战）

## spec 大文档版本修订的编辑模式（多章节编号顺延，v2→v3 实战 2026-11-07）

- 动笔前先全文梳理交叉引用清单：正文互引（"见 5.N"、"N.M R#"）、附录 A 映射表逐行、门禁表/交付清单联动项，逐条列成更新点再开始编辑（本次 604 行文档共梳理出 20+ 处顺延点）。
- 插入新章节导致后续编号顺延时，Edit 的 oldString 替换按编号**从大到小**执行（先 5.7.x→5.8.x，再 5.6.x→5.7.x，最后 5.5.x→5.6.x）——从后往前可保证任一时刻文件内编号唯一；同一批 Edit 调用按此顺序排列即可顺序安全执行。
- 新旧章节标题同名时（插入后出现两个"### 5.4.1 业务规则"），oldString 必须带下一行首句上下文消歧，如 `### 5.4.1 业务规则\n1. **出题官收窄规则**`。
- 长文档多点修订分批执行（每批 5–6 个 Edit，批内互不重叠）；Edit 成功即已落盘无需 read 回验（失败会报错），全部完成后统一 grep 旧引用残留模式（如 `见 5\.5|5\.5 R|5\.8 R1-`）确认零残留，grep 无匹配即为校验通过。
- 顺序依赖的改号必须分轮（2026-11-12 实战修正"同批按顺序排列"的说法）：同轮消息内的多个工具调用并行执行、先后不保证——编号顺延链上相邻两步（如原 5.4.1→5.5.1 与原 5.3.1→5.4.1）若同轮且新号步先执行，会撞前者 oldString（同名标题命中两处失败）。分轮执行：每轮只放相互独立的编辑（倒序链上一步一轮），同轮内可混入文本互不重叠的引用联动编辑。
- 插入新章节的 Edit 放在整批改号完成后的最后一步（2026-11-12 实战）：插入的 newString 自带一整套新小节标题，若先插入，后续旧小节改号的 oldString 会命中插入引入的同名标题；最后插入时 oldString=原主标题（此时唯一），newString=新章节全文+顺延后的原主标题，一步完成"插入+原章节改号"。
- 落盘验证三件套（用户修订纪律明确要求时逐项执行并写入返回摘要）：①列目录确认文件存在与字节数（Length>0）；②read 抽查关键修订区（头部版本块/新章节定位/附录）；③grep 双向校验——旧编号引用残留清零（如 `（5\.[3-8]）|见 5\.[3-8]`，命中项逐一核对确为修订后应存在的正确引用）+ 新结构落位（章节标题清单/新标记计数）。
- 修订摘要按固定四要素输出：①改了哪些章节（表格式）②新增条款编号 ③待裁决项闭合状态（闭合须注明日期+依据，如"附录 B1 已闭合，依据 U4"）④停驻声明等待用户确认。

## design 阶段大文档分块写入法（新建 600+ 行文档，2026-11-07 实战）

- 适用：design.md 等单次生成超长（500+ 行）的产物。一次性 write 超长内容有失败/截断风险，改为分块追加。
- 执行序：①glob 确认目标文件不存在（存在则改为 Edit 更新，防覆盖）→ ②write 写入首块（文档头+第一章）→ ③后续每块用 Edit 追加，oldString=**上一块末尾最后一句原文**（锚点唯一且刚写入、必定命中），newString=锚点句+下一章正文 → ④全部完成后统一校验：行数 + `Select-String '^# '` 提取顶级章节标题清单与预期结构比对。
- 锚点变体（2026-11-09 实战，600+ 行分 6 块）：写每块时在块尾预埋 HTML 注释锚点 `<!-- ANCHOR-SEC-N -->`，下一块 Edit 以该锚点为 oldString（逐字命中零歧义），newString=本章正文+下一个锚点，末块移除锚点。比"逐字复制上一块末句"更稳：不依赖正文句子形态、不怕末句含表格/代码块等难以逐字复制的结构；锚点在最终校验时顺带 grep 确认无残留。
- 分块粒度：按顶级章节切（本次 645 行分 4 块：第一章 / 第二章前半 / 接口+数据模型 / 测试+风险+附录承接+追溯表），每块独立成篇可校验。
- 锚点纪律：oldString 必须逐字复制前块结尾（含标点），禁凭记忆重写；newString 以同一句开头实现无缝衔接。

- 可执行验证方法五要素（写入门禁检查单/条件）：①扫描命令（可重放）②关键词清单（按对象分组+保留项豁免口径，如保留技能名命中不算残留）③豁免区（历史留痕允许命中但须 archived 标记且现行加载入口不指向）④判定标准（现行区零命中）⑤留档要求（输出存指定文件、追加式不覆盖）。预扫描基线数字写进设计（如"当前命中 29 行，全部对应剥离对象"）证明剥离覆盖面完整。
- Mermaid 时序图（用户点名"补一张时序图"时）：sequenceDiagram 覆盖完整嵌套顺序（含 alt/else 分支回环），事件箭头先后关系逐条对齐 spec 触发时机条款号；图下附编号硬序约束清单（每条挂 spec 条款）；消息/Note 文本内英文冒号改中文标点防渲染歧义。
- 批量并行 edit 实测：同一文件多处修订，oldString 各自唯一且互不重叠即可一轮消息并行（实测 8 个/轮；2026-11-08 tasks v2 对齐修订实测单批 13 个、共两批 24 处全部成功）；"从大到小顺序"仅在编号顺延替换（旧编号须先改）场景需要，不重叠的追加/替换无需排序。

## 口径级全量替换修订模式（spec+design 双文档同步升版，v1.1→v2.0 实战 2026-11-10）

- 适用：用户下达**口径级修订意见**（全局约束变更，如"取消隔离环境、改本机直跑、红线保留"），且授权"不预设修改方案、该改哪改哪、全量重审"——既非追加式（多疑问模式）也非编号顺延，而是旧口径词贯穿全文的**替换式重审**。
- 动笔前：spec+design 两份全文读齐（长文档 offset 分段续读）+ 列目录确认无其他相关文档；先把"旧口径词→新口径词"替换映射列成清单，按文档结构逐类过一遍（术语定义/DFX 红线/业务规则/异常场景/交互流程图/数据约束/接口契约/类图字段/追溯表）。
- 修订次序：先 spec（需求源升版）后 design（承接方同步升版），双文档头部修订记录均登记本次变更，版本号联动（如 v1.1→v2.0）。
- 红线与机制的分离处理：安全红线条款**逐字保留**（仅环境措辞随口径同步）；环境机制条款能删则删、能简化则简化。强制机制在新环境下无法达成时降级为"建议"并在风险登记中说明边界，同时把红线的可验收落点转移到仍可机器校验的层（实战："隔离环境网络闸门"→"任务配置目标地址白名单"，红线本身不放松、校验层换了位置）。
- edit 批量并行每轮 5-6 个；同一短语/组件名在文档多处出现时 oldString 必须带相邻行上下文消歧（如两处 `component "X" as Kali` 用前后行区分）。
- 收尾 grep 双向验证：①旧口径词残留检查——命中项逐个按语境判定，三类属合理残留：历史修订记录中引用旧词（登记性质，必须保留）、无关领域同形词（如"故障隔离/按实例隔离处理"是可靠性术语）、新口径表述自身含旧词（如"不强制虚拟机嵌套隔离"）；三类之外清零才通过。②新口径词落位检查（命中分布与预期结构相符）。
- 追溯表同步刷新：所有被改条款对应行逐行更新要点与承接方式，无空行无悬空；语义标识符变更（如 ISOLATION_UNKNOWN→READY_UNKNOWN）在接口契约与追溯表两处同步。
- 呈报变更点清单固定五要素：①改了哪些章节（表格式）②删了哪些条款 ③新增了什么 ④哪些原条款降级为建议 ⑤哪些原样保留（红线清单显式列出）——停在当前阶段等用户确认，不自行进任务分解。
