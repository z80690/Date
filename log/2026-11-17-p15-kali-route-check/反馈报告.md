# P15 反馈报告：换 Kali 这条路到底行不行

## 你提的想法
三条：①Velxio 在 Windows 上跑不了，换 Kali（Linux）行不行？②Docker 搞不定能不能换方案？③项目根目录 .env 能不能帮上忙？你说这是商量，错了可以不听。

## 我查完的结论：方向得掰一下，但你的怀疑精神是对的

**① 换 Kali——方向偏了，实测不支持。**
- 关键事实：Velxio 的 AVR 仿真是**纯前端 JavaScript**（`AVRSimulator.ts`，用 avr8js 库），跑在浏览器里，不是后端 QEMU。换 Kali 只影响后端，管不到浏览器里的仿真时钟。
- 我直接绕开浏览器，跑仿真内核单测：`npx vitest run src/__tests__/AVRSimulator.test.ts` → **18/18 全过**，里面就有"执行 Blink 固件后 pin13 变高"。**仿真内核根本没坏。**
- 所以卡点不在操作系统、不在仿真内核，在浏览器把 hex 喂给仿真器、驱动时钟那一层接线（`useSimulatorStore.ts`）。换 Kali 治不了这个。
- 还有个硬现实：我实测 Kali 里 pypi、npmmirror 全超时（HTTP 000），没配代理。.env 里只有 Context7 令牌和 SSH 公钥，**没有代理配置**。就算想搬源码进 Kali 重装依赖，网也不通。

**② Docker 换方案——已经在换，而且换对了。**
就是这次的思路：不靠 Docker，本地起全栈 + 直接跑单测，把仿真内核单独验证清楚。

**③ .env——用不上。** 里面没网络线索。

## 一句话
你的直觉"Windows 环境有问题"方向没错，但具体病灶看错了：不是操作系统，是浏览器接线层；仿真内核本身是好的（18/18 证明）。所以不用搬 Kali，下一步该盯的是那段接线代码。
