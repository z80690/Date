# 优化建议报告 · ARTEX 全链路演练（2026-11-25 16:40）

## 建议 1：把"我当大脑驱动框架"固化成可复用脚本（最高优先）
现状：这次靠我临时手搓——自签 token、建任务、包靶机 HTTP，全在对话里一步步敲。下次重来还得重敲。
建议：落一个 `scripts/artex_drive.py`，参数化三件事：靶机地址、任务描述、证据文件。一条命令完成：签 token → 建任务 → 打靶 → 存证 → 清理。
判定：脚本能判 exit code，机器可验，不靠我记性。

## 建议 2：靶机与案例对齐——别再拿错洞
现状：GitHub 唯一能拉到的群晖靶机是 CVE-2025-4679（密钥泄露），而案例库里写的是 CVE-2026-120382（命令注入）。两个洞混过一次。
建议：在 `攻防案例库.md` 每条案例顶部加 `模拟靶机` 字段，明写"有/无/替代品"。无靶机的案例不许拿别的洞顶替演示。

## 建议 3：给本地服务起停做统一封装
现状：PG 用 `pg_ctl` 起会被 shell 退出清掉；ARTEX/靶机用后台托管；关的时候手敲三个 PID。踩了两次坑。
建议：一个 `scripts/local_services.sh`，`start <name>` / `stop <name>` / `status`，统一用托管后台方式，记录 PID 到 `log/.../pids.txt`。守"用完即关"规矩，但别每次手忙脚乱。

## 建议 4：ARTEX 的"无 LLM 模式"要有明确边界声明
现状：`llm_configured:false` 时 ARTEX 只提供 CRUD 和界面，不能自主攻击。用户容易以为"框架起来了=能打"。
建议：在 `攻防案例库.md` 或 ARTEX 规矩文件里写明三档：①界面验证（无 LLM 可）②API 驱动（我当大脑，可）③自主攻击（必须 LLM，本机没有）。防止下次又拉扯。

## 建议 5：证据录入缺口——补一个"手动录 finding"的通道
现状：ARTEX 没有 POST finding 接口，证据只能留外部文件，没进框架。全链路最后一截断了。
建议：要么用 ARTEX 的 agent 会话 + MCP 工具录（需配 LLM），要么承认框架只做任务台账，证据独立存。二选一写死，别悬着。

## 优先级
1 → 3 → 2 → 4 → 5。前两个直接消除这次踩的坑，后三个防概念混淆和链路断点。
