## 三个必须说清的事实

1. **靶机是别的洞**。GitHub 这个是 CVE-2025-4679（群晖 ABM 密钥泄进 URL，CWE-522），不是早上那篇 CVE-2026-120382（命令注入，CWE-88）。不能混。

2. **"用我自己"的落地方式**。ARTEX 自己长脑子必须有 LLM 端点。用户不让启本地模型，我也没有可暴露给它的模型接口。所以走的路是：我当大脑，通过 ARTEX 的 HTTP API 驱动它——自签 token、建任务、录证据。ARTEX 在这条链里是**被驱动的平台**，不是自主攻击主体。

3. **没录 finding 进 ARTEX**。ARTEX 没有直接 POST finding 的 API，漏洞由 agent 会话经 MCP 工具写入。要走那条路必须有 LLM agent。所以证据留在 `evidence.txt`，没硬塞进框架冒充它的产出。

## 追加：为什么"我能连、OpenRouter 连不出"（17:19）

用户问：都在一台电脑上，为什么 WorkBuddy（我）能连模型，OpenRouter 连不出？

1. 我用的模型是 `CODEBUDDY_CURRENT_MODEL_ID=hy4flash-free`——腾讯自有模型，**根本不走 OpenRouter**。所以"我能连"和"OpenRouter 能不能连"是两条完全独立的路，没有可比性。
2. 我走的是 WorkBuddy 内置本地网关 `127.0.0.1:60156`（进程 12080），带 `CODEBUDDY_GATEWAY_PASSWORD` 认证。探活：根路径 200，`/v1/models` 等 OpenAI 路径 401；用 gateway 密码 Bearer 认证后变 404 `No mapping found`——认证通过，但这网关是内部 hook 服务，没有标准 OpenAI 路由。
3. 结论：**我不是"用 OpenRouter 连出来的"**，我是走腾讯自有模型的内部网关。用户看到的"我能说话"≠"这台机器能连 OpenRouter"。两者通道不同。

**为什么我不能把自己当模型喂给 ARTEX**：
- 我是跑在 WorkBuddy 会话里的 AI，没有对外开放的 OpenAI 格式 HTTP 接口（本地 60156 是内部 hook 网关，非标准 chat/completions，且不对外暴露给第三方程序）。

- 所以"我也是大模型"成立，但我这个大模型**不以 ARTEX 能调用的形式存在**。

**最终定性**：不是能力问题，是通道形态问题。要 ARTEX 自主跑，缺的还是"一把有效且对话路径放行的 OpenAI 兼容端点"。当前机器上：OpenRouter 对话路径被拦、其余 key 失效、我的通道不给 ARTEX 用。

## 重大更正 + 深挖结论（17:27）

**先认错**：17:00/17:07 我说"Request path cannot be relayed 是本机网络策略拦的"——**错了**。抓完整响应头坐实：`Server: cloudflare`、`x-openrouter-error-origin: client`、`x-openrouter-release: api;7c...`、`CF-RAY: ...-LAX`、`Set-Cookie: __cf_bm`。这些是 OpenRouter 自己服务器发出来的。请求**到了** OpenRouter，是 OpenRouter 服务端拒的，不是本机拦的。

**这把 key 的真实状态（GET /api/v1/key，权威）**：
- `is_management_key:false`、`is_provisioning_key:false` → 普通可用 key
- `limit:0.1` 美元、`limit_remaining:0.1`、`usage:0` → 有额度、没用过
- 结论：key 完全正常，不是废 key。用户判断对，我先前说"通道拦"是误判。

**把所有可能性排除干净**（都返回同一个 `Request path cannot be relayed`）：
| 尝试 | 结果 |
|---|---|
| POST /api/v1/chat/completions（裸） | 400 |
| 加官方要求头 HTTP-Referer + X-Title | 400 |
| 加全套浏览器指纹 User-Agent/Origin | 400 |
| POST /api/v1/messages（anthropic格式） | 400 |
| POST /api/v1/responses（文档推荐新端点） | 400 |
| Python urllib 发（换TLS栈） | 400 |

对照：GET /models、GET /key 都 200 正常。参考官方文档确认路径格式无误。

**定性**：OpenRouter 服务端针对本出口 IP，**统一拒绝所有对话类 POST**（chat/messages/responses 全拦），但放行 GET。这不是 key 问题、不是格式、不是本机网络、不是工具。是服务端侧的访问控制（可能是地区/IP 策略，错误头 `x-openrouter-error-origin: client` 是它自己的标记）。本机 curl 的 TLS 吊销检查问题只是附带小坑（加 --ssl-no-revoke 已绕过），不是主因。

**前台"添加模型"框救不了这个**：
- 供应商下拉只有「腾讯云 Token Plan / 通用 Token Plan（个人版）」，没有 OpenRouter 选项无处填这把 key。
- 该框配的模型是给 WorkBuddy 自己用，与 ARTEX 是两套独立配置。
- 官方 docs 站无模型配置页（Model-Settings/Models 均 404）。

**最终**：这把 key 是好的，但 OpenRouter 服务端不接受从这个出口发来的对话请求。前台配不了、后台也被服务端拒。要让 ARTEX 自己跑，只能换一个出口环境（换网络）或换一家服务端放行的模型商。这是当前唯一诚实的结论。

## 追加：ARTEX 是否必须配钥匙 + GitHub 议题调研（18:20）

**用户问题**：ARTEX 必须配钥匙吗？GitHub 议题有没有解决方案？

**来自 GitHub 的实际证据**：
- 分支仓库 `RuoJi6/ARTEX`（原作者 `Autumn-27/ARTEX` 已不维护）。翻遍 OPEN 22 + CLOSED 47 条议题。
- **议题 #187**（2026-11-25）：标题 `openrouter Request path cannot be relayed code 400`，跟我们的错误一字不差。填 `https://openrouter.ai/api/v1`、GET 模型没问题、POST 报 400。**当天提问当天自己关闭，零评论，无公开解法**。用户猜"议题里有解决方案"——实测没有。
- 议题 #68：OpenCode 格式要加 `x-opencode-session` 头；另有人"通过中转格式解决"（非本错误）。

**"是否必须配钥匙"**：ARTEX 文档写明——探索必须配 LLM（环境变量 key 或 UI「LLM 配置」页）；只有 Demo 模式（纯前端）不需要密钥。它本质是 LLM 多 agent 系统，没模型就干不了活。

**错误对照实验**（钉死责任层）：假 key 打对话路径→401；真 key 打错路径→404；真 key 打对话路径→400 Request path cannot be relayed。请求到了 OpenRouter、key 认、路径对，是它 relay 层拒对话请求。六种绕过全失败。官方错误文档无此条。

**其他钥匙全堵**：DeepSeek/智谱失效、超算地址错、jev(typesafe.ai)是打分接口非聊天、WorkBuddy 内部网关无 OpenAI 路径。

**结论**：GitHub 无解法；ARTEX 必须配模型；OpenRouter 钥匙好的但服务端拒对话；当前机器凑不齐可用端点，ARTEX 自主跑暂时不通。详细见 `ARTEX是否必须配钥匙-调研报告.md`。
