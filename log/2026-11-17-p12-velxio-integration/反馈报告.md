# P12 反馈报告 —— Velxio 集成实测

## 这单要干嘛
上一单（P11）我把 Velxio 登记成了固件仿真器，但只验到"本地 Windows 原生测试大面积挂"，就老老实实标了"不默认启用、信心 L2"。你把客观条件摆出来了——Docker 有、引擎在跑、还有代理和 Kali。这单就是让我别停在"没条件"，把上一份优化建议里第一条（把 Velxio 真跑起来）干到底。

## 我怎么干的（先猜一步，拿现实校一步）
1. **先打基线**：`4698b44`，改错了能退回来。
2. **猜 Docker 能用**：截图上明写 Engine running，命令行实测也通（v29.9.3）。但一拉镜像就露馅——官方镜像 1.55GB（一层就 999MB），ghcr.io 国内直连 136KB/s、走代理 373KB/s，Docker 的 daemon 还不吃系统代理，拉了十几分钟一层没下。**现实校完：Docker 这条路今天走不通，我不假装拉成了。**
3. **换路**：Velxio 的 `compile_project` 本质就是调 arduino-cli 编 sketch，Docker 镜像里也只是多装了个 arduino-cli。那我本地直接装 arduino-cli（20MB，走代理秒下）+ AVR core（50MB）+ AVR 编译器，用仓库自带的 venv 跑 Velxio 自己的 MCP 工具——验的是**同一套 Velxio 代码、同一个能力**。
4. **跑通了**：Blink 编出真 hex（2556 字节），`success: True`，`simulation_ready: True`，结论行 `VELXIO_MCP_BLINK: PASS`。这是真跑出来的，不是静态推断。

## 结论（不粉饰）
- **编译层：真跑通了。** Velxio 自带的 MCP 工具在本地把 Blink 编成了 hex，这是它固件编译能力的实打实验证。
- **信心等级：L3，不是 L4。** 我只验到"编译出 hex"。Velxio 的仿真**执行**是在浏览器前端做的（官方 MCP 文档写明的），我这边没跑浏览器；ESP32/小智固件要 ESP-IDF（优化建议里的 O4），也没编；Docker 官方镜像端到端没成。这三样都没验，所以不敢标满级。
- **开关翻成 True 了，但带诚实边界**：`firmware_sim_path.enabled` 从 False 翻到 True，`measured` 里写清楚验了什么、没验什么，字段 `not_yet_verified` 明列三件未做的事。

## 集成做了什么（优化建议 O2）
写了个适配层 `velxio_adapter.py`（纯标准库），干三件事：
- `detect()`：逐项查真实文件（arduino-cli / venv / 验证脚本 / AVR core），缺一个就报 `unavailable`，**绝不静默返回 True 假装可用**。
- `compile_blink()`：调 Velxio 的验证脚本实编 Blink，返回归一化结果。
- `capability()`：声明这是固件层、`protocol_layer_replaced=False`（协议桩保留，两层互不替代）、列出未验事项。

配套加了 4 项单测，专门验"环境缺失时不假装"。

## 测试
- 适配层单测 + 原有适配层测试：23 项全过

- 全链路 `run_final.py`：`all_pass: true`（g6/g7/g8 三段全绿）——集成没破坏任何原有链路
