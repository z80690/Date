# P12 优化建议报告

## 这单验证了什么
Velxio 的**编译层**在本地真跑通了（MCP 工具编 Blink 出 hex）。但还有三件事没验，列成后续派工单待办。

## 下一份派工单待办

### O1：把 Docker 官方镜像这条路打通（想验完整板级仿真就得做）
现状：镜像 1.55GB，ghcr.io 国内太慢（直连 136KB/s、代理 373KB/s），Docker daemon 还在自己的 Linux VM 里、不吃 Windows 系统代理，拉了十几分钟一层没下。
两个解法：
- 给 Docker Desktop 的 daemon 配代理（daemon.json 里加 proxies，指向 `host.docker.internal:代理端口`），或
- 找国内可达的 ghcr.io 镜像源 / 用 GitHub Actions 把镜像转存到 Docker Hub。
打通后用官方命令起服务，开 `http://localhost:3080`，能验浏览器里的 ESP32 Blink 真跑。

### O2：浏览器前端仿真自动化（补 L3→L4 的关键一块）
Velxio 的仿真执行在浏览器前端。可以用浏览器自动化打开自托管页面，加载编译出的 hex，抓串口输出 / LED 状态，证明"不只是编出来，还真跑起来了"。这一步过了，信心才能从 L3 升 L4。

### O3：ESP32 / 小智固件编译加载（原 O4，最后一块）
AVR Blink 只是最小验证。真目标是小智固件跑在 ESP32 上，需要 ESP-IDF 工具链（比 AVR 大得多）+ 对应板型。这是"固件层真跑通"的最后一块，依赖 O1/O2 先通。

### O4：把适配层接进 catalog/门禁
现在 `velxio_adapter.py` 是独立可用 + 有单测，但还没挂到 `workflow_base/core/catalog.py` 的目录里、也没接进统一门禁（优化建议 P11-O3 的三副本校验门禁同样还散着）。等前三条验完，再做统一挂载。

## 一条经验（给后面的活）
这单又验证了一次第七条"预测校正"：我一开始猜 Docker 能用（截图 + 命令行都显示引擎在跑），拿现实校一步才发现镜像根本拉不动；没死守判断，换成等效的本地路线，反而把编译层跑通了。**开关翻 True 之前先有真 hex，没 hex 就不翻——条件不满足不假装。**
