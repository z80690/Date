## 第二部分：Velxio 对比与接入

### 它是什么（核实过了，不是听头条吹）

官方仓库 `davidmonterocrespo24/velxio`，3.7k+ 星，AGPLv3。浏览器里跑的真固件仿真：40 块板子、5 种 CPU 架构、150+ 元件，QEMU 跑真固件，带串口/GPIO/示波器，还有 MCP 接口给 AI 调。头条说的属实。

### 关键判断：它不是来"替换"的，是来"填空"的

|-|原方案（小智桩）|Velxio|
|--|--|--|
| 层次 | 协议对答（不加载固件） | 真固件仿真（QEMU 跑指令）|
| 干的事 | 回答 chat/status_query | 跑 Arduino/ESP32/Pico 固件 |
| 关系 | 两层，互不替代 | 补上工作流一直空着的固件仿真层 |

咱工作流文档早就写了要用 Renode/QEMU 做固件仿真，但代码里 `firmware_sim_path()` 一直是 `enabled: False`，从没落地——**真跑的只有一个 69 行的协议桩，根本不是仿真器**。所以你说"底层仿真环境不太合理"，直觉是对的：那位置本来就空着。Velxio 正好能填。

### 实测：Windows 原生跑不通，得走 Docker/WSL

拉到 `D:/refs/velxio`（git clone 被网络重置，改用 tarball 下载，71M，完整）。装好依赖跑官方单元测试：

**1769 过 / 243 败 / 8 错 / 10 跳。**

失败主因挑清楚了：`pass_fds not supported on Windows`（POSIX 文件描述符传递，QEMU 子进程要用），426 处；其次是 Arduino 库路径没装。**这是平台问题，不是 Velxio 代码烂**。它官方主推 Docker，README 里也是 Docker 优先。本机 Docker daemon 没起、WSL Kali 里也没 docker，所以 Docker/WSL 路线本次没实测（这条结论我标 L2，不冒充 L4）。

### 怎么接的

没有傻乎乎地"整个换掉"。做法：
- 协议桩保留（Velxio 干不了业务协议，也不该干）。
- `firmware_sim_path()` 登记 Velxio 为推荐固件仿真器，写清实测结果和限制。
- **保持 `enabled: False`，不默认启用**——因为当前环境跑不通，硬开只会把原来全绿的链路搞崩。这是拿实测校过之后的决定，不是拍脑袋。
- 工作流文档、选型声明同步更新，Renode/QEMU 降为备选。

### 验证

接入后原闭环测试 `run_final.py` 仍全绿（all_pass: true，g6/g7/g8 全 true）。没破坏现有东西。

## 一句话结论

O1-O3 落实完，测试全过。Velxio 是好东西，但它填的是"固件仿真"那个一直空着的层，不是替换协议桩；本机 Windows 跑不通、要 Docker/WSL，所以先登记接入、不默认启用。没粉饰的 FAIL：Velxio 本机测试 243 败是真实情况，已如实写清原因和应对。
