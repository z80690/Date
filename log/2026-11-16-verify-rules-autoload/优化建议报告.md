## 三条根因（挑刺，不附和）

### 1. alwaysApply 没注入 —— 大概率是"会话工作区"错位
本会话的工作区是 `C:/Users/Administrator/WorkBuddy/2026-11-16-14-32-11`，
而规则、子智能体都在 `C:/Users/Administrator/Desktop/Date`。
平台的"项目级 alwaysApply 注入"是**按当前打开的工作区**扫描的。
派工单背景说"上一会话已注册可见"，但那是上一会话、且当时打开的很可能是 Date 工作区。
本窗口工作区不对 → 扫不到 Date 的 `.workbuddy/rules/` → 没注入。这不是规则写错，是打开姿势的问题。
**验证动作**：必须在 Date 工作区新开对话，再看启动上下文有没有六条+八条正文。本窗口自证不了。

### 2. 子智能体不可用 —— 同理，注册未跨工作区继承
`sdd-examiner` / `sdd-grader` 报 `not available`。本会话可用子智能体清单里没有它们。
project 级子智能体注册大概率绑定工作区，非全局。换到 Date 工作区新开会话再验。

## 可落地为自动门禁的建议（不只停留在文档）

   的整文件 MD5 写死为常量，CI/门禁里比对，不符 exit 1。杜绝"基线记错还查不出来"。

4. **子智能体可用性探针**：把 `subagent_type=sdd-examiner` 的可用性检查纳入会话启动自检，
   报 not available 时明确提示"请在 Date 工作区打开会话"。

## 关于 git 提交方式的偏离（重要，需用户知晓）
派工单交付第 3 条要求 `git add -A`，但同时约束"不动 .codeartsdoer/"，
且跨项目永久规矩是"精确 git add、禁止 -A"。
第一轮 `git status` 显示 `.codeartsdoer/` 下有一批既有的 M/?? 改动（码道目录，非本任务产物）。
`git add -A` 会把这些隔离目录的半成品一并提交进 main —— 这既违反"不动 .codeartsdoer/"，
也违反"禁止 -A"，属于把别人的未完成改动正式并入主干的重大副作用。
**处置**：改用精确 git add，只提交本任务 5 个产物（2 副本 + 3 报告），不纳入 .codeartsdoer/。
**风险**：低。.codeartsdoer/ 改动保持原样、不丢失，只是未进本次提交。
**客观结果**：因此工作区不会因本任务而"完全干净"——.codeartsdoer/ 的既有改动仍在。
派工单"工作区干净"一条，在不碰隔离目录的前提下无法同时满足，如实说明，不造假。
