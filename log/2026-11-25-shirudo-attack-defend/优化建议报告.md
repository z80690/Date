# 优化建议报告 · Shirudo 攻防演练（2026-11-25）

## 一、结论先行

Shirudo 的方向对（补丁前的临时护盾），但**这个 java-sql-inj 盾的判定太窄**，
而且**部署门槛高到这台机器根本跑不起来**。两条都能改。

## 二、发现的问题（按严重度排）

### P1 · 正则漏主流写法

现状：`(['"]\s*--)|(\b(OR|AND)\b\s+\d+\s*=\s*\d+)`

漏网：
- `'1'='1'`（带引号数字）
- `'a'='a'`（字符串恒等）

影响：第二关实测的第一打法直接穿盾。

**建议**：别靠正则猜。用参数化查询（PreparedStatement）从根上消除注入——
真修好了根本不需要盾。盾只能用在"没法立刻改代码"的过渡期，
这时候判定至少扩到：
```
(['"]\s*(--|#|/\*)) | (\b(OR|AND)\b\s+['"]?\w+['"]?\s*=\s*['"]?\w+['"]?)
```
但仍只是更宽的猜，不是根治。

### P2 · 环境门槛与 WSL2 不兼容

官方 quickstart 要 KVM + 测试内核 + clang/LLVM23 + QEMU + swtpm + TPM 工具链。
WSL2 无 `/dev/kvm`，死结。装依赖也绕不过。

**建议**：这台机器上别硬跑 quickstart。两条路：
1. 用官方**在线 lab**（`labs.isovalent.com/#/lab/shirudo-getting-started`），浏览器里跑真 VM
2. 真要本地跑，得在 Windows 装 VMware/VirtualBox 起完整 Linux VM（不在本次范围）

### P3 · 实验脚本自身的坑（已修）

第一版忘了 URL 解码，误判漏网数。这类"模拟层错误"会污染结论。

**建议**：所有源码级模拟，先把真实数据流路径列清楚（这里：HTTP 参数 → URL 解码 → 拼 SQL → RASP 检查）。
少一步就得出错结论。本次已加 `unquote` 并留修正记录。

## 三、值得学的设计（不是挑刺）

1. **签名 + 人工批准**：盾要签名才加载，agent 不能直接上线规则——把权力关在笼子里
2. **先观察再生效**：可以先看盾会拦什么，不影响服务，再决定启不启用
3. **TPM 记账**：谁加了盾、谁撤了盾，留硬件级证据
4. **明确 self-limitation**：README 直说 pre-release、要专门内核、root 能绕过 Java agent——不吹牛

第 4 条最值得学：诚实标注边界，比吹"全能防护"靠谱。

## 四、落地到咱们项目的建议

咱们有 `adapter/` 代码门禁（白名单、越界即停、回执驱动）。建议：

- 把"模拟层数据流要完整"写进测试规范（对应 P3）
- 别引入正则式防护当主力——咱们已有白名单机制，比正则硬
- Shirudo 的"签名+人工批准"思路可借鉴到门禁规则变更流程

## 五、优先级
