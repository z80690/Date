# 优化建议报告 — ARTEX 靶场授权攻击演练

演练日期：2026-11-24｜配套：运行时报告.md / 反馈报告.md

## 建议一：让网络层跳板 IP 真实可见（补当前最大短板）

**问题**：单机回环栈出站源 IP 固定 127.0.0.1，跳板 IP 只在应用层 XFF 体现。
**方案**：用 Docker 容器网络，每个跳板独立容器、独立 IP（172.x 网段），容器间转发的源 IP 就是真实跳板 IP。
- victim 容器 172.20.0.4、jump2 容器 172.20.0.3、jump1 容器 172.20.0.2
- 每容器日志的 src_ip 会是真实上一跳 IP
**代价**：本机 Docker daemon 当前未运行，需先启动。收益是拿到网络层真实逐跳 IP 证据。

## 建议二：日志实时外发，反制痕迹擦除（防守核心）

**问题**：本次攻击者删本机日志就得手（3 行证据被删）。
**方案**：victim/jump 的日志每行生成即通过 UDP/syslog 发到独立日志容器，攻击者删本机文件也删不掉已外发的副本。
- 演练版：加一个 collector，日志双写本地 + `artifacts/logs_remote.jsonl`
- 擦除后对比：本机剩 2 行，remote 仍有 3 行 → 证明"集中日志让擦除失效"
**价值**：这是真实对抗里反 anti-forensics 的标准手段，值得加进下一版靶场。

## 建议三：护栏升级为“规则表 + 检查器”（符合项目约定）

**现状**：boundary_guard.py 白名单硬编码 127.0.0.0/8，够用但写死。
**方案**：按项目既有约定（维度可判的编码进注册表+检查器，exit code 可判）：
```
config/range_rules.json    # 允许网段、禁止网段（含中国 IP 段列表）、动作
scripts/boundary_check.py  # 读规则表校验，exit 0/2
```
收益：改规则不用改代码；中国 IP 段可单独列成禁止清单，命中即拒并标注原因。

## 建议四：把 ARTEX 引擎真跑起来（需补环境，按需开启）

**前提缺口**：LLM 服务 7810 停、API key 空、Docker daemon 未跑、无靶场镜像。
**补齐路径**：
1. 起本地 LLM 或填 API key（注意：会消耗额度/费用——正是你在意的积分问题）
2. 启动 Docker Desktop
3. `docker compose -f docker-compose.bench.yml up --build`，浏览器 localhost:8787
4. 在 ARTEX UI 里建任务、配目标、开人在环路审批
**权衡**：这条会真实消耗 token/额度。要与"积分掉"的顾虑一起权衡——先补环境再决定是否用 ARTEX 引擎跑。

## 建议五：漏洞面扩展（按需）

当前只演示目录穿越（CWE-22）。可加：命令注入、未授权访问、弱口令。每个漏洞配独立检测规则，形成“攻击-检测”对照矩阵，更适合系统研究攻击者行为。
