# 漏洞报告 · 第四关（上传洞 + 后果演示 · 掺沙子版）

| 项 | 内容 |

## 二、最重要的一条：数据是假的

靶机里被读出来的 `fake_secrets.env`，内容全是**编造的**：

```
FAKE_DB_PASS=THIS_IS_FAKE_DO_NOT_USE_12345
FAKE_API_TOKEN=fake-token-0000000000
```

文件名带 `fake_` 字样，文件第一行也写明"本文件全是靶机编造的假数据，不是真实密钥"。

**没有读任何真实凭据、没有读真实系统文件、没有提权、没有横移、没有跳板。** 这关演示的是"漏洞成立后危害长什么样"，不是真攻击。

## 三、复现步骤

1. Kali 里启动靶机：`python3 vuln_app4.py`
2. 看首页功能：`curl http://127.0.0.1:8768/`
3. 正常上传文件：`curl -F "file=@/tmp/web4/note.txt" http://127.0.0.1:8768/upload`
4. 正常查看：`curl "http://127.0.0.1:8768/view?name=note.txt"` → 看到刚传的内容
5. 改成 `name=../config/fake_secrets.env` → **读出了假配置**

## 四、关键证据（原文照抄）

```
=== 2 先探一下：能不能跳出上传目录（读上级的假配置）===
{"file": "../config/fake_secrets.env", "content": "# ===== 本文件全是靶机编造的假数据，不是真实密钥 =====\nFAKE_DB_HOST=127.0.0.1\nFAKE_DB_USER=fake_admin\nFAKE_DB_PASS=THIS_IS_FAKE_DO_NOT_USE_12345\nFAKE_API_TOKEN=fake-token-0000000000\n"}
```

复现 3 次一致；读不存在的文件报 `Errno 2`，说明是真文件读取，不是写死的展示。

## 五、如实说明一处对照没做扎实

证据第 5 步我写的是 `../../etc/hostname`，但路径算错了：

`/tmp/web4/uploads/../../etc/hostname` 展开是 `/tmp/etc/hostname`，本来就不存在。所以它报"找不到文件"**不能证明**真实系统文件读不到。

按代码逻辑，多加一层 `../` 是能读到 `/etc/hostname` 的。这一步我**故意不做**——那属于读真实系统文件，超出"掺沙子"范围。报告如实记着，不拿一个错路径冒充边界证明。

## 六、危害（如果这是真网站）

上传接口不检查文件名，查看接口不拦 `..`，两个洞凑一起：攻击者能读到网站目录外的任何文件——数据库配置、API 密钥、源码。

这就是"挖到洞之后"的真实后果。本关用假数据把它演示出来，不碰真东西。

## 七、修复建议

1. 查看文件：把文件名做**白名单校验**（只允许 `字母数字.下划线`），拒绝 `..` 和绝对路径
2. 用 `path.resolve()` 后确认结果仍在允许目录内，不在就拒
3. 上传：限制扩展名 + 重命名文件，不让用户控制最终文件名
4. 密钥不要放在 web 进程能读到的目录里
