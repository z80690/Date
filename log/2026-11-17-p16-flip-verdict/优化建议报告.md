# P16 优化建议报告

## 待办（按值不值得干排序）
### O1：ESP32 / 小智固件编译（真目标，唯一实质缺口）
AVR Blink 已 L4 闭环。真正要跑的是小智固件跑 ESP32，需要 ESP-IDF v5.5.4 + arduino-esp32 3.3.10 + QEMU 库。这是从"验证玩具例子"到"验证真目标"的关键一步，依赖重但值得排期。

### O2：Docker 官方镜像（可缓）
本地全栈已等效跑通 AVR，镜像 1.5G 拉不动。除非要验 ESP32/多板，否则不急。

### O3：验证脚本本身该修（教训固化）
这次翻案的根子是我的验证脚本不可靠：抓错 DOM 元素、没处理弹窗、没读底层日志。建议把 P16 的 `prove_cycles.js`（读 CPU cycles + 处理弹窗）固化成正式验证脚本，替代 P13/P14 那些会误判的脚本。这样以后复验不会再冤枉仿真环境。

## 一条经验（第七条预测校正，这次是重量级翻案）
前面 P13→P15 一路把问题往深里猜：无头限制→仿真内核→接线层，越猜越复杂。P16 按用户"最终能用"逼自己拿最底层证据（CPU cycles），结果发现**问题根本不在仿真，在我的观测手段**。

教训两条：
1. **观测工具本身要先验。** 我用去读状态的工具（抓 DOM 文本）没验过它抓的是不是真东西，就拿它的输出下了结论——等于拿坏掉的尺子量东西还相信读数。
2. **别在错误结论上继续盖楼。** P13 误判后，P14/P15 都在"时钟为什么不走"这个假前提下往下挖，越挖越偏。每轮都该回到最硬的证据重新校验前提。用户反复强调的"拿现实校一步"，这次是活教材。
